# GKS 工科赛 单片机 ↔ 树莓派 串口协议

> 本文档是**双端契约**，单片机端适配时以此为准。
> 权威实现见 `protocol.py`（树莓派端）；模拟器实现见 `../GKS_Web/simulator.py`。
> 改动本协议时，需同步更新 `protocol.py` 与本文档。

## 1. 物理层

- 接口：UART（USB 转串口，树莓派端设备节点 `/dev/ttyUSB_GKS`）
- 波特率：`115200`，8 数据位，1 停止位，无校验

## 2. 帧格式（双向统一）

```
SOF | TYPE | LEN | DATA(LEN) | CRC8 | EOF
 1B    1B    1B     LEN 字节    1B    1B
```

| 字段 | 值 / 说明 |
|------|-----------|
| SOF  | `0xAA`（帧头） |
| TYPE | 帧类型，见 §3 |
| LEN  | DATA 长度（0~64），`FRAME_MAX_LEN = 64` |
| DATA | 载荷，长度 = LEN |
| CRC8 | 覆盖 `TYPE + LEN + DATA`，查表算法，初值 = 首字节（见 §4） |
| EOF  | `0x55`（帧尾，重同步二次确认） |

## 3. 帧类型 TYPE

| TYPE | 常量名 | 方向 | 说明 |
|------|--------|------|------|
| `0x01` | `TYPE_CMD` | 单片机 → Pi | 任务指令，DATA = 命令码（ASCII） |
| `0x02` | `TYPE_COORD` | Pi → 单片机 | 结果回传，DATA = 坐标/状态 |
| `0x03` | `TYPE_QR` | 预留 | 二维码任务（6B 颜色码） |
| `0x10` | `TYPE_HELLO` | 预留 | 握手请求 |
| `0x20` | `TYPE_ACK` | 双向 | 应答，DATA = 1B（`0x00` 失败 / `0x01` 成功 / `0xCC` 握手） |
| `0xDB` | `TYPE_DEBUG` | 单片机 → Pi | 调试字符串（ASCII），Pi 端打印后丢弃 |

## 4. CRC8 算法

- 多项式查表 CRC8，初值 = `data[0]`（即 `TYPE` 字节），逐字节迭代。
- 计算范围：`TYPE + LEN + DATA` 三个字段（**不含 SOF/CRC8/EOF**）。
- 查表见 `protocol.py::_CRC8_TABLE`（256 项，与 gcs_stm32 一致）。
- 伪代码：

```
crc = data[0]                      # data = [TYPE, LEN] + payload
for b in data[1:]:
    crc = CRC8_TABLE[crc ^ b]
```

## 5. 握手时序

1. Pi 上电 → 发 `TYPE_COORD` 帧，DATA = `"SYNC_HS_1"`（9 字节 ASCII，不足补 0）。
2. 单片机收到 → 回 `TYPE_ACK` 帧，DATA = `0xCC`。
3. Pi 收到 `0xCC` → 握手成功，进入指令等待。
4. 超时（2s）未收到 → Pi 重发握手帧，循环直到成功。

> **单片机端行为约定**：单片机 `vRpiTask` 收到 `"SYNC_HS_1"` **无论脚本是否在等握手都立即回 `0xCC`**，
> 保证 Pi 任何时刻上电/重连都能完成握手。脚本 `STEP_WAIT_HANDSHAKE` 在首个握手请求后
> 再等一个「静默确认窗」（> Pi 2.5s 重发周期，默认 3s）——窗口内无新握手请求即视为双向链路皆通。
> 窗口内又收到请求 = 应答丢失，单片机已自动补答并重开窗口。

## 6. 命令表（TYPE_CMD 的 DATA，ASCII 字符串）

> **⚠️ 可选的时限后缀（2026-09 加）：** 阻塞类视觉指令（`"1"`/`"D"`/`"E"`/`"F"`/`"G"`）
> 的 payload 可以写成 **`<命令码>,<毫秒>`**（例：`"F,7500"` = 「这条我最多等 7500ms」）。
> 本端拆出头来查表分发，并把这个毫秒数**减掉一个余量**（`config.QR_CMD_MARGIN_S`，
> 默认 1.5s）当作自己的预算 —— 于是「谁先放弃」只由单片机那一个数决定，
> 两边不用各记一个数字互相迁就。
>
> · **不带逗号时行为与加这个扩展之前一字不差**（`head == payload`），老固件照旧能跑；
> · 余量那 1.5s 是留给「开相机 + 回帧」的：单片机是从**它发指令那一刻**开始计时的。
>   少了它，本端会答得比单片机放弃还晚，而**迟到的结果帧会落进下一次重扫的等待窗口里
>   被当成那一次的结果**（扫描 A 的结果被判成扫描 B 的）；
> · 只有 `handler.py::_MS_COMMANDS` 里**登记过**的指令能收这个后缀，其余指令带了逗号
>   会被判成「形状不认识」而拒掉并打一条 WARN —— 刻意**不**静默忽略那个时限；
> · 本端预算另有上限 `config.QR_CMD_MAX_TIMEOUT_S`（默认 12s，护相机租约的空闲看门狗），
>   超了会夹住并打 WARN。
>
> **⚠️⚠️ 同一个形状、两种含义（2026-09 加）：** 预热指令 `"B"`/`"C"` 也吃这个后缀，
> 但那个数是 **使用次数**，不是毫秒：**`"C,2"` = 「主摄接下来要被 2 个任务消费」**。
> 本端把相机租约的空闲窗口放宽成 `次数 × config.LEASE_IDLE_TIMEOUT_S`（见
> `camera_lease.idle_limit_s`），于是隔了一二十秒的第二个任务也能命中同一份租约、
> 不再白花 ~2s 重开设备（任务用完相机**不会**关它，卡住复用的只是那个 15s 窗口）。
> · 不带数字 / 0 / 1 → 窗口就是 1 倍 = **加这个参数之前一字不差**；
> · 倍数在声明的次数**用完之前一直保持**（用满才回到 1 倍），不会越用越窄；
> · 上限 `config.LEASE_USES_MAX`（默认 10），超了夹住并打 WARN —— 因为窗口同时就是
>   「发了预热却没跟进识别时相机被白占多久」的倍数（安全阀）。
> 加新命令族时**先想清楚自己的数属于哪一类**，别照着字面把毫秒抄过去。

> **`"sd"` / `"rb"` 与 `"r"` 不是一回事**：`"r"` 只重启 GKS 主程序，这两个停/重启**整台树莓派**。
> 都是**只收不回**（对方正在关机，没有结果帧）——发完之后单片机会看到心跳停、8s 后自动把链路
> 判为 DISCONNECTED，这是预期现象；重启后 `gks.service` 自启并重新握手，链路自行恢复。
> ⚠️⚠️ **`"sd"` / `"rb"` / `"r"` 三条都要求「连发两次」才执行**（防误触）：树莓派端
> `handler.py::_require_double_send` 只记下第一次、打一行日志，同一条指令在
> `config.SYSTEM_CMD_CONFIRM_S`（默认 10s，Web「设置参数」可调）内**第二次到达才真执行**；
> 执行后还有等长冷却，所以「卡住的连发」最多一个窗口执行一次。
> **两次必须是两次操作**（操作员按两次键），一次按键里连发两帧等于没有确认。
> ⚠️ 树莓派端服务跑在普通用户 `xixi` 下，关机/重启要提权：优先 `sudo -n systemctl poweroff|reboot`
>
> **关于 `"9"`（拍照）——它是"四跳、有回应"的**：
> 单片机 →（本协议 `"9"`）→ 树莓派 →（`openmv_serial` 写控制字节 `'P'`）→ **OpenMV** 存盘
> →（回写一行 `"P,<ok>"`）→ 树莓派 →（**本协议 COORD TAG=0x06**，见 §6g）→ 单片机
> → OLED 闪一句「拍照 成功!/失败!」（1s）。
> **单片机没有直达 OpenMV 的路**：OpenMV 只有一路串口（`UART(3)`），被树莓派占着
> （`config.py::OPENMV_PORT`，一个 USB 转串口适配器）。
> ✅ **有回应**：OpenMV 存盘成功回 `"P,1"`、失败回 `"P,0"`；树莓派解析后作为
> TAG=0x06 帧回传单片机（见 §6g）。
> ⚠️ **超时兜底（这条很重要）**：`config.PHOTO_ACK_TIMEOUT_S`（默认 3s）内没等到回执，
> 树莓派就回一条「失败」—— 否则相机没上电 / 跑的是没实现 `'P'` 的旧固件时，
> 单片机那边是**一片沉默**，「按了没反应」根本查不出来。
> ⚠️ **照片是干净原图**：OpenMV 在全部图像处理之后、绘制调试标记之前存 —— 带镜头畸变校正、
> 不带黄十字/绿拟合线。目录是相机盘根上的 `photos/`（**必须是 ASCII**：那台固件的 FatFS 是
> CP437 模式，中文目录名会变成乱码孪生目录）。
> ⚠️⚠️ **保存的图片要重启相机之后 PC 上才看得见**（OpenMV 官方行为）——
> "拍完立刻刷新看不到"是正常的，别当成失败；**与"拍照成功"的判定无关**
> （判定看的是 §6g 那条回传帧，不是"盘上看得见"）。
> ⚠️ 拍照**不影响巡线**：OpenMV 那边只写文件，采样循环与 `'G'`/`'S'` 发送开关都归别人管，
> 所以拍照与巡线可以同时进行（不像 `"1"`/`"4"`/`"5"`/`"6"` 要先停巡线腾主摄）。
> （需一条免密 sudoers 规则），其次退回 `systemctl`（polkit 对后台服务通常拒绝）。
> 免密规则见 `handler.py` 里 `_system_priv_cmd` 上方的说明。

> 发送方式：`TYPE_CMD` 帧，DATA = 命令码的 ASCII 字节（如 `"1"` = `0x31`）。

## 6a. 二维码结果回传（命令 `"1"` / `"D"` / `"E"` / `"F"` 完成后，Pi → 单片机）

> **本帧格式由四条命令共用** —— 它们走同一条解码链，只有「相机」与「解码算法」两个轴不同
> （`"1"`=副摄+微信 / `"D"`=主摄+微信 / `"E"`=副摄+自研 / `"F"`=主摄+自研）。
> 所以单片机侧**同一套 `ucRpiWaitQrResult` / `iGetQrCode()` 同时服务四条命令**，
> 用哪台相机、哪个算法对下游完全透明。加「只换相机/只换算法」的命令时照此办理，
> **别新增帧型**。
> （副摄 = `/dev/camera_Qr`；主摄 = `/dev/camera_main`。）

Pi 完成二维码识别后，以 `TYPE_COORD` 帧回传结果（9 字节 ASCII，补零，复用 `serial_comm.send`）：

| 结果 | DATA 内容 | 单片机解析 |
|------|-----------|------------|
| 成功 | `"QR"` + 三位数字（如 `"QR211"`，不足 9B 补 `0x00`） | `iGetQrCode()` = 211 |
| 失败/超时 | `"QRF"`（补零） | 视为失败，`ucRpiWaitQrResult` 返回 0 |

> 单片机 `ucRpiWaitQrResult(timeout_ms)` 阻塞等待该帧：前 2 字节 == `"QR"` 才认，
> 第 3 字节 `'F'` = 失败、三位数字 = 结果；期间其他 COORD 帧（坐标等）被忽略继续等。
> 串口断开导致结果帧丢失时，单片机超时后可在脚本里重发 `"1"` 重试。

## 6b. 巡线数据流（OpenMV → Pi → 单片机）

OpenMV 是**独立传感器**（上电即持续发数据，不等指令），通过 ATK-USB-UART 接 Pi：
`/dev/ttyUSB_OpenMV` @115200，文本帧 `L,<offset>,<angle>,<valid>\r\n`
（offset ∈ [-100,100] 归一化偏差；angle 单位 0.1°；valid 0/1）。

Pi 收到命令 `"2"` 后进入转发模式（默认 30Hz，`config.LINE_SEND_HZ` 可调）：
归一化误差 → PID（参数在 Pi 端 config.py，Web 可在线调）→ 以下列帧发单片机。
命令 `"3"`、超时保护（60s）或串口断开时停止。

## 6c. 人质形状识别结果回传（命令 `"4"` 完成后，Pi → 单片机）

Pi 用主摄像头（`/dev/camera_main`）跑 YOLO（`gks_yolo_model/best.onnx`，cv2.dnn 推理）识别
圆柱 / 圆锥 / 腰鼓 三种人质形状，凑满 `HOSTAGE_MIN_TARGETS`（默认 3）个目标即成功，
以 `TYPE_COORD` 二进制帧回传（DATA 首字节 `0x02` 作子命令标记，与巡线帧 `0x01` 同约定）：

```
DATA = [TAG=0x02] [status u8] [count u8] + count × [shape u8] [cx u16 LE] [cy u16 LE]
LEN  = 3 + 5×count（失败帧 3B，3 目标 18B）
```

| 字段 | 类型 | 说明 |
|------|------|------|
| TAG  | u8 = `0x02` | 人质识别帧标记（< 0x20，与 ASCII 坐标帧天然不冲突） |
| status | u8 | 1 = 成功；0 = 失败（摄像头打开失败 / 超时未凑满目标） |
| count | u8 | 目标数（成功 1~3；失败恒 0） |
| shape | u8 | 形状码：1 = 圆柱 cylinder，2 = 圆锥 cone，3 = 腰鼓 drum(pellet) |
| cx / cy | u16 LE | 目标中心像素坐标（1920×1080 画面，按中心 x 升序 = 图像从左到右） |

> **单片机端判别规则**：`TYPE_COORD 且 DATA[0] == 0x02 → 人质帧`（在巡线帧判别之后、
> 通用 9B ASCII 坐标帧之前分支）。`ucRpiWaitHostageResult(timeout_ms)` 阻塞等待：
> status=1 返回 1（结果经 `vGetHostageResult()` 快照读取），status=0 / 超时返回 0。
> 类别映射按**类名**（`classes.names`）而非类 ID —— 类 ID 随训练顺序变化
> （`config.HOSTAGE_NAME2SHAPE`：cylinder→1 / cone→2 / pellet→3）。
> 与命令 `"1"`（二维码）同理，Pi 收到 `"4"` 时先停巡线转发，防 COORD 帧交错。
> 同步阻塞期间 Pi 不发心跳（默认超时 6s < 单片机断链阈值 8s，不会误判断开）。

## 6d. 色球顺序识别结果回传（命令 `"5"` 完成后，Pi → 单片机）

Pi 用主摄像头（`/dev/camera_main`）跑 HSV 阈值 + 连通域（**不用 YOLO**：颜色是像素属性，
HSV+findContours 在 Pi 上比 YOLOv8n 快一个数量级），识别场地上一行三球（红/绿/蓝各一个，
顺序抽签决定）的颜色顺序，凑满 `COLOR_MIN_TARGETS`（默认 3）即成功，
以 `TYPE_COORD` 二进制帧回传（DATA 首字节 `0x03` 作子命令标记，与巡线帧 `0x01` 同约定）：

```
DATA = [TAG=0x03] [status u8] [count u8] + count × [color u8] [cx u16 LE] [cy u16 LE]
                       + （2026-09 扩展，仅成功帧）[yaw i16 LE 0.01°] [fit_ok u8]
LEN  = 3 + 5×count（失败帧 3B，3 目标 18B；含扩展 21B）
```

| 字段 | 类型 | 说明 |
|------|------|------|
| TAG  | u8 = `0x03` | 色球识别帧标记（< 0x20，与 ASCII 坐标帧天然不冲突） |
| status | u8 | 1 = 成功；0 = 失败（摄像头打开失败 / 超时未凑满三色） |
| count | u8 | 目标数（成功 1~3；失败恒 0） |
| color | u8 | 颜色码：1 = 红，2 = 绿，3 = 蓝（对齐单片机 `color_t`，也等于二维码第一位） |
| cx / cy | u16 LE | 球中心像素坐标（**1920×1080 全分辨率**，按 cx 升序 = 图像从左到右） |
| yaw | i16 LE | 三球质心 fitLine 直线的**图像**倾角，单位 0.01°（左高右低 = 左球 cy 小于右球 cy 为正）。⚠️ 是图像角不是车体角：车原地转 θ 图像只斜约 (h/Z)·θ（标定比例，预期 ~0.3），单片机端换算后再用。旧版失败帧 / 老固件不携带 → 单片机按 LEN<21 兜底为 0 |
| fit_ok | u8 | 1 = 三点共线残差合格（各点到拟合直线最大距离 < `config.COLOR_FIT_MAX_DIST_PX`）；0 = 残差超限，某球识别可疑，建议重发 `"5"`。旧版帧恒按 1 兜底 |

示例（红 400,500 / 绿 800,505 / 蓝 1200,510，连线角 +0.35° 共线合格）：

```
03 01 03  01 90 01 F4 01  02 20 03 F9 01  03 B0 04 FE 01  23 00 01
└TAG └st └cnt └红 └cx=400 └cy=500 └绿 └cx=800 └cy=505 └蓝 └cx=1200 └cy=510 └yaw=+35(0.35°) └fit_ok
```

> **⚠️ 坐标是 1920×1080 全分辨率**：Pi 为提速会在内部降采样（`config.COLOR_PROC_SCALE`），
> 但**回传前已还原回全分辨率**。单片机端 `COLOR_ALIGN_CX` / `COLOR_PX_TO_MM_X` 全按
> 全分辨率标定 —— 改动 `COLOR_PROC_SCALE` 不影响协议，但改**摄像头分辨率**要双端同改。
>
> **⚠️ Pi 端多帧投票要求小车静止**（同色 cx 跨帧散布 > `COLOR_MAX_SPREAD_PX` 即作废该色），
> 故单片机**必须在底盘停稳后**才发 `"5"`。
>
> **单片机端判别规则**：`TYPE_COORD 且 DATA[0] == 0x03 → 色球帧`（在巡线帧、人质帧判别
> 之后，通用 9B ASCII 坐标帧**之前**分支；否则 18 字节整帧会被当 9 字节 last packet 吞掉）。
> `ucRpiWaitColorResult(timeout_ms)` 阻塞等待：status=1 返回 1（结果经 `vGetColorResult()`
> 快照读取，index 0/1/2 = 左/中/右），status=0 / 超时返回 0。
> 与命令 `"1"`/`"4"` 同理，Pi 收到 `"5"` 时先停巡线转发，防 COORD 帧交错。
> 同步阻塞期间 Pi 不发心跳（默认超时 5s < 单片机断链阈值 8s，不会误判断开）。

## 6e. 靶标识别 + 靶心定位结果回传（命令 `"6"` 完成后，Pi → 单片机）

三色靶盘（红/绿/蓝外环）识别 + **每颗靶的圆心定位**：

```
DATA = [TAG=0x04][status u8][count u8]
       + count × [color u8][cx u16 LE][cy u16 LE][r u16 LE]
LEN  = 3 + 7×count            （count ≤ 3 → 最长 24B，远小于 FRAME_MAX_LEN=64）
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `TAG` | u8 | 恒为 `0x04`（< 0x20，与 ASCII 首字节 ≥ `'0'` 天然不冲突） |
| `status` | u8 | `1` = 成功；`0` = 失败/超时（此时 `count = 0`） |
| `count` | u8 | 靶数（≤ 3，与单片机端 `TARGET_MAX_CNT` 对齐，双端同步改） |
| `color` | u8 | `1` 红 / `2` 绿 / `3` 蓝（对齐 `color_t`，也等于二维码第一位） |
| `cx` / `cy` | u16 LE | **靶心**像素坐标，**全分辨率 1920×1080** |
| `r` | u16 LE | 靶盘**外圆等效半径**[px]（见下） |

> **坐标空间**：与文档其它坐标帧同约定 —— **全分辨率 1920×1080 像素**。Pi 侧若降采样
> 提速，回传前必须还原（`_target.py` 已按 scale 还原）。
>
> **`r` 的语义（重要）**：是**外圆（Ø100）等效半径**。现场样件的色环外缘是手工贴的、
> 不是圆，所以圆心其实取自**内边界**（色环↔白心的 Ø55 圆）的拟合，`r` 已按
> Ø55/Ø100 折算回来。这样 `r` 与固件那条视差补偿
> `offset_px = h_mm · r_px / 50`（见固件 `app_config.h` 的 `TARGET_LASER_H_MM` 一族）
> 是**同一个口径**，可直接用；顺带也是一个粗略的距离标尺。
>
> **回传三颗而不是一颗**：哪一颗是目标由**二维码第二位**决定，而二维码结果是单片机
> 在解 —— Pi 侧不掺和任务语义（与 §6d 色球完全一致）。单片机按目标色在 `count` 颗里挑。
>
> **⚠️ Pi 端多帧投票要求小车/机械臂静止**（同色 cx 跨帧散布 > `TARGET_MAX_SPREAD_PX`
> 即作废该色），故单片机**必须在机位停稳后**才发 `"6"`。
>
> **单片机端判别规则**：`TYPE_COORD 且 DATA[0] == 0x04 → 靶标帧`（在巡线帧、人质帧、
> 色球帧判别**之后**，通用 9B ASCII 坐标帧**之前**分支；否则 24 字节整帧会被当 9 字节
> last packet 吞掉）。等待函数 `ucRpiWaitTargetResult(timeout_ms)` 阻塞等待：
> status=1 返回 1（结果经 getter 快照读取，index 0/1/2 = 图像从左到右），
> status=0 / 超时返回 0。
> 与命令 `"1"`/`"4"`/`"5"` 同理，Pi 收到 `"6"` 时先停巡线转发，防 COORD 帧交错。
> 同步阻塞期间 Pi 不发心跳（默认超时 `TARGET_TIMEOUT`=6s < 单片机断链阈值 8s，不会误判断开）。
>
> **算法与判据**（详见 Pi 端 `tasks/_target.py` 顶部注释，离线评估在 GongKeCompetition
> 仓库 `tools/target_offline/`，61 个用例中位 0.33mm / 最大 0.63mm，判据是 10 环半径 7.5mm）：
> ① **跨色尺寸一致性**选靶 —— 治「同色大块」（现场背景整面蓝柜子）；必须有 ≥2 颗靶
> 同时在画面里才起作用；② **内边界优先、外边界兜底** —— 不依赖同伴，单靶也成立；
> ③ **ROI 裁切**（可关）—— 瞄准闭环会把靶心拉到画面中心附近，窗口外的干扰不用看。

**示例**（status=1，三颗靶，红在左/绿在中/蓝在右）：

```
04 01 03  01 84 01 1B 02 39 00  02 3E 03 1C 02 3A 00  03 FA 05 1B 02 39 00
TAG st n  R  cx=388 cy=539 r=57  G  cx=830 cy=540 r=58  B  cx=1530 cy=539 r=57
```

失败帧（让单片机立刻解锁，不空烧等待超时）：

```
04 00 00      # TAG=0x04, status=0, count=0
```

## 6f. 靶标流帧（命令 `"7"` 起流 / `"8"` 停流期间，Pi → 单片机 ~20Hz）

命令 `"6"` 的**流式版本**：起流后在小跟踪窗内高频回传靶心，给单片机的瞄准闭环当测量源。

```
DATA = [TAG=0x05][status u8][count u8]
       + count × [color u8][cx u16 LE][cy u16 LE][r u16 LE]
LEN  = 3 + 7×count            （count ≤ 3 → 最长 24B）
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `TAG` | u8 | 恒为 `0x05`（< 0x20，与 ASCII 首字节 ≥ `'0'` 天然不冲突） |
| `status` | u8 | 流模式下恒为 `1`（检测正常运行）。**预留，单片机不消费** |
| `count` | u8 | 本帧在跟踪窗内找到的靶数。**`0` = "流还活着但没找到"**，不是失败帧 |
| `color` | u8 | `1` 红 / `2` 绿 / `3` 蓝；**`0xFF` = 无色模式**（颜色未知，见下） |
| `cx` / `cy` | u16 LE | 靶心像素坐标，**全分辨率 1920×1080**（与 §6e 同口径，`tg_*` 标定直接复用） |
| `r` | u16 LE | 外圆等效半径[px]（口径同 §6e） |

按 `cx` 升序排列（与 §6e 同约定）。

> **与 §6e 逐字节同布局，只是"连续流"**：所以单片机端解析代码整段与 `0x04` 分支同构，
> 坐标/半径语义一致、固件侧无任何换算。区别只在落点不同 —— `0x04` 进"结果 + ready
> 一次性信号"的快照，`0x05` 进**独立**的"最新一帧 + 帧计数"快照
> （`vSetAimFrame` / `ulGetAimFrameCount`）。**两个快照刻意分开**：合成一个的话，
> 闭环停流时留下的最后一帧会污染随后的终验（终验会拿一帧 ~20Hz 的旧测量当权威结果）。
>
> **`count = 0` 的语义（重要）**：**帧计数照常推进**。单片机的判据是
> 「帧计数还在不在涨」（新鲜度），不是「有没有结果」——
> `count=0` = 流活着、只是这一帧没找到靶（窗跟丢/掩膜失锁）；
> 帧计数停涨 = 流停了 / Pi 掉线 / 链路聋了。两者在单片机端的处置完全不同
> （前者冻结不动舵机等它回来，后者同样冻结，但排障方向一个是"视觉"、一个是"链路"）。
>
> **`color = 0xFF`（无色模式）**：Pi 侧 `TARGET_STREAM_USE_COLOR=0` 时，检测只按
> S/V 掩膜、不带色相判据，于是颜色未知。单片机端的退化规则是：先找
> `color == 二维码第二位` 的靶；没有但存在 `0xFF` 的靶 → 取**离瞄准点
> `(tg_center_x, tg_center_y)` 最近**的一颗（闭环本来就在把靶往瞄准点拉，最近的
> 那一颗就是正在跟的那颗）。⚠️ **默认带色**（`USE_COLOR=1`）：另外两颗靶是等大的圆环，
> 无色时唯一区分手段是距离门，一次大修正跳到邻靶就锁错，而且闭环还会持续往错的那颗上拉。
>
> **流帧不要求机位静止** —— 恰恰相反：单片机闭环期间舵机一直在动，跟踪窗**必须**
> 跟着目标走（"上一帧位置 ± 边距"的并集 bbox，丢失时逐帧扩张退化成全画面重搜）。
> 这是与 §6e 最大的差别（那里多帧投票要求同一机位）。
>
> **互斥规则**：流帧与结果帧同为 `TYPE_COORD`，所以
> ① Pi 收到 `"1"/"4"/"5"/"6"` 与 `"end"`/`"r"` 时**先停靶标流**（防帧交错 + 主摄互斥）；
> ② `"2"`（巡线起流）先停靶标流，`"7"` 先停巡线 —— 两条流独占主摄与 COORD 通道。
>
> **单片机端判别规则**：`TYPE_COORD 且 DATA[0] == 0x05`（在巡线/人质/色球/**靶标 0x04**
> 帧之后，通用 9B ASCII 坐标帧**之前**分支；否则 17/24B 整帧会被当 9 字节 last packet 吞掉）。
> 另：诊断行 `[STM-DBG] COORD tag=.. len=..` **排除 0x05** —— 它是 20Hz 的，
> 而那条调试串走的是忙等发送，不排除会把链路和 50ms 的 PID 任务一起拖垮。
>
> **起流失败的处置**：相机打不开时 Pi **立刻回一帧 `count=0`** 再退出，而不是干脆不发 ——
> 单片机判"流是否活着"看的是帧计数，一帧都不发它要空等到超时才知道。
>
> **参数**（`config.py`，Web「设置参数」在线可调）：`TARGET_STREAM_HZ`（发送频率上限）、
> `TARGET_STREAM_INIT_FRAMES`（起流锁定采帧数）、`TARGET_STREAM_MARGIN_PX`（跟踪窗边距）、
> `TARGET_STREAM_R_TOL`（半径门）、`TARGET_STREAM_USE_COLOR`（颜色跟踪开关）、
> `TARGET_STREAM_MAX_S`（安全时长上限，防 `"8"` 丢失后一直占着相机）、
> `TARGET_STREAM_LOG_HZ`（状态日志限流）。阈值/色相族/尺寸判据复用 §6e 那一套
> （`TARGET_SAT_MIN`/`TARGET_MIN_AREA`/`COLOR_HUE_FAMILIES`…），**不另开一套**。

**示例**（count=2，绿靶 + 蓝靶；可见与 §6e 的示例是同一个布局）：

```
05 01 02  02 3E 03 1C 02 3A 00  03 FA 05 1B 02 39 00
TAG st n  G  cx=830 cy=540 r=58  B  cx=1530 cy=539 r=57
```

空窗帧（丢目标，**流仍活着**）：

```
05 01 00      # TAG=0x05, status=1, count=0
```

## 7. 示例字节流

单片机 → Pi 发「二维码识别」命令：

```
0xAA 0x01 0x01 0x31 <CRC8> 0x55
 └SOF  └TYPE └LEN └'1'   └CRC  └EOF
```

Pi → 单片机回「二维码结果」：`TYPE_COORD`，DATA = `X(4) Y(4) COLOR(1)`（9 字节，预留布局）。

Pi → 单片机发「巡线帧」（TYPE_COORD，DATA 首字节 `0x01` 作子命令标记，8 字节）：

```
DATA = [0x01] [err i16 LE ×10000] [steer i16 LE ×1000] [angle i16 LE 0.1°] [valid u8]
```

| 字段 | 类型 | 说明 |
|------|------|------|
| TAG  | u8 = `0x01` | 巡线帧标记（< 0x20，与 ASCII 坐标帧天然不冲突） |
| err  | i16 / 10000 | 归一化偏差 [-1, 1] |
| steer | i16 / 1000 | PID 输出控制量 |
| angle | i16 | 航向角（0.1° 单位，OpenMV 原始值） |
| valid | u8 | 0 = 丢线（err/steer 无意义，单片机自行保持/停车） |

> **单片机端判别规则**：`TYPE_COORD 且 DATA[0] == 0x01 → 巡线帧`，否则按 ASCII 坐标帧解析。

## 6g. 拍照结果帧（命令 `"9"` 的回执，Pi → 单片机）

```
[TAG u8 = 0x06][ok u8]        共 2 字节
```

- `ok`: `1` = OpenMV 已存盘；`0` = 失败（含"等回执超时"）
- **帧长 2 < 9**，所以天然落不进"通用 LEN>=9 进 last packet"那条分支；
  单片机端仍按规矩把该分支判在通用分支**之前**。
- 单片机侧：`app_rpi.h::RPI_PHOTO_TAG` / `RPI_PHOTO_LEN`，
  收帧后只置两个 Beam 量（`photo_ok` + `photo_done_tick`），由 OLED 任务闪一句 1s ——
  **不做 ready/一次性信号**（它不是同步点，做成信号会被别的读者偷走）。
- 树莓派侧只发这一条；**收不到它单片机不会卡住**（拍照不是阻塞步骤）。

**这条帧为什么存在**：命令 `"9"` 本身到树莓派就返回了，真正的"拍没拍到"只有 OpenMV 知道。
没有回程的话，单片机按了「拍照」只能短鸣一声、不知道成没成（现场无法排查）。

## 6h. 矩形地板识别结果回传（命令 `"A"` 完成后，Pi → 单片机）

色球区地上那圈**黑胶带**围出来的矩形（板面可能白也可能黄，所以只看黑胶带、不看板面颜色）
→ 回传**板心**像素坐标。单片机拿它当**不依赖色球**的横向基准：缺球（且缺球推断也不成立）时
作为备选对位方案（见 `Application/app_rpi.c::ucRpiAlignChain` 的"矩形板心"方案）。

```
DATA = [TAG=0x07] [status u8] [cx u16 LE] [cy u16 LE] [flags u8] [spread u8] [保留 u16]
LEN  = 10（成功、失败都一样长）
```

| 字段 | 类型 | 说明 |
|------|------|------|
| TAG | u8 = `0x07` | 矩形地板帧标记（< 0x20，与 ASCII 坐标帧天然不冲突） |
| status | u8 | 1 = 成功；0 = 失败（板子没识别出来 / 超时） |
| cx / cy | u16 LE | **板心**像素坐标（1920×1080 全分辨率）。板心 = 四边形**对角线交点** —— 世界矩形中心的射影，透视下 ≠ 四角均值 |
| flags | u8 | bit0 = 三边估（只有三条边时按长宽比仿射补出，误差 ~15px 量级）；bit1~3 = 用了几条边；bit4 = 走主路径（量胶带**内沿**），0 = 回退路径（量胶带**中线**） |
| spread | u8 | 中心跨帧散布 [px]（封顶 255；只做遥测/排障，单片机不据此判失败） |
| 保留 | u16 | 恒 0，以后加字段用 |

示例（板心 (932,473)、四边精确、主路径、散布 2px）：

```
07 01 A4 03 D9 01 18 02 00 00
└TAG └st └cx=932 └cy=473 └fl=0x18(边数4<<1=0x08 | 内沿0x10  | bit0三边估=0) └散布=2 └保留
```

> **⚠️ 失败帧也一定回**（status=0 + 其余全 0）：单片机靠它立刻解锁，不然要空烧等满整个超时。
> Pi 侧任务内部有自己的时限（`config.RECT_TIMEOUT`）与采帧上限，所以**这条帧一定会来**，
> 单片机的超时只是兜底。
>
> **⚠️ 坐标是全分辨率**：当前实现全程 1920×1080（无降采样）。若日后为提速降采样，
> **回传前必须还原**（同色球帧那条纪律），否则单片机侧标定全部成比例失真且不报错。
>
> **⚠️ 单次耗时约 2~3s**（9 帧 × ~180ms + 打开摄像头），识别期间小车必须静止。
>
> **⚠️ 它用主摄** → Pi 收到 `"A"` 时**先停巡线转发与靶标流**（与 `"5"` 同族，防 COORD 帧交错）。
>
> **两条测量路径**（flags bit4）：`enclosed`（量胶带**内沿**，四边齐全时）与 `lines`
> （量胶带**中线**，缺一条边/板子伸出画面时）。两者在本机位差 ~15px ≈ 5mm ——
> **标定 `RECT_ALIGN_CX/CY` 时记一下当时页面标的是哪一路**，别跨着用；单片机的中心量
> 会在标定时把这点差吸收掉。
>
> **单片机端判别规则**：`TYPE_COORD 且 DATA[0] == 0x07 → 矩形帧`（**必须排在通用
> `LEN >= 9` 分支之前**；长度特意取 10 而**不是 9**，避免与「9 字节 last packet」混淆）。
> `ucRpiWaitRectResult(timeout_ms)` 阻塞等待：status=1 返回 1（结果经 `vGetRectResult()` 读），
> status=0 / 超时返回 0。

## 6i. 看路结果回传（命令 `"G"` 完成后，Pi → 单片机）

主摄看**地面**：地面上的**黄色区**（比赛是黄胶带；练习地图上是那块米黄篷布）**一般落在
画面右上角**，车越往前开它越大、**左边缘越往左跑** —— 于是「黄色区左边缘的 x」本身就是
一把**测距尺**。Pi 把 **Δx = 黄色区左边缘的 x** 量好回传，单片机拿它修一次车体纵向。

同一块色块的**另一个轴**也量：**Δy = 黄色区下边缘的 y**，单片机拿它修一次**车体横向**
（本车相机相对车体转了 90° ⇒ 图像 y 那条轴就是车体横向）。用**下**边缘不用上边缘：
黄区固定在画面右上角，**上**边缘永远被画面顶边裁掉（实测现场帧 bbox top 全是 0、
flags 全是 `0x05` —— 那个 bit2 正是上边缘触发的），而下边缘全在窗内（实测 278~576px）
且随机位变化。

> **Δx / Δy 都由 Pi 量好、直接放进帧里**（单位都是 0.1px），单片机**不再自己算距离**。
> 「原点」= 画面左边 x=0（Δx）/ 画面上边 y=0（Δy）；换别的参考只差一个常数，
> 会被「理想值」吸收掉。
>
> **判据是 R−B（色度差），不是 HSV 的 H/S/V**：补光灯把画面中心打到过曝时会带着
> 亮度/饱和度类阈值跑，而 R−B 是色度关系。实测本机位：米黄区 **+7** / 灰地 −11 /
> 黑线 −18 / 车身 −32 —— 18 级余量，**车身自己就被排除**。
>
> **物理**：车往前开 → 黄区变大 → 左边缘 x **变小** ⇒ Δx 是一把"越近越小"的尺。
> 所以单片机那侧的方向常常要填 −1（见 `app_config.h` 的 `ROAD_DX_DIR`）。

```
DATA = [TAG=0x08] [status u8] [dx i16 LE /10] [ex i16 LE] [ey i16 LE] [flags u8] [spread u8] [dy u16 LE /10]
LEN  = 12（成功、失败都一样长）
```

| 字段 | 类型 | 说明 |
|------|------|------|
| TAG | u8 = `0x08` | 看路帧标记（< 0x20，与 ASCII 坐标帧天然不冲突） |
| status | u8 | 1 = 成功（dx 有效）；0 = 失败（没找到黄区 / 超时，其余字节全 0） |
| dx | **i16** LE | **Δx = 黄色区左边缘的 x**，单位 **0.1px**（i16 → ±3276.7px）→ 车体**纵向** |
| ex / ey | **i16** LE | 左边缘那一点的全分辨率像素坐标（**只做遥测/画图**，单片机不参与运算） |
| flags | u8 | bit0 = 左边缘有效；bit1 = 黄区贴画面**左边** → Δx 可能饱和不可信；bit2 = 黄区贴画面上/下边（只提示）；bit3 = 面积刚够门限（勉强）；bit4 = **Δy 有效**（下边缘没被裁） |
| spread | u8 | Δx 跨帧散布 [px]（封顶 255；只做遥测，单片机不据此判失败） |
| dy | **u16** LE | **Δy = 黄色区下边缘的 y**，单位 **0.1px**（u16 → 0~6553.5px）→ 车体**横向**。⚠️ **2026-09-30 之前这里是「保留 u16」恒 0** |

> **⚠️ dx/ex/ey 都是 i16、不是 u16**（本协议里**只有这条帧**的坐标是有符号的，别照别的帧
> 改回去）：方向对调后误差可以为负，且黄区贴到画面左边时 x 可以到 0 附近 —— u16 会被
> 钳成 0 而且**不报错**（车会朝错的方向走）。**dy 例外**：下边缘的 y 不可能为负，就是 u16。
>
> **⚠️ CLIPX 只看左边**：黄区**右侧**跑出画面是常态（它本来就铺到画面右边），
> 不该报"不可信"。
>
> **⚠️⚠️ bit4 是新旧 Pi 的分水岭**：帧尾那个字段以前是**恒 0 的保留位**，光看值分不出
> 「这版 Pi 没量这个量」和「下边缘真的在 y=0」（后者与"黄区总在右上角"矛盾）。所以
> **填了 dy 就必须同时置 bit4**；单片机只有看到 bit4 才会用 Δy，否则整段横向修正跳过
> （只打一行 `ROAD fixy: skip (no y edge)`，纵向照常）。这保证两个仓库谁先烧都不炸。
>
> **⚠️ bit2 不能当 Δy 的失效门**：它是**上**边缘被顶边裁掉触发的（现场帧常置），
> 与下边缘无关；拿它当门 = 横向永远不生效。
>
> **⚠️ 长度刻意仍是 12**（dy 占原来那个保留字段）：改成 14 的话，按 `>= 14` 判的新固件
> 会把旧 Pi 发来的 12B 帧当「9 字节 last packet」吞掉（静默失效）。

示例（Δx = 724.0px、左边缘在 (724,14)、边缘有效、贴上下边、散布 2px、Δy = 576.0px）：

```
08 01 48 1C D4 02 0E 00 15 02 80 16
└TAG └st └dx=7240(0.1px) └ex=724 └ey=14 └fl=0x15 └sp=2 └dy=5760(0.1px)
```

> **⚠️ 失败帧也一定回**（status=0 + 其余全 0）：单片机靠它立刻解锁，不然要空烧等满整个超时。
> Pi 侧任务内部有自己的时限（`config.ROAD_TIMEOUT`）与采帧上限，所以**这条帧一定会来**，
> 单片机的超时只是兜底。
>
> **⚠️ 单次耗时约 1~2s**（最多 9 帧 + 打开摄像头），识别期间小车**必须静止**
> （多帧投票要求同一机位）。
>
> **⚠️ 它用主摄** → Pi 收到 `"G"` 时**先停巡线转发与靶标流**（与 `"A"` 同族，
> 防 COORD 帧交错、也防流线程占着设备）。
>
> **⚠️ 单片机端判别规则**：`TYPE_COORD 且 DATA[0] == 0x08 → 看路帧`（**必须排在通用
> `LEN >= 9` 分支之前**；长度特意取 12 而**不是 9**，避免与「9 字节 last packet」混淆）。
> `ucRpiWaitRoadResult(timeout_ms)` 阻塞等待：status=1 返回 1（结果经 `vGetRoadResult()` 读），
> status=0 / 超时返回 0。消费它的积木是 `STEP_ROAD_ALIGN_WAIT` → `ucRpiRoadAlign()`。
>
> **历史**：本帧的第一版布局是 `[vx][vy][tx][ty]`（两条拟合直线的交点 + 切点，由单片机按
> 两点距离算 Δ）。那一版在合成本例上正确、但真实机位上取不出边界，已整个换成现在这种
> 「整块黄区 + 左边缘」——**别把 `[vx][vy][tx][ty]` 捡回来**。复盘见 Pi 仓库
> `tasks/_road.py.bak-curve` 与 `Desktop/road_offline/README.md`。
