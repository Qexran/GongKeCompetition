## OLED 菜单（5 页：状态 / 二维码 / 任务 / 巡线 / 射靶测试）—— `app_oled.c`，2026-09 加

> ⚠️ 第 5 页「射靶测试」是 2026-10-09 加的，**细节单独成节**（见上面「射靶测试（OLED 保持式平移射靶）」）——
> 下面那张 4 页表是加它之前的形态。

> ⚠️ **2026-10 起菜单已经是数据表驱动的**: **内容**在 `Application/app_oled_menu.c`（由 Web 控制台「OLED」Tab 生成/回写），**行为**在 `app_oled.c`。本节的「4 页 / 各行文案」是**当时**的形态，现在页数/文案/顺序/启停都能在控制台里改。
>
> **核心分工: 表是「结构」，`switch` 是「动词」。** 表项只有 `{标签, 动作码, 启用, 参数, 子表指针}`; 取值/步进/量程/离散档位/副作用/前置条件全在 `app_oled.c::ucOledRunAct` / `vOledTuneStep` 的 switch 里。
>
> **`app_oled.c` 里的通用引擎**（`「菜单页 —— 通用引擎」`那一段）:
> - `pstOledPageList/ucOledPageKind` 按**页的类型**分派（`vOledTask` 的 switch 键是 kind, **不是页下标**）。前两条恒为状态页/二维码页（**跨文件契约**, 控制台保证）。
> - `ucOledVisibleCount`（启用项数, 上限 `OLED_MAX_ITEMS`=16）/ `ucOledEntryCount`（条目数 = 可见项 + 子菜单那条「返回」）/ `ucOledEntryIndex`（条目序号 → 表下标, ⚠️ **越界回 `0xFF`**, 调用方必须判）/ `ucOledCursorEntry`（光标 → 条目序号）把「条目」折算成屏上窗口行号。
> - **滚动窗口**: `s_ucTop`（窗口顶行的**条目序号**, 只是个缓存）+ `vOledWindowSync`（每拍画之前**幂等**重算: 先钳 `top ≤ N-4`, 再**最小幅度**把光标带进窗 —— 漏改 `s_ucTop` 会在 50ms 内自愈, 所以翻页/进子菜单那几处显式复位只是"意图清楚"）。`vOledCursorStep(pstList, bSub, ±1)` **顶层与子菜单共用**（保留回绕, 有界循环）。`vOledScrollbarDraw` 画右侧竖直条, **必须最后画**（前面几步都会写到 x≥120）。
> - `vOledHighlightRow(y, w)` 有滚动条时只反色到 `OLED_LABEL_W`(120), 否则反色把条子那 8 列刷白 → 滑块"白底白块"看不见。
> - **换行动画**（2026-10 加）: 上下选择时**选中那一行的文字从右侧滑入**（`s_ucAnimOfs` 8px → 0, 每拍 4px ≈ 100ms; `vOledAnimStart` 起跳 / `vOledAnimTick` 收回）。⚠️ **刻意不做"整屏滚动滑动"**: 驱动画不了 y<0 的内容（`vOledShowImage` 在 `Y>63` return）, 整屏滑会在顶边留细黑边 —— 只动选中行、只动文字就没这个问题。⚠️ 偏移上限 8px 是**硬约束**: 标签预算 120px, 120+8=128 正好一行, 再大就会在动画头 1~2 帧把长标签从尾部截掉。画行走 `vOledDrawRowX`/`vOledDrawRowfX`（带 x 偏移的变体, 偏移 0 = 与加动画之前逐字节一致）。开关 = 蓝牙「OLED」组 `oled_menu_anim`（上电初值 = `app_config.h` 的 `OLED_MENU_ANIM_EN`, 「调参」Tab 可改要重编译; 关掉即无动画）。
> - `ucOledRunAct` 是唯一的动作分派入口, 返回 `OLED_RES_STAY / ENTER_SUB / ENTER_CONFIRM`（**把散落的 `s_ucMode` 赋值收成一处**）。
> - ⚠️ **页数是动态的**: 翻页判据用 `g_ucOledPageNum`（**先判非零再做减法**, 无符号下溢会把第 1 页判成还能右翻）; `vSetOledMenuBusy` 的判据是 **kind != STATUS**（不是「页下标 != 0」—— 页序一变就会改到比赛路线里等 MAIN 的步骤）。
> - `vOledMenuDraw` **四行逐个处理: 要么画、要么清**（窗口一挪, 上一帧的内容靠这一帧的清行带走）—— 帧缓冲是持久的（`vOledClear` 只在初始化时调）, 不清就会留着上一帧/上一屏的内容, 看着像"没藏掉"。⚠️ 别把每行 `vOledDrawRow*` 里那次**整行 128px 的清**改窄, 它是擦掉上一条滚动条的那只手。
> - ⚠️ **导航一律用有界查找**（`for k < count`）, **绝不用 `while`**: 全禁用时 while 会死循环, 而本任务优先级最低(1), 挂死 = 整屏停摆 + `vSetOledMenuBusy` 一直拉高。
> - ⚠️ **派发前再判一次 `ucEnabled`** —— 不然被藏起来的项还能被 MAIN 激活, 禁用就形同虚设。
> - ⚠️ **静态标签行走 `vOledRow`（不带 printf）**, 只有调参行才走 `vOledRowf` —— `acBuf[44]+vsnprintf` 是全工程最深的 printf 用法, 而本任务栈只有 **384 字**。
> - 「让出成功!」横幅挂在**含 `POST_HANDSHAKE` 的那张表**上（原来写死第 3 页; 页面可增删后按语义挂才站得住）, 且**必须画在菜单项之后**、清行**必须在窗口判断里面**（否则每拍无条件清第 4 行 → 刚画上的那项永远看不见）。
>
> **数据结构上的硬约束**（控制台保存时校验, 手改源文件能绕过 → 固件侧也有防御）:
> - 一页 / 一个子菜单最多 **32 个启用项**（2026-10-16 起; 屏一屏只画 4 行 —— 64px ÷ 16px, 第 5 项起驱动 `Y>63` 直接 return、**静默不画** —— 但放不下的靠 UP/DOWN **滚动**看, 右侧画竖直滚动条）; 子菜单的「返回」由固件补在**最后一条**、随列表滚动、**不占**这 32 个额度（它不进表, 所以"生成表漏了返回 → 卡死"不存在）。⚠️ 上限受滚动条几何约束: 条目最多 33（32+返回）, 滑块高 256/33 = 7px, 仍在 [5,64] 内。
> - ⚠️ 滚动条占最右 8px ⇒ **菜单标签宽度预算 128px → 120px**（`LABEL_PX = ROW_PX - SCROLLBAR_PX`; 现存最长标签 `巡线状态:待实现` 正好 120px, **零余量**）; 调参行仍 64px。控制台（`oled_menu.py::_check` + `app.js` 预览）与固件同源同义, 有测试钉着。
> - 子表用**直接符号引用**（`&s_stListTaskExec`）, 删除即 `undefined identifier` **编译错误**（有意的硬失败, 胜过重排后无声指向另一张表）; 书写顺序（子表要先于引用它的表）由控制台保存时**自动拓扑排序**, 排菜单的人不用管。
> - 动作码 / 调参量两个枚举在 `app_oled_menu.h` 的「生成块」里, **控制台只读不写**（加一个动作码必然要改 `app_oled.c` 的 switch, 不是能生成的）。
>
> 控制台那一侧的全部细节（含 `PYTHONUTF8=1`、自动补字的事务性、`check_coverage.py` 的扫描范围）见 **`tools/webconsole/CLAUDE.md` 的「OLED」Tab 一节**。

- **第 1 页第 4 行的优先级（2026-11 健康检查加）**：握手积木勾了健康检查时，结果显示为 `H:M√Q√Pi√MV√`（M 主摄 / Q 扫码副摄 / Pi CSI / MV OpenMV；失败 ×、检查中或未检查 ?）。**秒表首次启动前**一直显示体检结果；`vTimerCmd(TIMER_CMD_START)` 之后永久让位给 `Time:...`（停止/重置都不回来 —— 比赛结束要看最终用时）。没勾健康检查时这一行始终是秒表，与加功能前一致。实现见 `app_oled.c::vOledPageStatus` 与 `app_beam.c` 的 `vGetHealthResult/ucGetHealthBusy/ucTimerEverStarted`。

- ⚠️ **「是/否」确认框两页共用**（第 3 页关机 / 未设二维码），在 `vOledTask` 里**先于页分派**处理（`ucOledConfirmKeys` + `vOledConfirmDraw`），两页处理函数**都没有** `OLED_MODE_CONFIRM` 分支。用途存 `s_ucConfirmKind`（`OLED_CONFIRM_SHUTDOWN` / `_NO_QR` / `_NO_LINK` / `_NO_PI`），进框一律走 `vOledEnterConfirm()` —— **别直接 `s_ucMode = OLED_MODE_CONFIRM`**（会漏设 kind）。
- **「起跑」前置条件（2026-10 改）**：
  - **「执行任务」三项**：① 二维码得先设好（`OLED_QR_IS_SET` = 100~399，与 `c_ucCondQr`/排爆同口径，**不是**「!=-1」）→ 确认框 `还未设二维码!`，按「是」跳第 2 页；② **Pi 得在线**（2026-10 加）→ 单键提示框 `未连接到树莓派`/`[返回]`（`OLED_CONFIRM_NO_PI`）。任务预设第一步就是视觉步骤，Pi 不在 = 跑到那步失败不动（不响, 留痕），像「跑一半卡住」。
  - **「开始巡线测试」**：**只查 Pi 在线，不再查二维码**（2026-10 改）—— 巡线测试从头到尾不读二维码内容，原来的二维码门只会白拦台架上的「不设码直接测」。
  - **「射靶测试」**（第 5 页）：仍查二维码（目标色来自第二位）。
- **第 2 页功能小菜单（2026-10 加，`vOledPageQr`）**：① **自动下发QR** = 翻转 Pi 的「自动下发二维码」（`"QE,<0|1>"`，状态 `√/×` 取自 `ucRpiQrAutoState()` 的 QS 回执镜像，`?` = 未知/过期/离线；查询**按需限频**——进页且值未知且链路 OK 才发 `"QA"`，2s 一次）；② **上传二维码** = 把当前值写进 Pi 并启用（`"QU,<ddd>"`，Pi 端写 `web_auto_qr.json`，**下次上电 Pi 握手后自动推调试帧** —— 台架调好的码直接带去比赛；要求当前值 100~399 且链路 OK，否则拒绝（不响, 留痕））；③ **清空二维码** = 本端清回 -1/清人工标记 + `"QC"` 清 Pi 端。协议见 Pi 侧 `docs/串口协议.md` §6l。
  ⚠️ 第 2 页设的值必落在 111..333，故「去设一下」后这道门自然过（`qr_manual` 也让后面的扫码步骤直接跳过）。
  ⚠️ 第 3 页那三项进确认框后**必须立刻 `return`** —— 那个 `case` 末尾有 `s_ucMode = OLED_MODE_NAV`，不 return 会把刚设好的 `CONFIRM` 冲掉。
- **第 2 页编辑**写 `vSetQrCode()`，三位都是 1~3 → 必落在 111..333。⚠️ 与 `STEP_QR_SET_TEST` 同性质：**会覆盖真实扫码结果**（第 1 行如实显示当前值）。当前值不在 100..399 时编辑起点 111（NAV 态显示走同一缓冲 → 进编辑不跳数字）。
  ⚠️ 方向是 **`DOWN` 加、`UP` 减**（需求如此，与「上下」直觉相反）—— 别「顺手」对调回去。
  ⚠️ 保存时**同时置 `qr_manual`** → 之后路线里的扫码步骤**直接跳过**（见下节）。两处星号（标题 `*`、第 1 页 `QR:nnn*`）就是它的可见性。
- **第 3 页「树莓派关机」= 确认框里按两次「是」，每次一帧 `sd`**：第 1 次 → 发第一帧（Pi 登记，日志「第 1 次收到, 10s 内再发一次才执行」）+ 第 3 行提示变 `再按一次`（**不退出确认框**，否则操作员不知道还差一次）；第 2 次 → 发第二帧 → Pi 执行。Pi 侧 `_require_double_send` 口径是「两次**操作**各一帧」。
  ⚠️⚠️ **别把两帧塞进同一次按键连发**（2026-09 实测踩过）：Pi **只登记不执行** —— 根因：`vRpiSendFrame` 无限流/去重（mutex + 拷进 TX 环）⇒ 只到一帧 = Pi 不认「一按键两帧」。**也别改成「进确认框就发第一帧」**：那样「进框 → 选否 → 10s 内又进框」两帧就落进 Pi 窗口 → **没按过「是」也会真关机**（Pi 只认帧数、帧收不回来，只能**不提前发**）。选「否」清 `s_bShutdownArmed`（干净取消，零帧）。
  ⚠️ 确认框里 `LEFT/RIGHT` 是**选择**不是「退回上级」（与其它子页不同）——要取消就选「否」按 `MAIN`；确认行画的是 `是  否`、**没有固定 `>` 标记**（选中态只靠反色，否则选到「否」时标记还杵在「是」旁，看着像「是」仍被选中）。
  ⚠️ **链路不是 `OK` 时按「是」一帧都不发**，改弹单键提示框 `发送失败:` / `未连接到树莓派` / `[返回]`（`OLED_CONFIRM_NO_LINK`，2026-09 加）—— `vRpiShutdownPi` 只发不等回应，链路 WAITING/DISCONNECTED 时上线没人收、静默会让操作员以为关成了；判据是**按「是」那一刻的 `emGetRpiLinkState()`**，它顺带清 `s_bShutdownArmed`（仍要**两次**「是」才算数）。此框**单键**（`MAIN`/`LEFT` = `[返回]`），`ucOledConfirmKeys` 里必须排在「是/否」之前并 return。
- **第 3 页「开关激光」= 就地翻转激光继电器**（2026-10 加，下标 3）：`MAIN` 一下开、再一下关，回执靠标签状态变化（无回执帧可等，同第 4 页「拍照」; 2026-10-23 撤声后不响）。标签**带状态**：`开关激光:开` / `开关激光:关`；状态取自 Beam `ucGetLaserOn()`，**不是本页的影子**。
  ⚠️ 判据与写引脚读的必须是同一个量：`vRelayOn()` / `vRelayOff()`（`app_actuator.c`）**同时写引脚 + 写 Beam**（`vSetLaserOn`），且激光只有这一对写引脚路径（`STEP_LASER_ON/OFF`、`vLaserShoot`、上电初始化都经它们）⇒ 状态永远等于实物。**别在本页另记一个影子标志、也别新开一条 `HAL_GPIO_WritePin` 旁路**，否则路线跑完 `vLaserShoot`（开→等→关）之后菜单还显示「开」。
  ⚠️ **它没有「二维码得先设好」前置**（不是"起跑"，不动底盘/臂、不投递脚本请求）—— 它是本页唯一**就地动手**的菜单项，不进子菜单。
  ⚠️ RAM 量 + 引脚初始化低电平 = 上电必是「关」，不存在自己亮着的情况。
  ⚠️⚠️ **第 4 行现在被这个菜单项占着**，所以那句「让出成功!」的 `vOledClearArea(OLED_Y4)` **必须挪进 `ucOledWithin(...)` 判断里面**：留在外面就是每拍无条件清行 → 刚画上的「开关激光」每拍都被擦掉、屏幕上看它永远是空的（2026-09 只有 3 项时第 4 行是空的，怎么清都没事）。提示期间两条都画（提示语压住那一项 1s），窗口一过只剩菜单项。
- **「补光灯」开关（2026-10 加，`OLED_ACT_FILL_TOGGLE`，PI管理菜单页）= 就地翻转补光 PWM**（TIM9）：开 = `FILL_LIGHT_ON_DUTY`（与积木 `STEP_BUGUANG_KAI` 不勾亮度同一默认档）、关 = 占空比 0。标签 `补光灯:开/关`，**真值 = Beam `usGetFillDuty()`** —— 纪律同激光：`vFillLightSet` 是全工程**唯一**的补光占空比出口且顺手写 Beam（四个写者：本开关、`STEP_BUGUANG_KAI/_GUAN`、任务自动补光 begin/end 全从它过，没有旁路），所以状态永远等于实物，**别另记影子、别开旁路**。
  ⚠️ 与**任务自动补光是后写者胜**：任务步末的 `vFillLightTaskEnd` 会把这里刚开的灯灭掉、这里也能关掉任务步骤开着的灯 —— 都是既有语义（`app_actuator.c::vFillLightTaskBegin` 处的说明），不是 bug。

### 拍照（第 4 页「拍照」→ 四跳，有回应）

「拍照」→ `vRpiPhotoTake()` → 发 `"9"` 给 Pi → `handler.py::_cmd_photo` 调 `openmv_serial.openmv_reader.send_command(b'P')` → **OpenMV** 存到 `photos/` → 回写 `"P,<ok>"` → Pi 作 **COORD TAG=0x06**（`app_rpi.h::RPI_PHOTO_TAG` / `RPI_PHOTO_LEN` = 2）回传 → 单片机置 Beam `photo_ok` + `photo_done_tick` → 第 4 页那行闪 **`拍照 成功!` / `拍照 失败!` 1 秒**（`OLED_PHOTO_MSG_MS`）后回「拍照」。

⚠️ **单片机的命令只走三跳，回程是第四跳**：`vRpiPhotoTake()` 本身**不等回应**（只发一帧），结果靠那条 COORD 帧异步送回 —— **别**进它里面等，也别做成阻塞步骤（它从 OLED 任务里调）。
⚠️ **单片机没有直达相机的路**：OpenMV 只有一路串口（`UART(3)`）被树莓派占着（Pi 的 `config.py::OPENMV_PORT = /dev/ttyUSB_OpenMV`，一个 CH340 USB 转串口）；本机 USART2（PD5/PD6，板上丝印 VICE_GYRO）与相机**无关** —— 原先那里是个空 stub（`vOpenmvTask`），**2026-10 起删掉、让位给 M0 副陀螺**（见「M0 副陀螺仪」一节）—— 别从那儿发。
⚠️⚠️ **Pi 侧有超时兜底**（`config.PHOTO_ACK_TIMEOUT_S`，默认 3s）：到点没等到 OpenMV 回执就回「失败」。**不能省** —— 没有它，相机没上电 / 跑的是没实现 `'P'` 的旧固件时，单片机那边**一片沉默**（「按了没反应」最难查的那种）。
⚠️ 判「成功」看的是**那条回传帧**，**不是**"盘上看得见"：按 OpenMV 官方行为，**保存的图片要重启相机之后 PC 上才看得见**（别据此判失败）—— 这是**固件行为**，不是我们的 bug。
⚠️ 它**不影响巡线**（相机那边只写文件，采样循环与 `'G'`/`'S'` 开关归别人管），故拍照与巡线可**同时**进行，不像 `"1"/"4"/"5"/"6"` 要先停巡线腾主摄 —— 因此第 4 页「拍照」**没有 QR 前置条件**。

**相机侧脚本**（在 OpenMV 的 U 盘上，不是本仓库）：`main.py` + `photo.py` + `photo_test.py`。
- `main.py` 在「按需发送」轮询里加了 `'P'`；落盘在**第 5.5 步**（图像处理之后、绘调试标记之前）→ 存的是**干净原图**但**带 `lens_corr` 镜头畸变校正**；要带标记就挪到第 6 步之后。
- `photo.py` 负责目录解析/序号/异常吞掉。**三条实测结论（都真栽过）**：
  ① `/` 是 **VFS 虚拟根**（只有 `rom`/`flash`/`sdcard`），往它写报 `ENODEV`；主文件系统是 **SD 卡 `/sdcard`**（= PC 上那个可移动盘 = `os.getcwd()`）。
  ② 目录名**只能用 ASCII**：那台固件的 FatFS 跑在 **CP437(OEM) 模式**，会把字符串的 UTF-8 字节**逐个当成 CP437 字符** —— 中文名会变成乱码孪生目录（`"拍摄照片".encode('utf-8').decode('cp437')` == `µïìµæäτàºτëç`），而 Python 读回来又显示成中文、**看着一切正常**。
  ③ 文件名**不能用时间**（RTC 没校过、`pyb.millis()` 上电归零 → 重启必重名）→ 扫目录取最大序号 + 1，永不覆盖。
- ⚠️ 相机侧**没有 git、没法在本机跑**（只有 OpenMV IDE 按 F5）；验证靠 `photo_test.py`（独立脚本、不碰 UART）+ **PC 侧看盘**，别拿连着 Pi 的 `main.py` 试错。

### ⚠️ 二维码人工预设 → 跳过扫码（`qr_manual`）

OLED 第 2 页保存二维码值（或路线排了「调试二维码」/「随机二维码」积木）后，**`STEP_QR_SCAN_WAIT` 直接返回、不再问树莓派**，沿用那个值 —— 台架没二维码可扫（演练后续步骤 / 排爆反恐链）与**多次扫码无果后的兜底**靠的就是它。

- **生产者**：OLED 任务（第 2 页退出编辑时 `vSetQrManual(1u)`）、脚本任务（`STEP_QR_SET_TEST` 只在值合法时置位 —— 清洗成 -1 的组合本来就要报错，不该顺带把扫码也关掉；`STEP_QR_SET_RANDOM` 写的一定合法，**无条件置位**）。**消费者**：`app_rpi.c::ucRpiQrScan`（决定扫不扫）+ OLED 两处星号 + 遥测 `qr_manual`。
- ⚠️⚠️ **那道门必须在 `vRpiSendTaskCmd(RPI_TASK_QR)` 之前**：`ucRpiWaitQrResult` 一进来就 `vSetQrCode(-1)` 清上一次结果 —— 指令一发出去，手工设的值就已被「没扫到」覆盖，再判就晚了；这是本改动唯一的实现要点。
- 返回 **1**（= 有结果）：下游读的都是 `iGetQrCode()` 那一个值，手工值与扫来的值没区别 —— **IF 条件（`SCRIPT_COND_QR` 的 100~399）、排爆/反恐那两块积木一行都不用改**。
- **怎么知道它生效了**：Pi 日志一条 `QR preset: skip scan` + OLED 两个星号（2026-10-23 撤声后不看声音）（第 1 页 `QR:111*`、第 2 页数字行 `[1] [1] [1] *`——2026-10-18 起「二维码设定」那项撤了, 星号挪到数字行）。
  ⚠️ 「随机二维码」那块额外打一行 `QR random: nnn`（它当场置位、不经任何扫描，故后面若没再排扫码步骤，`QR preset: skip scan` 不出现 —— 此时唯一能看出「随机到了哪个值」的就是这一行 + OLED 的 `QR:nnn*`）。
- ⚠️ **只有复位/断电能清**（RAM 量，故意如此：比赛上电后默认就是真扫码）；台架演练完忘了重新上电，比赛时就会看到 `QR:111*` 一直不动 —— 星号就是为这个加的：一眼分清「扫码被跳过」和「相机/二维码真的扫不到」。
- ⚠️ `STEP_QR_SET_TEST` 里那句 `vSetQrManual(1u)` **必须写在 `vSetQrCode(...)` 之后**：控制台取积木原语名读的是 case 体里**第一个**函数调用，放前面这条积木会显示成 `vSetQrManual`（`parse_catalog` 的 `primitive` 字段，map.c 行尾注释也跟着对不上）；已核对显示仍是 `vSetQrCode`。`STEP_QR_SET_RANDOM` 同一条规矩 —— 它把这两句收进 `vSetQrCodeRandom()` 内部（顺序写在函数里），故 case 体里只有一个调用。

### ⚠️ 「执行任务」的机械臂展开前置条件（`arm_deployed`）

OLED 第 3 页「执行任务」跑的是 `SCRIPT_REQ_TASK`（**不是**一般的「跑个预设」）—— 多一道前置条件：**机械臂必须先从初始折叠位展开过**。

- **为什么**：任务动作（抓球 / 打靶 / 抓人质）内部位姿都假定臂已展开，从**折叠位**直接摆过去会撞桌子/撞车身 —— 必须走「机械臂待命」（`ARM_ACT_1`）那条**三段式**序列（伸出 → 伸展 → 旋转到待命），一步直摆危险。
- **为什么用 flag 而非排积木**：展开**只需一次**（排进三条预设则跑三条各展开一次，只排一条则先跑哪条看操作员），故用 Beam `arm_deployed`（`ucGetArmDeployed`）记「**展开过**」。
  ⚠️ 它的语义**不是**「现在停在待命位姿」：用户口径是「展开过就够了，之后臂挪到哪儿都无所谓」，故臂停在别处时标志仍是 1。
- **谁置位**：**机械臂动作层**（`app_arm_action.c::vArmNoteDeployed`），各播放路径播完都走到 —— 路线里那两块大积木、`$B,PLAY`、排爆/反恐那两处。
  ⚠️ **只认 `ARM_ACT_1` / `ARM_ACT_12` 这两条待命序列**：别的臂动作（**含「复位回待命」`ARM_ACT_11/17`**）都直接摆到目标位姿，从折叠位起摆有撞的风险，不算「已安全展开」；加新的待命序列时记得也把它列进去。
  ⚠️ 只在**完整走完**时置位：`vArmPlayWait` 的调用点放在循环之后（该循环不查代次号，一定走完），泵那边放在「代次没变」的收尾分支里（被中止/顶掉就不置）—— 半途而废不算展开，正是本标志要防的「以为臂出去了、其实还折着」。
- **是 RAM 量，复位清零，故意如此**：复位后操作员可能手工掰过臂，重跑一遍展开序列是安全的（只多动几秒），胜过「误以为已展开、从折叠位直接撞过去」。
- **拒绝而不是硬跑**：待命动作不在注册表里（控制台删过/改号）、或播完没置上位 → **给 Pi 打调试串 + 拒绝，任务不执行**（不响）；折叠状态下硬跑任务比不跑更危险。
- ⚠️ **展开那一段是阻塞的，必须先 `vSetScriptRunning(1u)`**：`vScriptRun` 要到后面才置位，不占住的话蓝牙那边进场条件（「脚本没在跑 ⇒ 允许进机械臂编辑模式」）会把这段判成「脚本闲着」，操作员一点 `$B,MODE,1` 就进来和正在伸出的臂**抢舵机**。
- 遥测：`arm_deployed`（蓝牙 Tab「机械臂」组，只读）—— 「按了执行任务却没反应」先看它：0 = 还没展开过（会先跑待命）；调试串 `MENU: standby action missing, task refused` / `MENU: standby incomplete, task refused` 即任务被拒。

### ⚠️⚠️ 三条别踩回去的纪律

1. **菜单不能碰 `ucTakeMenuConfirm()`。** 那是脚本任务的「继续」键（`STEP_STOP` / `STEP_DEAD` / 让位积木 / 测试积木在等它），**读后清零、只能有一个消费者**。菜单走自己的位掩码通道（`vOledKeyPost` / `ucTakeOledKeyMask`），一次按键两条通道各置一份。菜单只要**不在第 1 页**就把 `vSetOledMenuBusy(1)` 拉高，按键任务见它**不再**喂脚本 —— 否则「在菜单里按 `MAIN` 选任务」会顺带把停在 `STEP_STOP` 的路线放走，**车突然动**；第 1 页 `busy=0`，比赛路线行为一字不变。
   - ⚠️ 派生：**菜单启动的预设若停在 `STEP_STOP` / `STEP_DEAD` 这类等 `MAIN` 的步骤，从菜单页放不走**（`MAIN` 被菜单吃着）。2026-09-27 起第 3 页「执行任务」投递成功**不再自动跳回第 1 页**，故 `map.c` 那三条 OLED 任务预设（色球放置 / 激光射靶 / 人质抓取）**别加** `STEP_STOP` / `STEP_DEAD` / 让位积木 / 测试积木；真加了，出路是 **`LEFT` 两次翻到第 1 页**（`busy=0`）按 `MAIN`，或在本页重开一个任务（`vScriptPostReq` 先中止停住的那条）。**别再「顺手」把自动跳页改回来。** 投递成功**无声音**（2026-10-23 撤声; 靠页面跳转/状态变化确认 —— 老版靠短鸣防「以为没按上再按 = 中止+重跑」）；「槽位被占 / 前置条件不满足」也是静默拒绝（留痕）。
2. **菜单不直接执行任何会阻塞或动底盘的事。** `ucRpiHandshake()` 阶段 1 是 `while(!ucTakeHandshakeSeen())` **无限等**（Pi 不上电就停住），而 OLED 是**最低优先级(1)** —— 阻塞它 = 整屏停摆、连 `BT:HS WAIT` 这个操作员唯一的反馈都没了；且 `s_bHsDone` 只有脚本任务读写；跑路线/巡线会动底盘。所以一律 `vScriptPostReq()` 投给 `vScriptTask`：`SCRIPT_REQ_PRESET` / `SCRIPT_REQ_HANDSHAKE` / `SCRIPT_REQ_LINE_TEST`。
   - **请求槽只有一个，不排队**（后写者胜）；投递失败回 0，**调用方必须长鸣响出来**。
   - 每个请求都**先置中止位**（`vScriptPostReq` 里做）→ 「新指令显式终止旧的」。中止点在**步骤边界**，不是从半路掐底盘/臂。

   ⚠️⚠️ **凡是「等外部事件」的循环都必须带上它**，漏一个就是一类死结。踩过**三次**，现状（全都不能删）：

   - `vBtArmEditHold` 的中止出口是**干净的**: 走 `break` 后同一段收尾（`bt_hs_wait` 归零 + 链路回 `OK`），不是半途而废。
   - ⚠️ **已知的例外（有意不加）**：`c_ucSeqDrain`（`ucArmPlayByMode` 的阻塞档）有 10ms 采样 + `ARM_SEQ_DRAIN_TIMEOUT_MS`(60s) 硬上界，且返回值有约定语义（0 = 降级，调用方要留痕报出去, 不响）—— 它是**有界**的，加中止反会把「等臂到位」弄成「降级告警」，留着。
   - ⚠️ **巡线那一步必须在自己循环里查它**（`app_line.c`），不能只靠步骤边界：那一步时长 `0xFFFFFFFFu`（实为不限），只在边界响应 = **停不下来**；中途退出也要靠它才来得及给 Pi 发 `LINE_STOP`，否则 Pi 一直 30Hz 推巡线帧，白占相机 + 拖累 50ms 的 `vPidTask`。中止时打一条 `LINE abort: stop by request`（**不加进 `LINE:` 那条串**：那条已接近 `RPI_DATA_MAX`(64) 的静默截断线）。
   - ⚠️ `ucRpiHandshake` 阶段 1 那个中止出口也**别删**：没它，Pi 不上电时菜单发起的「握手让出」就**死等**并连带堵住后面所有菜单请求（2026-09 踩过：先点「握手让出」（Pi 已开机，永远等不到 `SYNC_HS_1`）、再点「开始巡线测试」→ Pi 只看到心跳）；该出口返回 0 时**不动** `s_bHsDone`。
   - **菜单请求「没反应」怎么查**（按顺序）：
     1. **回第 1 页按一下 MAIN 就动了吗？** 动了 = 脚本任务卡在某个「等外部事件」的循环里（上表），不是菜单/投递的问题（2026-09 踩的就是这个）；修法是在那个循环里加中止位检查。
     2. `ucOledPostReq` 失败（请求槽被占）会拒绝并留痕（不响），不静默吞掉；巡线测试标签也只在投递成功时才翻成「停止巡线测试」（否则下次按键会走成「停」，看着就是「点了没反应」）。
     3. 脚本任务真正开跑巡线前会打一条 `LINE test: start` —— Pi 日志里**没有**这条 = 脚本任务压根没跑到；**有**这条而 Pi 没收到 `"2"` = 另一回事。
