## 标靶对位（反恐区打靶：STEP_TARGET_ALIGN_WAIT → ucRpiTargetAlign）

先横移摆正、再让臂细瞄——与「人质对位」同构的底盘对位步（2026-09 加）。

链路：发 `"6"` → Pi 回 `0x04` 帧 → **三颗齐才算数** → 取第 `idx` 颗（`0左/1中/2右`，默认 1=中间）作基准 → 其**横向**偏差 × 比例尺 → `vChassisMoveCameraLateral` 横移到位。

- ⚠️ **"三颗齐"不能省**：基准=「第二个」，**三颗全在画面它才真是中间那颗**；两颗时右靶被当"第二个"→**照错位置横移**、不报错（同 `ucHostageScanOnce` 的 `cnt==3` 门）。⚠️ 别调 Pi 的 `TARGET_MIN_TARGETS` 配合（它管 Pi 判识别成功，默认 1，非"对位可用"）。
- ⚠️ **只横移**（人质/小球那两步是横+纵两轴，刻意不是），前后距离由路线排定；补纵移照 `hs_*` 加 `px_to_mm_y`/`fwd_sign`/`dy_deadband` + `vChassisMoveCameraForward`。
- ⚠️ **不做转正**：`0x04` 帧无连线角字段，车歪时整排靶一起平移+透视、单点分不出；治车头朝向须另配带 IMU 闭环的一步。
- 标定量 `TARGET_ALIGN_*`（9 宏）+ 蓝牙组**「标靶对位」**（`ta_*` 8 条），**独立一套**，不共用 `TARGET_*`/`HOSTAGE_*`/`BALL_*`。标定序：`ta_side_sign` 看方向 → `ta_px_to_mm_x` 看走多少 → `ta_dx_db_mm` 收到不抖。
- ⚠️ **不碰机械臂，故不进 `c_bIsArmStep`**（同 `ucRpiHostageAlign`）。
- 排表：**排在 `STEP_TARGET_CALIB_WAIT` 之前**（粗调用车、细调用臂；20° 上限见 `TARGET_MAX_STEP_DEG`）。调试串前缀 `TGTA`：`TGTA meas:`/`TGTA fix:`/`TGTA fail:`。

## 标靶校准（反恐区打靶：STEP_TARGET_CALIB_WAIT → vTargetCalibAim）

链路：发 `"6"` → Pi 回 `0x04` 帧（三靶心+半径）→ 按**二维码第二位**选目标色 → `Δ = 靶心 − 瞄准点` × 比例尺 → **舵机6 管画面横向(X)、舵机3 管纵向(Y)** 各走一段。

- **标定量全是蓝牙可改的 Beam**（2026-09 加，「蓝牙」Tab**「标靶校准」组**）：`tg_center_x/y`（瞄准点）、`tg_px_to_deg_x/y`（比例尺）、`tg_x_sign/y_sign`（方向）、`tg_deadband_px`、`tg_max_step_deg`、`tg_move_ms`、`tg_move_slack_ms`、`tg_xy_swap`、`tg_calib_timeout_ms`。断电回 `app_config.h` 的 `TARGET_*` 宏=上电默认；「调参」Tab 才是持久默认（同 `BALL_*`/`HOSTAGE_*`）。**标定序**：`tg_x_sign`/`tg_y_sign` 看方向 → `tg_px_to_deg_x/y` 看走多少 → `tg_max_step_deg` 收步长。
- ⚠️⚠️ **`TARGET_MAX_STEP_DEG`（`tg_max_step_deg`）是安全夹，不是精度旋钮**：修正量=`偏差px × 比例尺`**本无上限** —— 靶心落画面边缘偏差可达 ±900px，×0.05°/px = **±45° 一次臂摆**，而它可能来自误检（角落同色杂块），开环增量式被带动会**越走越偏**；夹住后单次最多 20°（≈400px），**收敛靠同一积木连排几步**，不是一步到底。⚠️ **它与路线排的步数是一对**：默认 20° + 「测试标靶」预设**两步** ≈ 800px 兜住整幅画面宽；**调小须同步多排几步**，否则位姿偏远会停在没收敛处（不报错、打不准）。
- ⚠️ **`TARGET_XY_SWAP`（`tg_xy_swap`）同 `BALL_XY_SWAP`/`HOSTAGE_XY_SWAP` 语义**：「横/纵两路**轴+比例尺**整套对调」，相机相对车体装 90° 时才开；方向符号仍各走 `TARGET_X_SIGN`/`TARGET_Y_SIGN`，不跟着翻。⚠️ 它是**一个开关**而非「画面X/Y 各填舵机号」（会配出「两轴指同一舵机」的危险组合）；换非 6/3 舵机是接线改造，改 `vArmAimByPixels` 的 `ARM_SERVO6`/`ARM_SERVO3`，不是标定旋钮。
- ⚠️ **增量式**：`vArmAimByPixels` 以舵机**当前角**加偏移、非走绝对角 → 同一积木连排两步即迭代收敛（`map.c`），不必写循环、无需迭代次数。
- ⚠️ **开环**，刻意不做视觉伺服：Pi 一帧三色掩膜+多帧投票，闭环滞后太大反摆振；精度全压在比例尺与方向四个量。
- ⚠️ **二维码没结果就整段不做**（拒绝返回，绝不动臂; 不响, 留痕）；找不到目标色、Pi 没回帧同理。2026-10-23 撤声后放弃/已在死区/已微调都**不响**, 看调试串与 OLED。
- ⚠️ **`STEP_TARGET_CALIB_WAIT` 必须进 `c_bIsArmStep`**（app_script.c）—— 末尾动舵机6/3。
- `STEP_LASER_SHOOT`（`vLaserShoot`）把「开-等-关」封成一步：排成开/`STEP_DELAY`/关三行时中间延时易漏，变成激光一直开着。
- `STEP_BOMB_GRAB_WAIT`（`ucRpiBombGrab`）= **排爆抓取**（2026-09 加）：读二维码**首位**（1红/2绿/3蓝）→ **已识别**三球里的位置（0/1/2=左/中/右）→ 播对应**动作预设**（左/中/右+复位四个 ID 参数，下拉自动取自 `emArmActionIdTdf`）→ 播复位。⚠️ **读最近一次结果**：须排在「二维码扫描+色球识别」之后（`STEP_BALL_ALIGN_WAIT` 发 "5" 取三球结果）；数据不全（二维码 100~399 之外 / 三球不齐 / 无此颜色）→ **拒绝且一步不动**（不响, 留痕）。已登记进 `c_bIsArmStep`。⚠️ 参数类型**必须** `emArmActionIdTdf`（case 里 `(emArmActionIdTdf)I(n)`）；写成 `(uint8_t)I(n)` 控制台认不出枚举、下拉变手敲数字。
  - ⚠️ **抓取/复位各自阻塞方式跟随该动作标的「播放方式」**（`ucArmPlayByMode`，2026-09 加），不再写死 `vArmPlayWait`：都「阻塞到位」= 抓完再复位（**=改前行为**）；抓阻塞+复位启动即返回=路线先走、臂后台待命；抓启动即返回+复位阻塞=**整体仍阻塞**（④等排到自己那一刻，不掐③）；都启动即返回=立即返回、后台依次跑完。故 `_WAIT` 在这两块上**不代表一定阻塞**（同 `STEP_IF` 委托）。⚠️ 连带：**改一个动作的播放方式会同时影响路线那块大积木和排爆/反恐两处**（`#arm-mode` tooltip 已写明）。⚠️ 降级（队列满/超时）Pi 打 `BOMB arm play degraded` 留痕（不响）。
- `STEP_HOSTAGE_RESCUE_WAIT`（`ucRpiHostageRescue`）= **反恐任务**（2026-09 加）：与排爆抓取**同构**（`diff` 即见「只换了键」）：

  | | 排爆抓取 | 反恐任务 |
  |---|---|---|
  | 键 | 二维码**首位**=目标色 | 二维码**第三位**=目标**形状**（1圆柱/2圆锥/3腰鼓，同 `emHostageShapeTdf` 码） |
  | 查表 | `color_t`+`stColorTgtTdf` | `emHostageShapeTdf`+`stHostageTgtTdf` |
  | 取位 | `iQr / 100` | `iQr % 10` |
  | 末尾 | 播复位预设 | **不复位** |

  两组码值**都恰是 1/2/3**，语义不同（颜色 vs 形状）。
  - ⚠️ **`% 10` 后还要单独判一次 1~3**：`iQr` 的 100~399 **不保证**第三位合法（390 的第三位是 0）；不判会落到越界形状码、`for` 找不到，退化成"没这形状"。
  - ⚠️ **不复位是本步存在的理由，不是省事**：复位由路线自己排；**别加复位参数、也别在函数末尾偷偷补复位**（与 `STEP_BOMB_GRAB_WAIT` 的分工）。
  - ⚠️ 依赖「最近一次结果」，须排在「二维码扫描+**人质**识别」之后（`STEP_HOSTAGE_ALIGN_WAIT` 发 "4" 取三只结果复用）；数据不全（二维码 100~399 之外 / 第三位不在 1~3 / 三只不齐 / 无此形状）→ **拒绝且一步不动**（不响, 留痕）。
  - ⚠️ **阻塞方式跟着该动作标的「播放方式」**（`ucArmPlayByMode`，同排爆那套）；降级同样 `HSTG arm play degraded` 留痕（不响）。
  - 三个动作参数**按位置**（左/中/右）而非按形状（形状由二维码+识别结果**推**出）；参数类型同样**必须** `emArmActionIdTdf`。已登记进 `c_bIsArmStep`。
  - `STEP_QR_SET_TEST` 那条「三位=序号」的**第三位就是本步形状码**；台架演练：调试二维码 `x x 1`=圆柱、`x x 2`=圆锥、`x x 3`=腰鼓，前两位随便（归排爆/标靶用）。
- `STEP_QR_SET_TEST`（`vSetQrCode`）**测试积木**：直接写成指定三位数、不经 Pi。⚠️ 会覆盖真实扫码结果。**每位只能 1~3**（百位=目标色/二位=靶色/三位=序号）：下拉是显式枚举的 27 种组合（`app_script.h` 的 `{111=111,…}`），固件另有防呆 `c_iQrTestSanitize`（非法 → -1）。
- `STEP_QR_SET_RANDOM`（`vSetQrCodeRandom`，**无参**）= **随机调试二维码**：每次写**随机合法三位数**（每位 1~3，共 27 种）并打 `qr_manual`。用途=**多次扫码无果后的兜底**：排爆抓取（首位=色）/反恐任务（三位=形状）/标靶校准（二位=靶色）都按它选目标，值=-1 就整步不动、整链停摆；**重试由路线表达**（连排几块扫描 + 「如果/否则」嵌套，兜底支放本块）；它自己不扫码、不碰串口协议（只发一行调试串），Pi 端一字不改。⚠️ 打了标记=后面**所有**扫码步骤都跳过（见「二维码人工预设」节，复位/断电才能清）。⚠️ **不保证与上次不同**（撞上同一个正常）。随机源=自写 xorshift32（`app_rpi.c::c_ulQrRandNext`，熵=tick+调用序号+芯片 UID），**刻意不用 libc `rand()`**（全局态、非可重入）。现场判据：OLED `QR:213*`+Pi 日志 `QR random: 213`（不响）。不进 `c_bIsArmStep`（不碰舵机）。
- `STEP_ARM_EDIT_WAIT`（`vBtArmEditHold`）= **中途让位手动操纵机械臂**（2026-09 加）：停车+拉高 `bt_hs_wait`（`$B,MODE` 入场条件）+**把链路钉在 `WAITING`**，停这里等 MAIN 键（或 PC 退出编辑）。⚠️ 为何钉：编辑模式**退出门是「链路 OK」**（`vBtEditPump`），而 `DISCONNECTED` 会被 vRpiTask 的「收到任何有效帧即恢复 OK」翻回来（心跳 2s）→ **只有 WAITING 稳定**；退出恢复 `OK`——**别留在 WAITING**，否则后续「等待握手」永等 `SYNC_HS_1`（卡死）。⚠️ 它**不真的断开 Pi**、不给 Pi 发指令；要 Pi 停手得另发 `RPI_TASK_END`。已登记进 `c_bIsArmStep`（先掐后台臂序列，免得 PC 与后台抢舵机）。
- `STEP_TEST_LOOP_WAIT`（`vScriptTestLoop`）= **「测试」积木**：参数选某积木+轮数反复执行，每轮跑完等 MAIN 继续（轮数 0=不限; 不响）；**参数整条照抄「已知的那一块」**：先扫**当前表**，找不到再**扫整个预设注册表**。⚠️⚠️ **一处都找不到时参数只能是全 0，而 0 对带超时/距离/角度的积木是致命的**（`STEP_BALL_ALIGN_WAIT(0)`=发完立刻超时，现象是「Pi 报识别成功、单片机一直报失败」）→ 这时**发 `TESTLOOP: no params found (all-zero)` 调试串并拒绝**（不响），不再静默跑空动作。实现：把 switch 抽成 `vScriptExecStep`（主循环与它**共用同一份**语义）合成一张一步表——别改成第二套简化执行器。防呆：不能选「测试」自己（合成表递归爆栈）、「重置脚本」（紧循环）、哨兵 `STEP_COUNT`→ 拒绝（留痕）。台架沙盒=预设 10「测试积木」（测 1s 延时）。

**⚠️ 视觉帧坐标空间**：人质帧与色球帧的 `cx/cy` 都是 **1920×1080 全分辨率**像素。Pi 为提速降采样（`COLOR_PROC_SCALE`），**回传前必须还原回全分辨率** —— 漏了这步，`BALL_CX_CENTER`/`BALL_PX_TO_MM_X` 等标定成比例失真且不报错。

**双端配套**：Pi 端还需改 `handler.py::_COMMANDS`、`tasks/__init__.py` 导出、`GKS_Web/simulator.py::COMMANDS`、`docs/串口协议.md` §6（详见 Pi 端 `CLAUDE.md`）。


## 标靶流控闭环（反恐区打靶：STEP_TARGET_SERVO_WAIT → ucRpiTargetServo）

**与「标靶校准」并存的第二套打靶方案**（2026-09 加）。老方案 `"6"` / `0x04` 帧 / `STEP_TARGET_CALIB_WAIT` / `ucRpiTargetAlign` / 预设 8 一行未动，两套可混排。

**改的是「测量密度」，不是「检测算法」。** 落点随机病根**不在检测**（离线 61 用例中位 0.26mm / p95 0.59mm，10 环半径 7.5mm），而在**开环执行链**：① 比例尺线性近似只在标定位姿附近成立，首轮大修正（≤±20°）落在非线性区，步数有限时停在半收敛位**不报错**；② **舵机回差**：修正方向可能反转，「指令到位 ≠ 实际到位」，落点取决于最后一次逼近方向；③ 相机-激光视差烤死在 `tg_center_x/y` 一个固定瞄准点里，姿态一变残差跟着变；④ 每轮 `"6"` 重开摄像头（15 帧预热 + AWB）+ 8×220ms 采帧 + 1s S 曲线，单轮 4~5s。

**新方案**：锁定目标后 Pi 在小跟踪窗内 ~20Hz 回传靶心（`0x05` 流帧），MCU 以 ~10Hz 节拍做比例闭环微调舵机6/3。①② 被**根治**（回差变死区；比例尺失准只影响收敛速度、不影响终点），③ **缓解**（残差变常数偏移，标一次有效）。

```
① STEP_TARGET_SCAN_WAIT（可选）  ──"6"──► Pi run_target_detect（现有，未动）
② STEP_TARGET_SERVO_WAIT（新）   ──"7"──► Pi tasks/_target_stream.py（新，独立线程）
                                 ◄─0x05 流帧 ~20Hz─（小窗跟踪 + 门控）
   MCU: 10Hz P 环 → 舵机6/3 小步 S 曲线；收敛 / 超时 / 行程超限
                                 ──"8"──► 线程退出、释放相机
③ 终验（可选）= 现有 STEP_TARGET_CALIB_WAIT（全分辨率 8 帧投票 + 死区判断 + 按需终补）
④ STEP_LASER_SHOOT（现有，未动）
```

**职责划分**：**Pi 只发测量**（窗内所有靶 ≤3 颗、带颜色、全分辨率坐标；目标由 MCU 按二维码第二位挑，与 `0x04` 帧同构）；**MCU 做闭环**，瞄准点/比例尺/方向/XY对调**共用现成的 `tg_*`**；新增 `ts_*` 只管**闭环节拍**。

**⚠️ 几个别踩回去的点**：
- **`0x05` 用独立 Beam 快照**（`vSetAimFrame` + `ulGetAimFrameCount`），**不是** `ready` 一次性信号（否则读者会把信号偷走）：语义是「**帧计数还在不在涨**」；`count=0`（丢目标）**也推进帧计数**，靠它区分「流活着但没找到靶」与「流停了」。
- **两个快照必须分开**（`0x04` / `0x05`）：否则闭环停流留下的最后一帧会被终验当成「权威结果」。
- **`ucRpiTargetServo` 里 `"8"` 必须放在唯一出口**（收敛/超时/行程超限都经它），否则 Pi 一直占着相机（`TARGET_STREAM_MAX_S` 只是最后一道保险）。
- **帧新鲜度停涨 = 冻结，不是放弃**：定格不动舵机、`convCnt` 归零，Pi 回来即续跑 —— 否则一次几秒的链路抖动会变成「瞄准彻底失败」。
- **行程闸（`ts_travel_deg`）是安全夹、不是精度旋钮**：误检带飞会「越纠越偏」，累计行程一到即拒绝放弃（不响, 留痕; 同老方案 `TARGET_MAX_STEP_DEG`）。⚠️ 它同时是**「起手偏差能吃多大」的硬上限**：实测 **1° 舵机行程 ≈ 17~19px 图像偏差** ⇒ 25° 只能吃 ~440px —— 2026-10-01 红靶起手 cx=297、瞄准点 900（**-619px**），环**单调收敛、方向符号全对**，却因闸先到而在 dx 还差 172px 时 `TGTS fail: travel` 放弃（不响）；另一轮起手 -460px 在 trX=24 收敛。已把宏 `TARGET_SERVO_TRAVEL_DEG` 25→**50**（≈880px）。⚠️ **抬 `ts_step_deg` 不能替代**：单调逼近时累计行程 ≈ 实际走过的度数，下限由 17~19px/° 定死；正解是**排表上先粗对位**（`STEP_TARGET_ALIGN_WAIT`）。⚠️ 放宽代价：误检带飞敞口同比例变大；最后防线是**下发前的静态量程钳位**（舵机3 0~180 / 舵机6 0~360）。「环没起作用」另有独立的 `noprog` 闸。
- **`_target_stream.py` 的跟踪窗是「动窗」**：舵机动一下靶心就走几百 px，窗跟着目标走（跟上一帧 ± 边距），丢失时逐帧扩张 → 全画面重搜。**提速靠「裁」不靠「缩」**（`TARGET_PROC_SCALE` 降 0.5 时遮挡用例整颗漏检）。
- **互斥**：`"7"` 先停巡线、`"2"` 先停靶标流（两条流独占主摄 + COORD 通道）；Pi 收到 `"1"/"4"/"5"/"6"` 与 `"end"`/`"r"` 时**先停靶标流**。
- ⚠️ **COORD 诊断行必须排除 `0x05`**（`app_rpi.c`）：流是 20Hz，逐帧打一条 `[STM-DBG]` 会把 RPI 链路流量翻倍、刷爆 Pi 侧日志。（**原理由「`vRpiSendDebug` 忙等、拖垮 `vPidTask`」2026-09 改 DMA 后已不成立 —— 但它本来就该排除，属流量问题，别据此删掉这一行。**）Pi 端流帧同样**不进模拟器通用日志**，只 1Hz 摘录（帧率 + 靶数 + 坐标）。

**台架实测（2026-09-20）**：Pi 稳态 **~22Hz**（`TARGET_STREAM_HZ` 上限 25，1920×1080 每帧 ~45ms）；**流式与 `"6"` 全画面路径检出一致到 ~1px**（`蓝(719,518)r60 / 绿(911,518)r65 / 红(1098,522)r65` 对 `蓝(719,518)r60 / 绿(911,519)r65 / 红(1097,522)r64`）。

### ⚠️⚠️ 2026-10-30 跟踪器抗「开补光灯才坏」修正（Pi 侧，三个根因）

现场现象：**不开补光时标靶流正常，开补光后红/蓝靶一丢就是好几帧**，固件日志夹着
`SHOT warn: color 1 r=82px rejected` / `d jump 124px rejected`，而 Pi 预览画面本身
**不过曝、颜色也正常**。查下来是三件事叠在一起，**不是补光把图像打坏**：

1. **半径门拿错了口径（主因）**。跟踪器存的 `r` 是 `_locate_one` 给的**内孔反推外径**
   （稳定），而候选的 `cand["r"]` 是 `minEnclosingCircle(色环掩膜)` —— **靶和同色背景
   粘连时它会被撑大**：蓝靶贴蓝柜子、红靶贴纸箱。实测同一颗蓝靶的 minEnclosingCircle
   在窗内随连通程度在 **139~158px** 跳（内孔反推恒 **184px**），一帧过门一帧不过 →
   丢帧 → 窗扩大 → 粘上更多背景 → 更不过门，**自激振荡**。补光灯把背景打亮后粘连更厉害，
   所以表现成「开灯才坏」。修法：`_target.py::_color_candidates` 给每个候选加 `r_eq`
   （内孔 ÷ 0.55，无内孔 = None），`_target_stream.py::_size_of()` 让**半径门比 r_eq**。
2. **丢帧后半径门放得太松**。原 `r_tol×(1+0.15×lost)` 封顶 1.6 倍 —— 丢 4 帧后
   `r=84` 的干扰块也能过门（`|84−174|=90 < 174×0.56`），这就是固件那条
   `r=82px rejected` 的来源（假测量被固件按半径范围拒掉，然后该色继续丢、越丢越松）。
   改用内孔口径后基准稳，放宽只需吸收遮挡/透视：**0.10/帧、封顶 1.30 倍**。
3. **跟踪是逐色独立的、且窗只按固定边距**。舵机一拍能把靶推 ~250px，靶压在窗边时
   色环被裁断 → 白心不再是闭合孔 → 内孔拟合/白心救回全失效。修法：跟踪器记 `(vx,vy)`
   （上一帧位移，丢失期间逐帧减半），`_window_of` 用**速度前瞻**挪窗心；本帧丢的色
   用**跟上的色**的中位位移一起平移（三种靶在画面里是一起动的），窗不会停在旧位置。
   另有 `_pick_tracked` 的 `4×r` 距离安全阀 + **内孔候选优先**，以及 `_lock` 的
   **假锁过滤**（半径地板 = 0.12×`r_max`，实锤曾锁到画面角落 `R(1151,33)r15`）和
   **差色时多采几帧**（跟踪阶段不会去搜没建跟踪器的颜色）。
   - ⚠️ **差色多采帧（2026-11-02 现场修正）**：原判据「≥2 色就早退」在**车还没停稳**
     时会漏掉第三色。实锤（16:47:38）：粗调 112mm 的 `SHOT fix` 与起流 `"7"` 同一秒
     发出，锁定第 1 帧漏了绿靶 → 只锁 R(267,1064)/B(745,1047) 就收工 → 整条流没有
     绿跟踪器 → 精调选不到瞄准色 → `SHOT settle s=0` → 12s 超时 `SHOT fail`。
     日志里那条 `靶标流锁定忽略疑似假锁: G(170,1360)r21 < 半径地板 42px` **是过滤器
     正常工作**（5MP 下真靶 r≈178，r21 是角落碎块），不是故障本身。
     修法：彩色模式下 `need=3`，差色时最多读到 `_LOCK_PARTIAL_FRAMES`(6) 帧；三色齐时
     仍是**第 1 帧收工**，无色模式行为不变（两色/上限 3 帧）。离线验证（同一份检测
     代码 + 现场静止帧）：三色齐 1 帧、首帧缺绿 2 帧、前两帧缺绿 3 帧、一直缺绿 6 帧
     后按老行为出 2 色。
   - ⚠️ **同机位静止时算法本身是好的**（2026-11-02 用 `rpicam-vid` 抓 22 帧回归：
     22/22 三色齐，R(262,1014)r178 / B(739,1001)r177 / G(1286,985)r176）—— 碰到类似
     "某色没锁上"先确认车是否已经停稳、再看那几帧是不是运动模糊，别急着调阈值。

**⚠️⚠️ `ts_ctrl_ms` 必须 > `ts_move_ms`，差值就是"停稳段"**（2026-09-20 台架实测后修正；**2026-10-06 起它的实现从"盲等 ctrl_ms"改成"等舵机真正到位 + 停稳段"，见下**）：「走 N ms → **停** → 采帧」里那个"停"**不是自动的** —— 盲等版 `vTaskDelay` 后立刻读到的**最新一帧**是相机在舵机**运动中**采的（Pi 还要 ~45ms 处理），`ctrl == move` 时采到的全是运动画面，**等于没有"停"这一步**。
- 实测症状（初始偏差仅 22px 却振荡到行程闸）：偏差反复穿越零点、幅度一路涨；逐拍「实际移动 ÷ 期望移动」在 **7.0× 与 0.1× 之间乱跳**（采样落点随机）。
- **这不是增益问题**：增益不对会让倍率**一致地**偏离 1，而它**乱跳**。所以**先查 CTRL/MOVE 比例，再动 `ts_kp_scale`**。
- 搭配不对固件仍会打 `TGTS warn: ctrl<=move no settle`（停稳段被钳到 50ms 下限）。
- ⚠️ **底盘接管阶段这条纪律不适用**：那个"停稳"由 `vChassisMoveCameraLateral` 内部的 `fChassisMoveDelay` 阻塞等待提供，与 MOVE/CTRL 差值无关；底盘阶段要查就查 `ts_chassis_px_to_mm`（过冲 = 太大、收敛慢 = 太小）。

**⚠️⚠️ 2026-10-06 节拍重写：盲等 `ctrl_ms` → 「等舵机真正到位（`ucServoIsSmoothStepDone`，含被速度闸削峰后的恒速收尾）+ 停稳段」**。根因：被 `ARM_SERVO_MAX_SPEED_DPS` 削峰后，小步的真实耗时经常 **> `move_ms`**，固定节拍里"停稳段"被运动吃掉 → 采到运动帧（现场为治 dy 振荡把 ctrl 从 180 抬到 280 就是它）；而小步快收时又白等满 ctrl。改后：**上一拍发过舵机步的拍先等两轴曲线走完（上限 move+700ms 兜底防舵机卡死）再等停稳段（= ctrl−move 的差，语义不变）**；死区/无帧/首拍的拍只等停稳段。效果：小步的拍 ~200ms 就能采（280/100 默认下原来 380ms，收敛速度近翻倍），大步永远不会再采到运动帧——**速度与准确率同时受益，参数一个不用改**。⚠️ 等到位的循环带中止位（铁律）；等待耗时计入 `ulElapsed`（超时预算按真实耗时算）。同日 Pi 侧流帧率 ~22Hz→贴 30fps（读帧线程双缓冲，见 Pi 仓库 `tasks/_target_stream.py`）。

### ⚠️ 阶段化 X→Y + Y轴踢步 + 距离辅助（`ts_seq_en`，2026-10-06 加，**默认开**）

**机理先记住**：舵机3 **没有位置回读**，`servo_device` 的 `fCurrentValue` 是纯指令模型 —— 低于静摩擦/回差的小步长（如 dy=4px→0.08°）舵机原地不动、模型却照常推进，**指令目标以每拍一步的速度从物理位置"溜走"**，某拍突破静摩擦后一口气冲向溜走的终点 = 现场看到的"给值不动、憋久了突然大角度超调"（2026-10-05 实测 dy=4px 卡 9 拍到超时）。三层处方（`ts_seq_en=0` 全部不参与，行为逐字节同旧）：
1. **阶段化**：先只修左右（舵机6→底盘接管，判据 `ts_conv_x_px`）→ 切只修上下（舵机3，判据 `ts_conv_y_px`=2.5 比旧 conv_px 紧）。Y 阶段通道安静（底盘不再搅动 dy 读数）。换挡/接管/去抖那套机制**只在阶段1跑**。
2. **踢步**：Y 停滞（连续 `ts_stall_ticks`=3 拍改善<1px）且 |dy|<2×conv_px → 朝 P 律方向发一次 `ts_kick_deg`=0.5° 大步（**不受 `ts_step_deg` 限幅**），下一拍按图像裁决：`acc` 变好≥1px 收货 / `rev` 没动→退回踢前角（溜走量有界）/ `wst` 动了没变好→原地让 P 环重进；全程最多 `ts_kick_max`=4 次（不重置，防时间爆炸）。**停滞但无踢可踢时冻结（零增量）—— 这就是"堵溜走"**。
3. **距离辅助**（`ts_dist_en`，先做灵敏度实验再开）：踢完仍卡 → 底盘**离靶远近**微调 `fDy×ts_dist_px_to_mm` mm。⚠️⚠️ **轴是车体横移（`vChassisMoveCameraLateral`，v_x），不是前后** —— 本车相机**侧看**靶（图像横向 cx 对应车体纵移，见「底盘参与闭环」段），所以"离靶远近"物理上是车体横移；车体前后只是沿靶面滑动、图像 cy 纹丝不动（2026-10-06 首版实现错在这里，用户现场抓到"到Y阶段底盘还是在横移"）。下发段按 `ucMmLateral` 标志分流，CX 辅助仍走 Forward，fMm 清零时标志必须一起清（否则下一次 CX 挪车会被误打到横移轴）。（**带符号，实验标定**：真实射击线上打一发→远离 5~10cm→再打一发，读 dy 位移定符号与大小）→ **立刻回阶段1重修一圈**（远近挪车经光点视差项扰动 dx）→ 再回阶段2；最多 2 次，行程另有 `ts_dist_mm` 闸（外罩 `ts_chassis_mm` 总闸）。⚠️ 黄区余量只有 ~3cm。
4. **宽容收敛**：踢完仍达不到 `ts_conv_y_px` 但 |dy|<旧 conv_px（连续 conv_ticks 拍）→ 照样收货，打 `TGTS grace` 行区分。

⚠️⚠️ **跨阶段 fMm 泄漏（2026-10-06 用户现场抓到并修复）**：`fMm`（挪车量）的常规清零在底盘接管块里，而那块只在阶段1跑——X 阶段最后一次 CX 辅助的 fMm 会跨过 `st=y` 存活，而 Y 阶段每拍都一路落到下发段把它**再执行一次**，症状是"Y 阶段车一直在（沿面）滑"。修复：阶段2分支顶部每拍清 `fMm`/`ucMmLateral`（距离辅助同拍稍后重新 set，当拍下发不受影响）；反方向（距离辅助的 fMm 漏进 X 回修拍）由接管块的门控清零挡住。**挪车量是"本拍"量，绝不允许跨拍/跨阶段存活。**

| `TGTS n=.. dx=.. dy=.. trX=.. trY=..[ mm=..]` | 每 3 拍（≈3Hz，节流） | 过程串。**这是闭环唯一的运行期可见性**（`mm=` 只在开了底盘时出现） |
| `TGTS ch on dx=..px mm=..mm tr=..mm` / `TGTS ch off dx=..px tr=..mm` | **换挡那一刻**（事件，不是每拍） | 「此刻 X 轴归谁」——过程串 3 拍才一条，会漏掉快速换挡 |
| `TGTS ok: dx=..px dy=..px n=..ms` | 收敛 | |
| `TGTS fail: noprog / travel / chasmm / timeout` | 四种放弃 | 见下 |
| `TGTS abort: stop by request n=..ms` | 操作员按的停 | **不蜂鸣**（按停是意图不是故障） |
| `TGTS fin: trX=.. trY=.. ch=..mm r=..px` | 停流后紧跟（六种出口都发，2026-10 加） | 一发收官数值：舵机累计行程（度）/ 底盘累计**指令**行程（mm）/ 最后跟到那颗靶的外圆半径（px，0=从没跟到）。ok/abort 行刻意不带这些量、全收在这——Pi 端「标靶练习」页（GKS_Web `/practice`）按这条行做一发记录的数值骨架 |
| `TGTS fin2: st=x|y ky=.. dm=.. dt=..mm` | 紧跟 fin（只有 `ts_seq_en=1`，2026-10-06 加） | 出口时所在阶段 / 用掉的踢步数 / 距离辅助次数与累计 mm。分析端拿它统计"踢步有没有把 Y 压下去"（GKS_Web 解析器只认 `fin:` 带**冒号**，`fin2:` 自动落进过程 log，不冲突） |

- ⚠️ **过程串是排障的关键**，别删：没有它, 不收敛时只有最后那一拍的偏差, 分不清「**方向反了**」（偏差单调变大）还是「**增益/迟延振荡**」（偏差上下交替）—— 两者处方相反（翻符号 vs 降 `ts_kp_scale`）。
- `noprog` = 偏差**连续 `AIM_NOPROG_TICKS` 拍不下降** → 判「环没起作用」，**提前收手**，别让机械臂一路推到行程闸。判据用 `|dx|+|dy|`，**振荡时上下交替所以不误伤**（振荡由行程闸兜底）。前提是车与靶都静止。⚠️ **底盘接管期间本闸停用**（`ucChasActive != 0` 时不累计）：底盘的"停稳"来自 `fChassisMoveDelay` 阻塞，一拍推进量与 1px 判据不一定比得过，照常累计会误报；底盘阶段兜底交给 `ts_chassis_mm`。
- `chasmm` = 底盘**累计指令行程**超闸。它**单独一条串、单位写 mm**，别和 `travel` 混读。排障含义三选一：方向标反了（`ts_chassis_sign`）/ 比例尺离谱（`ts_chassis_px_to_mm`）/ 轮子被架空或打滑（本闸按**指令值**累加，分不出这三种）。
- ⚠️⚠️ **调试串里的裸数字一律带单位**：早先打成 `travel x=-95.00 y=-14.00`，而 `x=`/`y=` 其实是**像素偏差**不是角度 —— 现场读成"X 轴走了 95°"（上限才 25°），排障方向全跑偏。现在 `dx/dy` 标 `px`、`trX/trY` 是行程的**度**、`tr=`（底盘）是 **mm**。
- ⚠️ `TGTS cfg` 那行**已经贴着 `RPI_DATA_MAX`(64B) 的上限**（约 54~57B），**再加字段就会被从尾部静默截断**（尾巴上正好是 `c=`/`m=`），所以底盘那组只能另起一行。
- ⚠️ **过程串刻意是两套格式串**：`mm=` 只在 `en != 0` 时打；`en=0` 时多打一个 ` mm=0` 就不再是"与加这个功能之前逐字节一致"了，那是本功能的硬约束。

**台架沙盒是预设 12「测试标靶流控」**：调试二维码 → 机械臂待命/识别位姿 → 等 MAIN → [预检] → 流控闭环 → [终验] → 激光。三块链路积木可单独删（删预检 = 直接闭环；删终验 = 收敛即开激光；换连排三块标靶校准 = 复现老方案）。⚠️ **「不动车」只对 `ts_chassis_en=0` 成立**：开了之后它会**前后走**。更要当心预设 12 里那块 `STEP_TEST_LOOP_WAIT` 会把这一步**反复执行**（每轮之间等 MAIN），开了开关就是「每按一次 MAIN 往一个方向挪几毫米」—— 架起来轮子离地再试。

> **默认构建下 `STEP_TARGET_SERVO_WAIT` 是会动车的**（|dx| 落进门限后用位置模式前后进给）——

**动机**：舵机6 颗粒度不够 + 有齿轮回差，细调段落点常在一环外、且**左右来回跳**（极限环）。**做法**：`|dx|` 落进 `ts_chassis_px` 以内后**舵机6 让位**（零增量软保持），改由**底盘位置模式小步"前后"进给**继续闭环；画面纵向（图像 cy）全程归舵机3。

⚠️⚠️ **底盘那一路走的是"前后"不是"左右"**（2026-09-27 实现时踩过并修正）：本车**相机相对车体装了 90°** —— 证据是 `BALL_XY_SWAP` / `HOSTAGE_XY_SWAP` / `TARGET_ALIGN_XY_SWAP` 三个默认**全是 1**。于是**图像横向 cx 对应车体纵移**；色球对位是现成例子（`app_rpi.c` 的 `ball_xy_swap=1`：**横移 ← usCy、纵移 ← usCx**），所以本组喂 `vChassisMoveCameraForward`（`v_y` / `AXIS_Y`）。❌ **用 `vChassisMoveCameraLateral`（`v_x`）会去改图像的 `cy`** —— 轴用错，现象是「**车在动、但偏差不降**」，极易被误诊成「符号反了」然后一路去翻 `ts_chassis_sign`。**别再"顺手"改回 Lateral。**

**新增 5 个运行时量**（蓝牙 Tab「标靶流控」组，断电回 `app_config.h` 的 `TARGET_SERVO_CHASSIS_*`）：

| 参数 | 单位 | 默认 | 作用 |
|---|---|---|---|
| `ts_chassis_en` | — | `0`（出厂） | 总开关。**0 = 整段逐字节等同旧行为** |
| `ts_chassis_px` | px | `20.0f` | 接管门限（退出滞环 = ×1.5） |
| `ts_chassis_px_to_mm` | mm/px | `0.34f` | 前后比例尺（**图像 cx px → 车前后 mm**）。初值同 `BALL_PX_TO_MM_X` —— 那才是"cx→纵移"那把尺；**不是** `ta_px_to_mm_x`（它在 `ta_xy_swap=1` 下配的是 cy）。**只影响收敛速度与是否过冲，不影响终点** |
| `ts_chassis_sign` | ±1 | `+1.0f` | 前后方向。初值由 `BALL_FWD_SIGN` 等效换算而来（cx→纵移的等效符号 = 它取反），**不是**照 `ta_side_sign`（那是 cy→横移的符号，与本法无关） |
| `ts_chassis_mm` | mm | `40.0f` | 累计行程闸（**安全夹**，按**指令值**累加） |

⚠️ **为什么是位置模式而不是速度模式**（选型理由，别改回去）：速度模式 `usVel` 是 **`uint16_t` 整数 RPM**（`emm_v5_device.c`），最小 **1 rpm = 5.079 mm/s** = **3.0 px/拍**（按 0.34mm/px），是死区 `ts_conv_px`(4px) 的 **75%** —— 收紧死区（本功能动机）就必跨过死区 → **永久极限环**（"一直超时"，易误诊成"增益不对"）。位置模式量化 **1 脉冲 = 1/10.5 mm ≈ 0.095 mm ≈ 0.28 px**，细 10 倍，**死区随便收紧**。另：位置模式**自终止**，故本步**任何出口都不发停车指令**；`fChassisMoveDelay` 的阻塞等待**就是"停稳段"**。

⚠️ **代价：底盘那一拍实际耗时 ≈ `ts_ctrl_ms` + 平移阻塞(≈100~300ms) ≈ 2× 名义值**，而 `ulElapsed` 只按名义节拍累加 —— 开了开关就得给积木的 `I(0)` 留 ~2× 余量，否则会被误诊成超时。

⚠️ **换挡有迟滞（退门限 = 门限 × `AIM_CHAS_HYST_PCT/100` = 1.5 倍）+ 2 拍去抖**：判据是 `|dx|` 与门限比大小，单帧噪声就能让它来回翻。⚠️ **不变式 `ts_chassis_px` > `ts_conv_px`**，否则接管带落在死区里、底盘没机会接管（表现"开了开关却从没见 `TGTS ch on`"）。违反了固件会打 `TGTS warn: chassis_px <= conv_px`。

⚠️ **标定顺序**：**先定方向，再定比例尺**。
- `ts_chassis_sign` 看方向 —— 车摆偏进接管带，看 `TGTS n=...` 的 `dx`：**单调变大 = 符号反了**（把 `1` ⇄ `-1` 翻过来）；**上下小幅交替 = 比例尺问题**，不是符号。两现象处方相反，别混着调。
- `ts_chassis_px_to_mm` 看一步走多少 —— **过冲振荡就调小、收敛太慢就调大**；最后拿 `ts_chassis_mm` 收行程。
⚠️ **复用「标靶对位」的 `ta_align_accel`/`ta_align_speed` 作为行走速度/加速度**。⚠️ **速度模式/位置模式互斥**（`app_chassis.c:472` 那条）：本步全程只发位置指令，**别顺手加一条 `vChassisMove(0,0,0)` 收尾**，那会主动中止在飞的位置移动。

⚠️ **坏味道**：`ts_chassis_mm` 是**意图行程**不是实测里程 —— 无 EMM 应答解析（`app_motor.c` 回调传 NULL），轮子打滑/架空也照样涨，失败**像控制问题、其实是机械问题**；只能当安全夹，不能当里程计。

⚠️ 标定前先跑**台架安全路径**：车架起、轮子离地 → 勾开关 → 跑预设 12 → ① `TGTS chcfg` / `ch on` 会打；② **停止键必须在一拍内退出**（见下）；③ 死区/舵机阶段不该有 200ms 空等。

⚠️ 底盘**前后进给会改变车与靶的距离**（横向对位不会）—— **别在依赖「车停在某个固定位姿」的段落之后接这一步**；架起来试也要想轮子离地后"走了多少"与实车不一致（`fChassisMoveDelay` 按脉冲当量估时间）。

### ⚠️ 中止位（2026-09 补，**别再删**）

`ucRpiTargetServo` 的闭环循环原本是**全工程唯一漏掉中止位检查**的「等外部事件的循环」（另 10 处都有）；兜底时只是"停不下来"，但加了底盘运动就升级成**安全问题**：按了停止键、舵机还在动、车还在走。

⚠️ **位置必须在循环体最前面、新鲜度判定之前**：下面那条 Stale 分支会 `continue` —— 放在它后面的话，**链路一断（恰恰是最想按停的时刻）本循环就再也看不到中止位**。⚠️ 中止走 `break` 到唯一出口（所以要发 `"8"` 停流），**不蜂鸣**（按停是操作员意图不是故障），且必须排在 timeout 兜底**之前** —— 否则会掉进 `TGTS fail: timeout`，给排障一个错误归因。

## 平移射靶（激光固定在底盘：STEP_TARGET_SHOOT_WAIT → ucRpiTargetShootAlign，2026-10-07 加）

### ⚠️⚠️ 优先用 pi(树莓派 CSI)摄像头看靶（2026-10-16 加，**出厂值下惰性**）

**为什么**：主摄 `/dev/camera_main` 装在**机械臂**上 —— 臂的位姿与残余振动会让**瞄准列**漂（每局的对准点不一样）；树莓派 CSI 那颗（`camera_picam.py`：libcamera / `rpicam-vid` 出 MJPEG，本机 OV5647）**固定在底盘上**，几何稳定。于是本步优先用它看靶，它不行时**自动退回主摄**那套老方案。

**链路（任务码不变，只多带一个标志）**：

| 谁 | 什么 |
|---|---|
| 单片机→Pi | `"6,<ms>,<pi>"` 粗调 / `"7,0,<pi>"` 起流 / `"C,<uses>,<pi>"` 预热（`<pi>`: 1=优先 CSI）。**标志为 0 时整段省略** ⇒ "只用主摄"时线上与改造前**一字不差** |
| Pi→单片机 | 回帧 `status` 的 **bit7** = 这一帧实际来自 CSI（`bit0` 仍是成功位，所以三处 `status == 1u` 的消费方一字未改）。**帧长/布局没变** —— 挤在 status 里是刻意的：加字节会让**老单片机把目标数组读错位**（静默错值），而挤位只会让老固件把 pi 成功判成失败（**响亮、不动车**，安全的退化方向）。见 `app_rpi.h::RPI_TGT_ST_*` |
| 谁来兜底 | **Pi 内部**（`tasks/_target*.py`）：CSI 打不开/被 GKS_Web 预览占着/看不到靶/中途掉帧 → 整条改用主摄重跑；流的 cam 位**每帧**跟着变 |
| 谁选瞄准列 | **单片机**（它才知道用了哪把尺）：每帧按 bit7 选 `tc_cx_aim_pi` / `tc_cx_aim`；精调环**每拍**重读（中途回落主摄也跟得上） |

- **分工（2026-10-18 定案）：粗调固定主摄、细调走 pi**。
  · 粗调（`"6"`）**不给 pi 标志**（`ucTargetScanOnce(..., 0u, 0u)`）：它的位移是
    `偏差px ÷ tc_gap_px × tc_gap_mm`，而 `tc_gap_px` 只有主摄那一把（150mm ↔ 289px ≈
    1.9px/mm）；pi 满视场在同一距离是 ≈3.8px/mm（靶 r 95→190px，正好两倍）⇒ 用 pi 会算出
    **约两倍**的位移。加上 pi 视场窄（三颗排开常只框到 1~2 颗）—— 粗调没理由用它。
  · 细调（`"7"`）**优先 pi**（`tc_use_picam=1`）：闭环只吃"每拍偏差 × `tc_px_to_mm`"，
    px/mm 大反而让 1px 对应更小的一步；起不来/掉帧由 Pi **整条改用主摄**重跑，每帧 bit7
    决定本端换哪把瞄准尺 —— **"pi 不行就粗细都主"的老方案自动成立**，不需要新协议。
  · 唯一的代价：细调起步白等 `PICAM_STREAM_UP_S=3s` 才退回。**预热**能消掉它 ——
    `STEP_RPI_WARM_CAM` 的 **`WARM_CAM_MAIN_PI`**（2026-10-18 加，一条积木预热两颗；
    `vRpiWarmCamera` 背靠背发 `"C,<uses>"` + `"C,<uses>,1"`），排在离射靶步
    **`uses × 15s` 以内**（隔一段行驶+巡线常 >15s ⇒ 给 `uses=2~3`）。

- **只分瞄准列/行这一对**（两台相对位置不同）；`tc_gap_px`/`tc_px_to_mm`/`tc_sign`/`tc_db_mm` 等**共用**。⚠️ 因为粗调固定主摄，**不需要再给 pi 开一条格距**（那是"粗调也用 pi"才要的账）；要动的是精调比例 `tc_px_to_mm`/`tc_conv_px`（随分辨率变）。
- **半径门已按相机各一套**（`AIM_R_TARGET_PI_MIN/MAX_PX`，`app_rpi.c`，**编译期常量**，同 `AIM_*` 那组的既有纪律——**别做成蓝牙运时量**）。初值 = 与主摄那对相同（先别拦）；CSI 视野/焦距不同 ⇒ r 可能整体缩放，被拒的症状是 `SHOT fail: color N bad radius` / `warn: color N r=..px rejected`，**看着像 2026-10-08 那个"背景同色物抢靶"的老病**，别误诊。
- **Pi 侧那条路**：`camera_picam.py` 里有 `PICAM` 持有器（`warm()` 非阻塞起流 + 丢前 `PICAM_WARM_FRAMES` 帧等 AE/AWB 收敛 + 空闲 `PICAM_IDLE_TIMEOUT_S` 自动关，看门狗 `picam_watchdog` 由 `main.py` 起）。**不在 `camera_lease` 里**（那单槽会收一颗放另一颗）⇒ **CSI 与主摄可以同时热着**（`WARM_CAM_MAIN_PI` 就靠这一条）。分辨率取 **2592×1944**（`tc_*_aim_pi` 的 0~2592/0~1944 钳位才成立）。
- ⚠️ **AWB 是这条路的头号嫌疑人**：色识别是 HSV 阈值，主摄当年正因 AWB 漂移才被固定 6500K（见「看路」那节）。CSI 走 `config.PICAM_AWB_MODE` / `PICAM_AWB_GAINS`（默认 auto/空）；靶色飘先动它，别去改 `TARGET_*` 阈值（那会连带改坏主摄）。
- ⚠️ **GKS_Web 的 pi 预览是另一个进程的 `rpicam-vid`**（libcamera 独占）⇒ 有人开着预览时 CSI 这条会起流失败（会被吞掉并**退回主摄**，本端只看到 `shoot_cam` 一直是 0）。**跑之前先关掉那个预览。**
- ⚠️ **部署顺序 = 先 Pi 后固件**：老 Pi 收到三字段形状会**响亮拒收**（本步超时失败，不会静默跑错相机）；老固件只发老形状，两边照旧。
- **遥测/判读**：蓝牙「平移射靶」组新增只读 **`shoot_cam`**（0 主摄 / 1 pi，每拍跟着回帧走）；日志新增 `SHOT cam: fine_pi=.. a_pi=.. g_px=..`（只说明**细调**那股流优先谁 —— 2026-10-18 起粗调固定主摄，不再看这个位）、`SHOT cam: now=main|pi`（相机**变了**那一刻一条）与 `SHOT fin: ... c=`（收官时的相机）；`SHOT meas:` 尾部多一个 `c=`。⚠️ **没往 `SHOT cfg2` 加字段**（那行贴着 64B 静默截断线）。
- ⚠️ **保持档的起流自愈（`AIM_HOLD_REVIVE_MS` 那次重发 `"7"`）必须带同一个 pi 标志**（`vRpiSendTaskCmdFlag`）—— 否则 Pi 侧 12s 让流自己退之后，重发会把环悄悄切回主摄，而瞄准列还是 CSI 那一把（静默跑偏）。
- ⚠️ **相机变了只换瞄准列，不重置行程闸**（两种档都不重置）：`fTravel` 夹的是"这一步真走了多少 mm"的安全量，回落后重置等于白送一倍。保持档下由"按一格"来重置（那是操作员的明确意图）。

## 射靶测试（OLED 保持式平移射靶：`STEP_TARGET_SHOOT_HOLD_WAIT` → `ucRpiTargetShootHold`，2026-10-09 加）

**要解决的问题**：`tc_cx_aim`（瞄准列）**没法从日志里标** —— 每一发都收敛到它（`SHOT ok: d=..px`
是恒真的），"打没打中"只有**真开一炮看光点**才知道。所以给一个"车一直咬住瞄准列"的常驻模式，
把「按一格 → 车跟到新目标 → 开一炮看偏哪 → 再按一格」这个闭环做出来。

```
OLED 第 5 页「射靶测试」第 1 项(开始) ──SCRIPT_REQ_TASK(预设 34)──►
  [臂没展开过就先阻塞播 ARM_ACT_1 待命] → 预设 34: ARM_PLAY_WAIT(ARM_ACT_16) →
  STEP_TARGET_SHOOT_HOLD_WAIT(永不结束) ── "6"粗调 → "7"起流 → 保持环 ──►
  第 1 项(停止) → vScriptAbort() → 保持环查中止位 → 发 "8" 停流、停车、退出
```

### 界面（一行 128px = 8 汉字 = 16 ASCII；4 项占满一屏）

| 行 | 内容 |
|---|---|
| 1 | `开始射靶测试` / 运行期**七态**：`停止射靶 粗调` / `运动中` / `OK!` / `冻结` / `无目标` / `无信号` |
| 2 | `激光:开 d=-3px` |
| 3 | `瞄准列:985` ← `tc_cx_aim`（swap=1 本车）/ `tc_cy_aim`（swap=0），±5px。⚠️ 2026-10-16 起**跟着"当前在用哪台相机"走**：射靶优先 pi(CSI) 时这一行读写的是 `tc_cx_aim_pi`/`tc_cy_aim_pi`（判据 `ucGetShootCam()`，见 `app_oled.c::fOledShootAimGet/vOledShootAimSet`）—— 调错那一对的现象正是"按了一格、车不动"（保持环读的是另一把尺） |
| 4 | `收敛阈值:4.5` ← `tc_conv_px`，±0.5px，钳 [2.0, 30.0] |

- ⚠️ **步进 5px 是刻意的**：必须 **>** `tc_conv_px` 默认 4.5 —— 否则按一下还在死区里、车纹丝不动，
  操作员会以为"调了没用"。（2px 那种步进比流帧检测噪声带 ±2px 还小，在它上面做分辨率没意义。）
  想更细就把第 4 项收到 3px（噪声带下沿），那时 5px 一按 ≈ 1.6mm 的落点分辨率。
- ⚠️ 后四个标签回答同一个问题 —— **车为什么不动**：冻结（撞行程闸/noprog，按一格可重试）/
  无目标（丢靶或被半径门全剔除）/ 无信号（帧计数停涨 = Pi 没在发）。少了它们，屏上会停在最后一个
  `OK!` 或某个陈旧 d 上，看着像"已经对准了、只是车没动"。
- ⚠️ `粗调` 那一态**单列**是安全考虑：那一段车随时会走 150mm 级别的纵移，而此刻还没开始测偏差
  （d 还是 0）—— 显示成"停止射靶"（=已稳住）是会误导的。
- `d=` **不上第 1 行**（用户定）：拼在「激光」那行的尾巴上，由 `vOledMenuDraw` 里一条
  **按语义挂**的分支拼（"这张表里有 `OLED_ACT_SHOOT_TEST` 才拼"，照抄「让出成功!」横幅的写法）
  —— 所以第 3 页那张表的激光行不带它。`激光:开 d=-3px` = 112px。
  ⚠️ 为此把**共享**的激光标签从 `开关激光:开/关` 压成 `激光:开/关`（省 32px；第 3 页跟着变短、
  信息不变）—— 不压的话 `开关激光:开 d=-3px` = 144px，会被**从尾部静默截断**。

### ⚠️ 保持档（`ucHold=1`）改了什么

1. **永不因超时/收敛/noprog/行程闸退出** —— 只有中止位能停
   （`while ((ucHold != 0u) || (ulElapsed < ulTimeoutMs))`）。
   ⚠️ 出口那条 `if (ucOk != 0u)` 加了 `&& (ucHold == 0u)`：保持档的"收敛"只是"现在稳住了"、
   **不是退出条件** —— 不挡的话**按「停止」会被报成 `SHOT ok`**（把"按停"说成"成功"）。
2. **每拍重读**瞄准常数与收敛阈值 → 按一格车就跟着走到新目标。
3. **瞄准常数一变就重置**行程闸 / noprog / 收敛计数 / `fPrevAbs`（"每次微调一套新预算"），
   并打一条 `SHOT hold: aim->985px`。不然 150mm 的闸会被一次次微调累计用光、几分钟后必然冻结。
4. **撞闸 / noprog 不退出**：发 0 停车 + **冻结** + 一条 `SHOT hold: ..frozen`；按一格即自恢复
   （冻结态也靠"按一格"那一拍复位）。
5. **起流自愈（必需，不是优化）**：帧停涨超 2×`ts_stale_ms` 就限速重发 `"7"`（最快 5s 一次，
   打 `SHOT hold: stream stale, re-arm`）。
   ⚠️ **根因在 Pi 侧**：`TARGET_STREAM_MAX_S = 12.0` —— 流线程 **12 秒自己退出**（安全阀：
   防 "8" 丢失后一直占着相机），而保持环**不判超时**，没有这条自愈就是"冻在那儿永不自愈"。
   ⚠️ `"7"` **不在 `handler.py::_MS_COMMANDS` 里** → 没法在指令里要更长的流；想少几次自愈就去
   Pi 的「设置参数」页把 `TARGET_STREAM_MAX_S` 调大（那是运行时覆盖，改完不用动源码）。
6. **过程串改节流**：死区外每拍、带内 ~2s 一条（`AIM_HOLD_TRACE_TICKS`）。
   "永不结束"必然带来日志撑爆的问题 —— 分钟级的带内停留就是几百条 `SHOT n=`。
7. **`keep_res` 恒 0**：保持测试绝不记残留（挂着会被后面任何勾"叠加残留"的世界系平移误吃）。
   所以新积木**没有** `keep_res` 参数。
8. **进门自动预热 pi（2026-10-18 加，`ucRpiTargetShootHold` 开头）**：这一档前面没有路线能排
   预热积木，而细调那股 `"7"` 只等 `PICAM_STREAM_UP_S`(3s) 起流，CSI 冷启动正好卡在边界上 ⇒
   **同一次台架测试，这次按跑 pi、下次按跑主摄**（瞄准列也跟着换台，第 3 行跟着 `ucGetShootCam()`
   显示的是另一对 —— 于是"按一格车不动"看着像坏了）。现在进门先发一条 `"C,2,1"`（只发不等），
   粗调(固定主摄)+等停稳那 ~2~3s 正好让它起好流 ⇒ **每次按都稳定落在一台相机上**；pi 被占着/
   起不来 → 稳定退回主摄（= 老方案）。判据与 ②'' 同源：`tc_use_picam=0` 或 `tc_cx_aim_pi≤0` 不预热。
   · ⚠️ 想**只测主摄那把尺**（标 `tc_cx_aim`）：临时把 `tc_use_picam=0` —— 这时粗细都主、
     也完全不碰 CSI（网页预览可同时开着），标定条件最干净；标 `tc_cx_aim_pi` 时再置 1。
   · ⚠️ 反过来：`tc_use_picam=1` 时按「开始」会占住 CSI 十几秒 —— 想接着用网页「测试pi」
     就先按「停止」（保持环退出时会发 `"8"`，流停 → 15s 空闲后释放）。
