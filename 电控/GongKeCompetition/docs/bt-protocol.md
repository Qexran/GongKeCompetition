## ⚠️ 新增蓝牙指令 / Beam 参数（`app_bt.c` 的 `$B` 协议）

宿主（PC）协议，与树莓派帧协议（`app_rpi.c`）无关；**Pi 端不用改**，别照它改 `handler.py::_COMMANDS`。

- **加一条 `$B` 指令**：改 `Application/app_bt.c` 分发（`bt_handle_line`）+ 新处理函数，按需加 `tools/webconsole/bt_link.py` 方法、`server.py::run_bt_action` 分支、本文件一行。**响应须以 `$B,OK` 或 `$B,ERR,<CODE>` 收尾**（PC 端靠它配对请求/响应）；新错误码同步 `bt_link._err_text()` 中文翻译表。
- **加一个可蓝牙读写的 Beam 量**：`app_beam.c/.h` 加 getter/setter 并**同步进 `s_astBeamParam[]` 注册表**（`app_beam.c`）——漏了不报错，只是「蓝牙」Tab 看不到；非 float 加转换 thunk（宏 `BEAM_ADAPT_*`）。
  ⚠️ **`ucTakeXxx` 一次性信号绝对不能进表**：读会清零、打断消费者（`ucTakeMenuConfirm`/`ucTakeYawFresh`/`ucTakeRpiFrameReady`/`ucTakeHandshakeSeen`/`ucTakeHostageReady`/`ucTakeColorReady`）；表内字段禁止 `,` 与 `\n`（`$B` 无转义，一个逗号就把记录串行）。
  ⚠️ **`fMin`/`fMax` 别填 <0.01**：上下界经 `bt_fmt_f2` 报名（只**两位小数**），填 0.001 报出去 = `0.00`，界面成"下界 0"、滑块能拉到 0 —— **真会放过非法值**（`ucBeamApply` 的 `fMin` 是设备侧 float、钳位对）。改 `bt_fmt_f2` 小数位会动全部 120 条参数报文格式，别为单个参数改。
  - ⚠️ 条数**直接影响 `$B,LIST` 耗时**（2026-09 修正：原「~2.7KB」是 ~40 条时的旧值）：现 **227 条 `$B,P` + 5 条 `$B,J`**（2026-10-16 数 `s_astBeamParam[]`，含本轮「平移射靶」组新增的 `tc_cx_aim_pi`/`tc_cy_aim_pi`/`tc_use_picam`/`shoot_cam`；⚠️ **一直在涨，别照抄，落笔前重新数**）。每行约 78B（UTF-8 每字 3 字节）→ 总线约 **~17KB**、115200 下**线上 ~1.5s**。
  - ⚠️ **`$B,P` 行尾多了一个可选字段**（2026-10 加）：`…,<value>[,<options>]`，`options` 形如 `0=主口那颗|1=副口那颗`，**只有该参数填了 `pcOptions` 才出现** ⇒ 解析必须接受 **12 或 13** 段（`bt_link.parse_param_line`；写成 `!= 13` 会把绝大多数参数判成无效行）。见「姿态传感器」一节末尾。
  - ⚠️ **「会拖抖 vPidTask」这条已不成立**（2026-09 发送改 DMA 环后）：`bt_sendf` 入队即返回，`vBtTask` 只在环满时让出（背压）。仍成立：`$B,LIST` 期间**持有 BT 命令锁 ~850ms**，别人的 `$B` 要排队 → **同一时间只让一人开「蓝牙/机械臂」Tab**。
- 线协议：ASCII、`$B` 前缀、逗号分隔、`\n` 结尾（容忍 `\r`）；浮点用自写的 `bt_fmt_f2`/`bt_parse_float`，**不用 `%f`/`atof`**（避 MicroLib 下 `%f` 输出空白）；`LIST` 多行**逐行发**（`bt_cmd_list` 里那 135 处行间 `vTaskDelay(1)` 是**忙等时代遗留**，2026-09 后只白花 ~130ms，删不删都行 —— 限速由 TX 环满背压负责）。
- 垃圾行（非 `$B,` 开头）→ 固件回一条 `$B,ERR,SYNC`（限速 1 条/秒）让 PC 重发。这**不再**是 DMA 回绕兜底（那个 2026-09 已修）。

### ⚠️ 舵机速度总闸：`ARM_SERVO_MAX_SPEED_DPS`（调参 Tab 可调）

**改「舵机快慢」只改这一个**（`Application/app_config.h`，「调参」Tab，改完重编译）。`vAppArmInit()` 末尾写进 6 舵机 `fSpeed`（°/ms），全臂唯一转速旋钮：

**⚠️ 2026-10 起它是「上电初值」而非唯一真相**：运行时量 = Beam `arm_speed_dps`（蓝牙「机械臂」组可改、**当场下发** 6 舵机）+ 新积木 **`STEP_ARM_SPEED_SET`（舵机速度）**——路线里中途改速度用，瞬时不动车不动臂、**也不掐后台臂序列**（它的意义恰恰是"边播边改"：对正在播放的动作下一拍削峰就按新值，曲线 t 不重置），想让某段动作慢/快就排在那段动作**之前**。30~1000 越界钳位。`vAppArmInit` 现在从 Beam 取值写 fSpeed。⚠️ 这两个量的 setter（`vSetArmSpeedDps`/`vSetArmCurve`）是"**存 + 当场下发**"，与 BALL_* 那批"存起来用时再取"的标定量刻意不同，别"顺手统一"成纯存储（驱动读的是舵机自己的字段，只写 Beam 不生效）。

**⚠️ S 曲线的插值形状也可选了（2026-10 加）**：`ARM_SERVO_CURVE`（调参 Tab，**下拉框**——调参 Tab 现在支持宏备注里的「`选项:0=xx 1=yy`」段渲染下拉，`ARM_SERVO_CURVE` 首用；要给别的参数加下拉照抄这个格式）+ Beam `arm_curve` 运行时量（蓝牙可改，当场生效）。四档：0=五次S（**与加选择前逐字节一致** → 那才是"默认"的意思）／1=三次S（峰速 1.5×，中段更匀）／2=余弦（峰速 1.57×，减速段更长）／3=线性（恒速，实际感觉=fSpeed 削峰后的梯形）。
⚠️ **2026-10-06 审查更正：本机 `app_config.h` 里现值是 `2`（余弦）**，不是 0 —— 那是现场在「调参」Tab 选定的（同样由控制台回写）。别照"默认"两字把它改回 0：那会同时动到已调好的动作手感、**削峰量**与到位耗时（下面那张"受它管的"表与 `ARM_GROUP_WAIT_TIMEOUT_MS` 的推算都按 1.875× 峰值写的，改成余弦后是 1.57×）。全局六轴共用；对**进行中**的动作下一拍就按新曲线算、t 不重置。实现全在 `servo_device.c`（`emServoCurveTdf` + `vServoDeviceSetCurve`，周期执行里按全局曲线算进度形状）。

| 受它管的 | 机制 |
|---|---|
| 拖滑杆（`ms=0` 恒速趋近） | 它**就是**趋近速度（`emServoMode_Smooth` 每 1ms 走 `fSpeed`） |
| S 曲线播放（`$B,PLAY` / `STEP_ARM_PLAY_WAIT` / 组动作） | 它是**削峰上限**：`vServoDevicePeriodExecute` 把每拍变化量夹到 `fSpeed`。五次赫米特中段峰值 `1.875·Δ/时长`，大行程短时长时会明显超出舵机允许转速 |

- **默认 360°/s**：这类 5V 舵机空载约 375~500°/s，默认基本不削峰值、只挡瞬跳；更斯文往下调（200~260 很温和）。
- ⚠️ **必须在所有 `vServoDeviceInit_*` 之后设**（那些 init 会把 `fSpeed` 复位成 `SERVO_DEFAULT_SPEED` = 1000°/s，等于不限速）。
- ⚠️⚠️ 被削速后 S 曲线走完时位置还没到目标，驱动会**切到恒速模式收尾**（而非直接写 `fTargetValue`，后者把削掉的那段凭空跳过 = 没限速；改这段时别把收尾改回去）；**「到位标志」必须把恒速收尾算作"还没到"**（`ucServoIsSmoothStepDone` 判 `emMode == Smooth` 时还要比 |目标−当前|）：它一翻 1，`$B,POS` 的 `done`、组动作等待（`vArmGroupMoveWait`/`vArmSetZhuaShou`）、路线臂步骤、控制台「播放整个序列」全往下走。老写法只看 `emMode != SmoothStep` → **收尾一开始就报完成**，臂还在爬最后几十~上百度的几百毫秒里下一条动作已发出（症状「动作提前播放」、底盘在臂没到位时先动）。**别再按函数名改回「只看模式」**。
- ⚠️ 因此 `ARM_GROUP_WAIT_TIMEOUT_MS` 只是**下界**：`vArmGroupMoveWait` 取它和「全臂最坏行程 ÷ 速度闸 + 余量」的较大者（360° 轴在 100°/s 下走满程要 3.6s，固定 3s 会把正常大行程动作提前放掉）。
- ⚠️ `vServoSetTargetValueSlew()` 在**已到位时不切模式**（保持 Static）——否则每拍一次 JOG 都把完成标志压成「运动中」，PC 侧 `$B,POS` 的 `done` 永远等不到。（副作用: 拖完松手后臂恒速滑行的几十~几百毫秒里 `done` 是 0 —— 诚实。）

### 组动作角度偏移：`ARM_GROUP_OFS_S*`（**蓝牙可调**，台架标定, 2026-09 加）

**症状**：编辑模式里把关节拖到位、记下角度，一进路线（组动作播放）就偏 —— 底座 S6 最明显。
**定性**：拖滑杆走**恒速趋近**、组动作播放走 **S 曲线**（快得多），舵机死区 + 齿轮回差让两种到达方式停在**不同物理位置**。
**处方**：五轴各一个偏移，**下发角 = 动作预设里写的角 + 本值**。

| | |
|---|---|
| 存哪 | Beam `s_afArmGroupOfs[ARM_GROUP_NUM]`（`app_beam.c`），初值 = `app_config.h` 的 `ARM_GROUP_OFS_S1/S2/S3/S4/S6` |
| 怎么调 | 「蓝牙」Tab 的**「臂偏移」**组（`arm_ofs_s1..s4/s6`，°）当场改，零重编译；断电回宏默认值；「调参」Tab 改的是持久默认 |
| 生效点 | `app_arm.c::vArmGroupMoveNoWait()` —— **组动作唯一收口**（`STEP_ARM_GROUP_WAIT/NO_WAIT`、`$B,ARM`、动作预设播放都经它）。一处叠加，避免三处各写一遍漏一处 |
| 生效范围 | 全部组动作；叠加后仍**按静态量程钳位**（宁可少走一点也不越量程） |

⚠️ **刻意不给 `$B,JOG`（拖滑杆）与夹爪吃这个偏移**：编辑模式拖的是**标定基准**，吃偏移就成了「滑杆读数与物理位置互相追着跑」，永远标不准 —— **编辑模式看到的永远是原始角，只有组动作播放才叠加。**
⚠️ 标靶校准（`vArmAimByPixels`）也不吃它（增量式）；这是**单向补偿**（只按标定方向修），若回差是主因，反方向来的动作会过头 —— 那时把回差调小（或统一从同一侧趋近）比继续加偏移有用。

### 机械臂相关指令（2026-09 加）

- `$B,JOG,<0..4>,<角度>[,<ms>]` 的 **`ms` 两种语义**：`ms>0` = 走完整 S 曲线（默认 250，比赛语义）；**`ms=0` = 跟手模式**（机械臂 Tab 拖滑杆）→ `vServoSetTargetValueSlew()`，**恒速趋近**。
  ⚠️ **别用 `payload.get("ms") or 250` 这种写法** —— `0` 被静默换成 250，症状「拖滑杆还是不跟手」，查不出来（`test_bt.py::test_jog_ms_zero_reaches_the_device` 锁这条）。
  ⚠️ S 曲线不能跟手：`vServoSetTargetValueTimed` 每次把 `t` 打回 0，五次赫米特在 `t≈0` 速度近乎 0 —— PC 每 ~50ms 推新目标 = 每次从缓入段重爬。**链路只要 4~6ms，不是瓶颈**；恒速趋近**不重启曲线**，是一阶跟随。
  ⚠️ 也**不要**改回「零时长旁路直接写目标」：舵机会以自身最高速甩过去，太快、砸齿轮。速度由上面那条总闸统一管。
- `$B,ARM,<a0..a4>,<kai>,<deg>`：播放**一个任意位姿**（5 轴同时启 S 曲线 + 夹爪），立即返回。比 5 条 `$B,JOG` 少 4 次往返、也不串行启动；到位用 `$B,POS` 轮询。
- `$B,PLAY,<id>`：让固件播放**已编译的**动作预设整段（含表内 `STEP_DELAY`），**阻塞**到走完。直接调 `vArmPlayWait` —— 与路线里的 `STEP_ARM_PLAY_WAIT` **同一个函数**，是「台架试跑 == 比赛跑路线」唯一的证据链。PC 侧超时 `bt_link.PLAY_TIMEOUT`(15s)，期间**不要**轮询 `$B,POS`（那时它也不应答）。
- 新错误码：`NOACTION`（设备上没有这个动作预设 —— 固件没重编译？）。

### ⚠️ 「启动即返回」的臂序列由 `vArmTask` 推进（并发纪律）

`vArmPlayNoWait` 只**投递**，推进在 `vArmTask`（`app_arm.c`）。投递排进**小待播队列**（深度 4，`app_arm_action.c` 的 `s_apstQueue`）：跑完接着跑下一条（`arm_seq_busy` 全程 1、不掉 0），空了才让出 20ms。`vArmSeqAbort()` 终止当前那条**并清空队列**；**任何新臂指令入口都要先调它** —— `app_script.c` 每条臂步骤之前（**switch 之外**）、`app_bt.c` 的 `JOG`/`GRIP`/`ARM`（`$B,MODE` 不碰舵机，不在此列）。规则「后写者胜 + 新指令显式终止旧序列」→ 无需排表纪律。

**两个投递入口，区别只在「要不要先中止」**（`app_arm_action.h`）：
- `vArmPlayNoWait()` = **后写者胜**：abort（连队列清）再投。路线里那块大积木走这条。
- `ucArmPlayByMode()`（2026-09 加）= 按**预设自标的播放方式**播，**追加、不 abort**：标「启动即返回」→ 入队即返回；标「阻塞到位」→ 入队后**等整条队列跑空**（`c_ucSeqDrain`，10ms 采样、60s 兜底，期间逐拍喂蓝牙编辑看门狗）。排爆抓取 / 反恐任务用它，故阻塞与否由**所选动作**决定；返回 1=正常 / 0=降级（队列满、drain 超时）——**调用方必须把 0 当失败处理**（`[STM-DBG]` 留痕; 不响）。
  ⚠️ 「抓取=启动即返回 + 复位=阻塞到位」这组**整体仍阻塞**（复位等它自己排到那一刻到位，不掐前一条）——想让路线立刻往下走，两条都得标「启动即返回」。
- ⚠️ **代次号 `s_ulSeqGen` 只有 `vArmSeqAbort()` 加一**。投递（含追加）千万别加：泵靠「代次变了就在下一步骤边界退出」响应中止，追加时加一 = 掐断正在跑的那条（症状「抓取只走了几步就跳去复位」）。
- ⚠️ **队列 push / pop / clear 都在临界区**（三方上下文：脚本任务 & vBtTask 投递、泵出队、任何任务 abort 清队），区内只有几条内存指令、**不碰串口**。出队与 `s_pstRunning` 赋值、`vSetArmSeqBusy(1)` 必须**同一临界区** —— 否则露出「队列已空但还没认领」的假空闲窗口，把 drain 提前放行、两条动作抢舵机（随机、难复现）。
- ⚠️ `$B,PLAY` **刻意不跟随**预设播放方式（仍走阻塞的 `vArmPlayWait`）：语义是「播给我看、播完回 ACK」，标「启动即返回」的动作也要完整播一遍才看得出录得对不对。

⚠️ **三个别踩回去的坑**：
1. **别把 `vArmSeqAbort()` 写进 `app_arm.c` 的原语里**（`vArmGroupMoveWait/NoWait`、`vArmSetZhuaShou*`）——后台泵正是经那些原语推进，会自己把自己中止（走一步就停）。
2. **别把 abort 写进 `vScriptRun` 的 case 体第一行** —— 控制台取积木原语名读 case 体**第一个函数调用**，那样积木显示成 `vArmSeqAbort`（`test_bt.py::test_matches_serializer_byte_for_byte` 会拦）。
3. **别把待播队列/`c_ucSeqDrain` 搬进 `app_arm.c` 的原语里**（同上）；也别把「队列满」的兜底写成 `vArmPlayWait` —— 那会静默 abort 掉前面排队的，「按模式播」就废了。
