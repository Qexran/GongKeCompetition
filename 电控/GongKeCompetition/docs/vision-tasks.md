## 相机预热（`"B"` 预热扫码相机 / `"C"` 预热主摄，2026-09 加）

**问题**：Pi 开一次相机实测 **≈1.5~2s**（`camera.py::CameraManager.open()`：15 帧预热 + V4L2 协商 + 曝光应用；⚠️ 2026-09-26 复测值，**比早先写的 1.3s 大**，排表按 2s 算）；**解码很便宜**（扫码 **0.56s**）。该开销也写进人质对位的超时预算（路线表 7500 = `HOSTAGE_TIMEOUT(6.0s) + **摄像头打开(~1s)** ≈ 7.1s`），逼近 8s 判死线。

**处方**：让 Pi 在**车移动 / 巡线的那几秒**先开好相机。两条指令都是 **fire-and-forget（只发不等，无结果帧）**：

| 枚举 | ASCII | 用途 |
|---|---|---|
| `RPI_TASK_WARM_QR` = 15 | `"B"` | 预热扫码相机 `/dev/camera_Qr` |
| `RPI_TASK_WARM_MAIN` = 16 | `"C"` | 预热主摄 `/dev/camera_main` |

⚠️ 2026-09 起**不再用 `STEP_RPI_SEND_TASK` 挑这两个任务码**（老路仍保留，老路线不炸），改用专门积木（原语 `vRpiWarmCamera()`）：

| 积木 | 参数 | 行为 |
|---|---|---|
| `STEP_RPI_WARM_CAM`（预热摄像头） | `cam` = 哪台（`WARM_CAM_MAIN` 主摄 / `WARM_CAM_QR` 扫码副摄 / **`WARM_CAM_PI` pi摄像头** / **`WARM_CAM_MAIN_PI` 主摄+pi**）<br>`uses` = **使用次数** | `uses ≤ 1` → 发**裸** `"B"`/`"C"`（线上与老写法逐字节相同）；`uses ≥ 2` → 发 `"C,2"`，Pi 把相机租约的空闲窗口放宽成 **`uses` × LEASE/PICAM 空闲超时** |

⚠️ **`WARM_CAM_PI`（2026-10-16 加）不占新任务码**：它复用识别主摄那条 `"C"`，只多带一个 `is_use_picam` → 线上是 `"C,1,1"`（`uses<2` 时第二字段补 1）。Pi 侧它走的是 `camera_picam.PICAM`（**不在 `camera_lease` 里**）⇒ **CSI 与主摄可以同时热着**，所以"预热 pi + 随后带 pi 标志的识别"与"预热主摄 + 主摄识别"两条路互不干扰。老 Pi 收到三字段形状会**响亮拒收**（预热静默失效、退回现开现扫，不坏）。

⚠️ **`WARM_CAM_MAIN_PI`（2026-10-18 加）= 一条积木预热两颗**：`vRpiWarmCamera` 背靠背发两条帧（`"C,<uses>"` + `"C,<uses>,1"`，都是只发不等，串口接收线程不阻塞），`uses` 对两颗**各算各的窗口**。用途 = 「平移射靶」定案的**粗主/细 pi**：CSI 冷启动 ~3s 而细调起流只等 `PICAM_STREAM_UP_S=3s`，必须提前热好；主摄也一起热着省掉粗调那 ~1.3s。
· 排法：放在**离射靶步 `uses × 15s` 以内**（map.c 里从"预热"到"平移射靶"隔着 ~1.7m 行驶 + 两次巡线收敛，`uses=1` 的 15s 常常不够 ⇒ 用 **`uses=2` (30s)**）。
· ⚠️ 主摄那格窗口别开太大：主摄同时还是**网页预览**要抢的那台（跨进程，控制端会先让位再重试，~0.3s）。
· ⚠️ 预热是**进程内**的：`main.py` 一重启，热着的流就没了（`gks-web.service` 重启同理）；链路没起来时预热帧会被丢（只发不等）。

**「使用次数」的作用**：Pi 侧任务用完相机**并不关它**（`release_camera(LeaseHandle)` 只 `touch()`），相机留到「最后一次使用之后 `LEASE_IDLE_TIMEOUT_S`(15s)」才被空闲看门狗释放 —— 复用的就是这个 15s 窗口：`uses=1`（或 0、不填）→ 窗口 15s，与加参数前**一字不差**；`uses=2` → 到第二个任务用完之前**每个**间隔都有 30s 宽限；倍数用到声明次数用完才回 15s。

**预热预算日志（2026-11-02 加，用来「跑着看」安排合不合适）**——Pi `camera_lease.py` 四处，全部只在**排了计划或 `uses>1`** 时打印（普通单次预热照旧安静）：

| 时机 | 日志 | 怎么读 |
|---|---|---|
| 预热登记/续期 | `[INFO] 预热登记: （预热 5 次已用 0 剩 5，计划=[road, road, hostage, 默认, 默认]）` | 确认固件那条 `"W"/"C,N"` 真的按你要的计划到了 Pi（没到 → 后面一条都不会有） |
| 每次任务命中 | `[INFO] 预热使用 2/5（档位 road, 剩 3 次）` | **实际消耗**。任务数比 `uses` 多 → 会看到 `剩 0` 之后不再打印，随后出现 `冷开相机接管为租约`（= 预付次数不够） |
| 空档提前切档 | `[INFO] 预热档位计划: 空档里提前切到第 3/5 次使用的档位 hostage（预热还剩 2 次）` | 计划在按序推进；没有这行 = 下一次任务抢在切换之前、计划会作废（日志另有 `预热档位计划作废`） |
| 空闲释放 | `[INFO] 相机租约空闲超过 75s, 自动释放（预热 5 次只用了 2 次、还剩 3 次没轮到 → 排多了/后续任务没跟上）` | **最重要的一条**: 剩得多 = `uses` 排大了（相机被白占）；`剩 0` = 刚好用满；随后紧跟 `冷开` = 排小了 |

- ⚠️ 判据是 **Pi 日志**（`logs/run_<ts>/log.txt` 或 GKS_Web 日志页），不是 OLED/蓝牙。
- ⚠️ 只有 `uses>1` 或带档位计划才会出现上面这些行；`uses=1` 的普通预热**刻意不打印**（否则每个视觉任务刷一行）。

**排表规则**：预热排在**动作/巡线之前** ——

```c
SCRIPT_STEP_I2  (STEP_RPI_WARM_CAM,       "预热摄像头: 主摄", WARM_CAM_MAIN, 2u),  // vRpiWarmCamera()
SCRIPT_STEP_F1I2(STEP_LINE_CONVERGE_WAIT, "巡线收敛", -180.0f, 800u, 0u),   // 末尾 0u = src: 0 相机
SCRIPT_STEP_I2  (STEP_HOSTAGE_ALIGN_WAIT, "人质对位: 识别→", 8000u, 1u),
```

- ⚠️ **巡线那一步是白送的窗口**：`tasks/_line.py` **完全不碰树莓派主摄**（巡线是 OpenMV 经**自己那路 USB 串口**做的），每个 `STEP_LINE_CONVERGE_WAIT` 都是整段空窗；两者只抢 **COORD 串口通道**。
- ⚠️ **预热步骤可以省略**：没排就退回「现开现扫」，只慢 ~2s。
- ⚠️⚠️ **「预热了」≠「省到时间」，判据是「指令与使用点的间隔 ≥ ~2s」**（2026-09-26 踩过）：间隔不够 2s **等于白预热**（Pi 侧 `acquire()` 原地等预热落地，总耗时 ≈ 冷开）。预热排在**一段会花时间的步骤之前**（移动 / 巡线 / 阻塞摆臂）；也别隔太远 —— `LEASE_IDLE_TIMEOUT_S`=15s **要乘 `uses`**，超了相机会被自动释放。
- ⚠️ **当前路线里预热排在哪**（改路线时别顺掉）：预设 1 第 3 步 = 预热(扫码相机, `uses=1`)，窗口「斜线到出发区中央」+「前进准备扫码」；预设 1 主摄重扫（`ARM_ACT_22` / `ARM_ACT_19` 阻塞摆臂）**之前**各一块预热(主摄)，加看路/小球对位/激光共 **6 处主摄**、**一律 `uses=1`**，都排在**摆臂之前**。
  - ⚠️ **`uses` 刻意先都填 1**（与改造前逐字节相同、零风险）：台上量出哪几处间隔真超 15s 再往上加 —— 窗口越宽，脚本没走到那一步时相机被白占越久。
- ⚠️ **OLED 三条任务预设（14/15/16）第一步就是视觉步骤，预设内部没有窗口** —— 窗口在它们前面的「执行任务」机械臂待命展开（阻塞好几秒），所以 `"C"` 在 `app_script.c` 的 `SCRIPT_REQ_TASK` 分支里、`vArmPlayWait()` **之前**发。⚠️ **展开窗只在 `ucGetArmDeployed()==0`（本上电周期第一次）时存在**。
  - ⚠️⚠️ **预设 16（OLED人质抓取）表首必须是阻塞的 `STEP_ARM_PLAY_WAIT`**：它没有展开窗，唯一窗口就是首步摆臂；原是 `STEP_ARM_PLAY_NO_WAIT` → 实测「预热与不预热耗时几乎一样」。预设 15 首步本就是 WAIT。
- ⚠️ **`"B"`/`"C"` 不在 `handle()` 里那个「先停巡线/靶标流」的元组里**（与 `"1"/"4"/"5"/"6"/"A"` 不同）：只开相机、不发结果帧，不撞 COORD 通道，且恰排在巡线**之前**，停巡线是错的。

**四个别踩回去的点**（细节在 Pi 仓库 `camera_lease.py` 顶部）：
1. **预开但没人读的 `VideoCapture` 会返回陈帧**（V4L2 环形缓冲，没设 `CAP_PROP_BUFFERSIZE`、默认 4 帧）：开着不读、驱动填满队列后丢新帧，于是「提前开好、等车停了一抓」拿到的是**转弯时拍的画面**且**不报错** —— 预热必须是「后台线程持续读 + 只留最新一帧」。
2. **空闲看门狗不能删**：发了预热却没跟进识别（路线被改 / 脚本被中止）时，没它就**永久占着相机**（Web 预览从此打不开且无人报错）；超时自动释放（`LEASE_IDLE_TIMEOUT_S`）是唯一安全阀，纪律同 `BT_EDIT_IDLE_TIMEOUT_MS`。⚠️ **`uses` 正是把这道阀按比例放宽的东西**（窗口变成 `uses × 15s`）：脚本发了预热却没走到那几次识别时，相机被白占也翻 `uses` 倍 —— 所以 `uses` 有上限（`_clamp_uses` 夹在 `config.LEASE_USES_MAX`，默认 10 → 最多 150s），且租约带没用完的预算被释放时 Pi 打一行 `相机租约已释放（预热次数预算还剩 N 档没用完）`。
3. **主摄有多个曝光档**（人质 `1/350`、色球/标靶 `3/166`，同一台设备）：按 main 档预热后人质进来，租约要**在已开设备上就地重设曝光**并丢掉收敛期那几帧，不重开设备。
4. ⚠️ **预热会牺牲租约里的另一台相机**：`LEASE.warm()` 发现目标不是当前租约那台时先 `release_now()` —— 所以**别在靶标流（`"7"`）运行期间发预热**（会掐断正在跑的主摄流），放在「离使用点近、且另一台相机没人用」的位置。

**与任务侧「零侵入」**：`tasks/*.py` 只把 `open_camera(...)`→`acquire_camera(...)`、`CameraManager.release(cap)`→`release_camera(cap)`，**扫描循环一行没改**。

**⚠️ 跨进程抢相机：`/abort` 兜底（2026-09-26 修，**这是「随机打开失败」的主因**）**：占着相机的网页推流跑在**另一个进程**（`gks-web.service`，端口 9000，`GKS_Web/app.py::_streams`），而 `handler._stop_main_stream()` 走的 `camera_web._stop_stream` 注册表在 `main.py` 进程里**是空的** → **空操作**。于是「谁先开到设备谁赢」：预热失败（`[WARN]`）→ 识别任务 5×0.3s 重试也抢不回来 → `[ERROR] 无法打开摄像头索引 N`。现在 Pi 侧 `camera_lease.py` 的 `_open_with_abort_retry()`：**open 失败就打 `http://127.0.0.1:9000/abort?cam=main|qr` 请 GKS_Web 停推流，等 0.3s 再试一次**；`_open_and_serve`（预热）与 `acquire_camera`（冷开兜底）都用它。
- ⚠️ 只在**第一次真失败**之后才打扰 GKS_Web —— 比赛时没人开预览，行为与加这条之前一样。
- ⚠️ GKS_Web 没在跑时是 Connection refused，**静默忽略**（normal case）；`/abort` 会顺带 set() 页面内在跑的识别 —— 可接受（两者本就在抢同一台相机）。
- 现场判据：Pi 日志 `已请 GKS_Web 停掉…推流（跨进程抢相机: 有人开着网页预览）` = 命中过这条兜底。
- 另一来源是**进程内双开竞态**：`LEASE_WARM_WAIT_S` 原先 2.5s 贴着 ~2s 开相机耗时，Pi 一忙预热线程就超时 → `acquire` 返回 None → 调用方兜底 open **与预热线程同时开同一台设备** → EBUSY。已抬到 **4.0**；`tasks/_rect.py` 是唯一**没有**重试的。

**遥测/判据**：Pi 日志 `相机预热完成: <相机> 档位=<档>` / `相机租约已释放` / `相机租约空闲超过 Ns, 自动释放` / `租约就地把曝光换成档位 <档>`。**别拿「任务成功了」当预热生效的证据**，验收标准是**视觉步骤不再出现 `摄像头 … 打开成功`**（租约命中不打这条日志）、扫码步骤从指令到出结果 **<1s**。

## 二维码：两条相机 × 两种算法（`STEP_QR_SCAN_WAIT` / `STEP_QR_SCAN_MAIN_WAIT`）

扫码是**两个轴**的组合：**用哪台相机**（副摄/主摄）× **哪个解码器**（自动/自研）。两块积木各有 `algo` 参数选算法，相机由积木本身决定 —— 四个组合 = 四个任务码：

| 积木 | `algo` | 任务码 | Pi 侧开的设备 | Pi 端解码器 |
|---|---|---|---|---|
| `STEP_QR_SCAN_WAIT` | `QR_ALGO_AUTO`（默认） | `"1"` | `/dev/camera_Qr` 扫码副摄 | `tasks/_qr_auto.py`「定位→紧裁→强放大」（末级含微信复核） |
| `STEP_QR_SCAN_WAIT` | `QR_ALGO_DIFF` | `"E"` | 同上 | `tasks/_qr_diff.py` |
| `STEP_QR_SCAN_MAIN_WAIT` | `QR_ALGO_AUTO`（默认） | `"D"` | `/dev/camera_main` 主摄 | `tasks/_qr_auto.py` |
| `STEP_QR_SCAN_MAIN_WAIT` | `QR_ALGO_DIFF` | `"F"` | 同上 | `tasks/_qr_diff.py` |

**「自动」档为什么取代了微信档**（2026-10-23，现场真帧实测）：现场停车位上二维码只有 **46×46 px**（约 1.6 px/模块），而旧链路的「画面中心固定裁剪 0.30 + 微信引擎」把码的位置写死了 —— 纸张平移 5~6% 就把码整块甩出裁剪窗，**重试多少次都是 0%**。新引擎先用 zxing 的 `return_errors` 拿到「解不出但位置准确」的检测框，再按框 1.6 倍紧裁、放大到 960、多增强多二值化器解码；定位不到时依次走中心裁剪阶梯、2× 上采样再定位、微信复核。同一批真帧：静止 **2/10 → 10/10**，平移 0~20% 与旋转 0~25° 全中，合计 **32% → 95%**，命中耗时 **60~75ms**。

**主摄那条为什么存在**：二维码在主摄视野内、副摄看不到的场合；且能吃 `"C"`（`RPI_TASK_WARM_MAIN`）预热好的主摄 —— 租约命中**就地换曝光档**、不重开设备。

**自研算法为什么存在**（2026-09 加，台架实测）：同一位姿下 wechat **连试三次全失败**（「未检测到二维码」），自研解出 `233`、用时 **4.48s**（开发机同图 1.0s → 倍率 4.5×）；它治的是斜视/小码/强透视，正是臂摄扫码的工况。

### ⚠️ 超时由**单片机**说了算（`"<命令码>,<毫秒>"`，2026-09 加）

阻塞类视觉指令（`"1"`/`"D"`/`"E"`/`"F"`）发送时**把本端愿意等的毫秒数附在命令码后面**：`vRpiSendTaskCmdMs()` 发 `"F,7500"`，Pi 侧 `handler._split_payload` 拆出头与时限、再用 `_budget_from_ms` 减掉一个余量当自己的预算。

- **为什么这么干**：原是两个仓库各记一个数、还必须满足「Pi 预算 + 开相机 < 固件等待」；现在**路线里那一步的 `I(0)` 是唯一时间权威**，想给自研多留时间改积木那一个数就行。
- ⚠️ **余量 `QR_CMD_MARGIN_S`(1.5s) 不能省**：单片机从**它发指令那一刻**计时，而这 1.5s 里 Pi 还要「开相机 + 扫描 + 回帧」。少了它，冷启动那次 Pi 会**答得比单片机放弃还晚**，迟到的结果帧会落进**下一次重扫**的等待窗口被当成那次的结果（扫描 A 的结果被判成扫描 B 的）。
- ⚠️ **顺带修掉一个旧隐患**：默认路线那两步扫码固件只等 6000ms，而 Pi 原来的 `QR_SCAN_TIMEOUT` 是 5.0s **加**开相机 ~1.3s = 6.3s —— 冷启动本就会触发上面那条；现按 6000 倒推成 4.5s。（⚠️ 2026-09-26 复测开相机是 ~2s 而不是 1.3s，4.5s 预算**更紧**了 —— 这正是预热步骤必须排够窗口的原因。）
- ⚠️ Pi 侧有上限 `QR_CMD_MAX_TIMEOUT_S`(12s)：相机租约空闲看门狗（`LEASE_IDLE_TIMEOUT_S`）只被 `read()` 续命，单次扫描超过它会在**解码途中**关掉设备，后续 `read()` 全失败、扫描循环空转到超时（现象是「一直超时」而不是报错）；超了会夹住并打一条 WARN。（⚠️ 窗口可能是 `uses × 15s`，那时上限偏保守 —— 别为此去抬它：它保护的是**单次扫描**这个最常见的 `uses=1` 场景。）
- ⚠️ **别把 `I(0)` 抬过 8s**：`RPI_DISCONNECT_TIMEOUT_MS`(8s) 是**编译期全局**，抬积木超时**不会**跟着动 —— 链路中途会闪一次 Disconnected（不是故障，Pi 一应答即自愈，代价是 OLED 闪一下 + 蓝牙臂编辑窗被关一次）。要更长的等待，改 `app_config.h` 那个宏并重编译；自研那一步建议 `7500`。
- ⚠️ 只有 `handler.py::_MS_COMMANDS` 里登记过的指令能收时限；其余指令带了逗号会被判成「形状不认识」而**响亮地拒掉**。

### 其余纪律

- ⚠️ **结果帧四条路共用** §6a 那 9B ASCII 格式（`QR<ddd>` / `QRF`），所以固件侧 `ucRpiWaitQrResult()` **一字未改**，下游（IF 条件 `SCRIPT_COND_QR`、排爆抓取首位、反恐任务第三位）读的还是同一个 `iGetQrCode()`；加这类「只换相机/只换算法」的任务照此办理 —— **别顺手去加新 TAG**。
- ⚠️ **固件侧共用一个实现**：`app_rpi.c::ucQrScanCommon(emTask, ms)` 是唯一实现，`ucRpiQrScan()` / `ucRpiQrScanMain()` 只是「用 `c_emQrTaskOf(相机, 算法)` 选任务码」的两行薄壳（越界回落微信档）。别把 `qr_manual` 那道门或失败音约定复制成第二份 —— 尤其那道门**必须在发指令之前判**（`ucRpiWaitQrResult` 一进来就 `vSetQrCode(-1)`，发出去就晚了）。
- ⚠️ **`algo` 参数落在 int 槽**（`anI: timeout_ms=..., algo=...`），case 体里必须写成 `ucRpiQrScan((uint32_t)I(0), (emQrAlgoTdf)I(1));` **同一行** —— 先读进局部变量会让这块积木显示成 `I`（case 体里第一个「标识符(」是控制台取的原语名）。下拉由 `(emQrAlgoTdf)I(1)` 的强制转换反查枚举，所以 `emQrAlgoTdf` **必须一行一个成员**（`parse_enums` 是整行锚定的正则，写成单行 `{A=0, B=1}` 会解析出 0 个成员、下拉**静默消失**）。
- ⚠️ **`qr_manual` 对四条路都生效**（与相机/算法无关）：跳过/扫到都**不响**（看 Pi 日志 `QR preset: skip scan` 与 OLED 星号）；失败 → 失败音（0.8s×2, 2026-10-27 加）。
- ⚠️ **预处理参数三条路各一套**（Pi 端 `config.py`）：副摄 `QR_SCAN_*`、主摄 `QR_MAIN_SCAN_*`、自研 `QR_DIFF_*`。`QR_SCAN_CENTER_CROP` 默认 **0.3**（只取画面中心 30% 正方形）是为副摄近距离取景调的；主摄对着场地时二维码**不在中心 30% 内** → `QR_MAIN_CENTER_CROP` 默认 **0.0（不裁剪）**；自研那条也 0.0，且 `QR_DIFF_MAX_SIZE` 给到 1280（它的定位角检测按分辨率调过，降到 960 会把小码定位角压到轮廓面积门限以下）。要在 Pi 的 Web「设置参数」里调（按**名前缀**自动分组）—— 但**新常量必须登记进 `config.py::EDITABLE_CONFIG`** 才出现在页面上（唯一登记处，漏了不报错、只是页面上没有它）。
- ⚠️ **`handle()` 那个互斥元组**：**实际 9 项** —— `if head in (b"1", b"4", b"5", b"6", b"A", b"D", b"E", b"F", b"G"):`（根 `CLAUDE.md` 旧版只列了 8 项、漏了 `"G"`，以 Pi 源码为准）—— 主摄那几条要用主摄，不先停巡线/靶标流就会被流线程占着设备（`open_camera` 直接失败），结果帧与流帧同为 COORD 会交错；`"E"` 虽用副摄但一样发 COORD 结果帧，同样要停巡线。**再加这类指令时记得同一个元组也要加**（那里判的是**拆出来的 head**，不是整串 payload）。⚠️ **`"B"`/`"C"` 仍不在那个元组里**（只开相机、不发结果帧，且 `"B"` 恰恰排在巡线**之前**）—— 别因为新加了 E/F 就把 B/C 也塞进去。
- ⚠️ **测量只能从 Pi 日志读**：路线里那块 `STEP_RPI_SEND_TASK` 是**非阻塞**的，拿不到结果帧、没法从固件侧计时。看 `检测到二维码 [diff]: 233（用时 4.48s）` 那一行（`_run_task` 里新加的耗时打点）。

### 积木参数与语义（最多 3 个方案槽）

```c
SCRIPT_STEP_I4 (STEP_BALL_ALIGN_WAIT, "小球对位: 识别→", 6000u, ALIGN_BALL_MID, ALIGN_RECT, 0u)
//             I(0)=每方案超时[ms]   m1         m2           m3（ALIGN_NONE=不试/空槽）
```

- 按 m1→m2→m3 **逐个试，第一个成功即停**；`ALIGN_NONE` 跳过；**同一方案只试一次**（重复写 =
  排表错误，去重免得白烧一个超时）
- 方案码 `emAlignMethodTdf`（`app_rpi.h`）：`ALIGN_NONE=0` / `ALIGN_BALL_MID=1` / `ALIGN_RECT=2` /
  `ALIGN_PULLBACK=3`；下拉自动从枚举尾注释派生 —— **加方案 = 枚举加一项 + 链里加一个分支**（`app_script.h` 的 DSL 不动）
- ⚠️ **`ALIGN_NONE = 0` 是唯一自洽的空槽值**：`map_codec` 把空参数槽补成 `"0"`
  （`_normalize_param("")` → `"0"`），故"不试"必须是 0（同 `SCRIPT_PRESET_NONE = 0`）
- ⚠️ **新拖出的积木默认三槽全是"不试" + 超时 0** → 必须先填 m1 与超时；**没配方案 → 失败音 +
  `[STM-DBG] ALIGN fail: no method`**，绝不静默空转（`map.c` 老行只填 `6000u` 即此 —— 改参数
  **必须按 `map_codec._serialize_step` 重写老行**，见规则第 8 条）

### ⚠️ 最坏阻塞 = 方案数 × (超时 + 平移时长)

**每个方案各拿满 `I(0)`**（宁可慢，不砍短下一个）。3 槽 × 6000 ≈ 18s，跨过
`RPI_DISCONNECT_TIMEOUT_MS`(8s) → 链路中途**闪一次 `Disconnected`（不是故障）**（`app_rpi.c` 收到有效帧即恢复 OK；代价只是蓝牙臂编辑窗被关）。**想不闪别调小超时**（会低于 Pi 识别耗时）：
正解是"一次识别带回两种测量"（板心字段追加进 0x03 帧）。

## 人质识别优化（对标色球四件套的适配版，2026-10-26 实现）

2. **次级候选池**：conf ∈ [`HOSTAGE_CONF_LO`, `HOSTAGE_CONF_THR`) 的框按形状归并进池；并集不齐时池里有缺的形状 → **实测坐标直补**（YOLO 框自带类别，不需要色球那套概率指派）；
3. **几何补齐**（`_hstg_rescue`，剩恰 2 只时）：⚠️ **缺谁由间距 d 判**（缺中间 d=全排宽 ~771px、缺端部 d=单间距 ~400px，`HOSTAGE_MID_GAP_PX`=550 一刀切，间距对车平移不变）——**别用"两只中点偏移"判**：端部没检出（车正）与端部出画（车偏）两种成因的中点偏移**方向相反**，分不开（2026-10-26 用户问倒后改的，原设计是错的）。缺中间 → 端部连线中点（池里中点 ±`HOSTAGE_NEAR_TOL_PX` 内的实测框优先）；缺端部 → 谁离 `HOSTAGE_CX_CENTER`（⚠️ 跨仓库复制品，与蓝牙 hs_cx_center 手动同步）近谁是中间，缺位等距外推（出画钳回，坐标不被消费）；
4. **对位自修**：补齐后中间那只永远是实测/高精度插值——缺端部哪怕真出画，对位用实测中间照常把车修回正位（**对位本身就是修正**，这是人质侧不需要色球那套"±固定距离"拉回的原因）；
5. **单目标拉回**（固件 `ucHstgPullToCenterOnce`，`ucRpiHostageGrabOne` 识别失败分支）：失败帧恰剩 **1 只路标**（Pi 失败帧 2026-10-26 起带"最好成绩"，0x02 协议零改动、旧固件兼容）→ 把它**平移到理想列**（`hs_cx_center`，对位 cx 路同一条符号链）→ 重扫一次。**不需要知道它是谁**：是中间则车已对齐；是端部则车只偏 150mm、三只照样全在画面（出画需 ~175mm+），重识别必然全出、后续对位自修——比色球开环拉回还准（按实测偏差定向平移）。`ucHostageScanOnce` 发 "4" 前清快照（防超时读旧路标）。全程无蜂鸣（用户自排提示声）。剩 0 只无路标 → 老实失败。
