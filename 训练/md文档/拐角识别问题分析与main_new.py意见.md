# "越来越偏是不是 PID 残留" & main_new.py 拐角识别意见

> 2026-09-23。两个问题：① "越来越偏"是否 PID 残留；② `main_new.py`
> （1000 行，已实现 v4 大部分条目）对拐弯处的识别"依旧不尽人意"。

---

## 一、"越来越偏"不是 PID 残留——链路上不存在能残留的积分器

逐层核过：

| 层 | 积分器 | 事实 |
|---|---|---|
| Pi 端 LinePID | `self.integ` 确实在累计 | 但 **`LINE_KI = 0.0`**——积分项算了乘 0，**没有积分作用**；KD 只作用在帧间差分上，也不积累 |
| MCU 航向环 | 无 | `app_line.c` 注释自证"纯 P、无微分"，`fW` 每拍从**当前**误差现算，无任何跨拍状态 |
| MCU 位置环 | 无 | steer 直通 vx，无积分 |

所以"上次的 PID 存在残留"这条假设不成立：**没有积分器，就没有残留**。
"越来越偏"只能来自随时间**单向漂移的测量或标定**，候选依然是 §6 清单那三条
（相机支架被减速带撞松 → 安装角漂移；单一 −3.0° 目标逐站不成立；符号/尺度逐站反转）。
**验证方法不变**：跑一轮前后把车摆回同一条直线，读 print 的 `ang` 对比；
再逐站摆平行读 `ang`。哪个数字变了，因就是哪个。这也是为什么排查清单要放在
一切改动之前——它只需要摆车，不需要改代码。

## 二、main_new.py 拐角识别"不尽人意"的根因与意见

先说做对的部分：v4 清单里的条目基本都实现了（追踪门 35px/0.3s、通道滞回 1.3、
EMA 带拒收门、双限速、LOST_GRACE_FRAMES=10、切线三条 sanity）——框架没问题。
问题出在**判据的标定域被自己改掉了**，以及**状态机没有迟滞**。

### A【主因】测量窗上扩打碎了拐角判据的标定——代码注释里自己已经承认

`main_new.py` 第 211-212 行原文：

> 结果是"上扩"把既有行为全改了：实测 img_0003（直线）的 wrms 由 1.3 涨到 6.7
> （被误判成拐角），而 img_0005（真拐角）由 7.1 掉到 2.6（漏判）。

`6.0 / 15°` 两个阈值是在**原窗口（row 80~240）**上标定的；窗口上扩到 19 条后，
点集混入了上扩区域的远端边界段，全点 RMS 的分布整个变了——直线图能涨到 6.7
（>6 误判），真拐角能掉到 2.6（<6 漏判）。**这就是"识别不尽人意"的主因。**

**修法（推荐①）：**
1. **判据域对齐**：拐角判据只用 `row ≥ FIT_MIN_ROW(80)` 的点——与拟合/offset
   同一个已标定域；上扩区域（row<80）的点只用于"提前看见"（进入视野提示），
   不参与判拐角。一行过滤，6.0/15° 的标定立即恢复有效。
2. 或者：保持全点判据，但用 PC 回归把 7 张图在**新窗口**下重新标定阈值
   （方案里有这个回归架子，跑一遍就有数）。

### B 状态机没有迟滞——阈值边缘单帧翻转

截图日志的最后两帧就是现场：

```
v=1 st=1 wrms=1.8 half=--   [拐弯处]
v=1 st=0 wrms=3.1 half=14.2° [正常]     ← half 距阈值 15° 只差 0.8
```

而前 7 帧 half 在 20~30°——**half 的帧间方差（14~30°）比阈值间距（15 vs 10）
还大**，任何硬阈值都会在这个方差下抖。修法：
- 进拐角 `>15°`、退拐角 `<10°`（迟滞），或 5 帧里 3 帧超限才切；
- 更进一步（符合方案自己"输出必须连续"的总原则）：**不要在"切线/割线"之间硬切**，
  按曲率强度加权混合（如 `w = clamp((half − 8)/20, 0, 1)`，angle = w·切线 + (1−w)·割线），
  状态位只做日志/诊断，不参与输出口径切换。

### C 一个疑似不一致要查：wrms=1.8、half=-- 却判了拐弯处

两条判据都不满足（1.8<6、half 缺失）却输出 st=1。要么状态被锁存（那要写明退出条件），
要么 half 在某分支有内部值但显示层打了个 `--`。无论哪种，**第 8 帧的 st=1 依据
在日志里读不出来**——判据命中的原因必须可见，否则现场没法排障。

### D 只有"左右分半"——迎面弯会晚判/漏判

`half_slope_diff` 以控制列为界分左右。这适合 0005 型"横扫的对角弧"；
但**迎着弯开过去时，曲率最先出现在远近方向（行方向）**——远端先弯、近端还直，
左右分半对此不敏感，表现为"晚判"。建议补第二条：
按行分远近两半（以 row=160 为界）各拟斜率取差，与左右分半**并联**（任一超限即拐角）。
零额外成本，点都是现成的。

### E half 帧间方差 14~30° 本身值得查

同一段弧上方差这么大，多半是点集在帧间变动（褶皱假点进出、或追踪门在拐角段
把真点也拦了——弧移动快，35px 门在拐角可能偏紧）。日志里加"每半边点数"和
"被追踪门拦掉的点数"，跑一圈就知道方差来自谁。

### F 性能：上扩让 stats 调用反而变多了

19 条 × 8 列 = **152 次** get_statistics/帧（原版 106、strip20 版 66），截图 14fps
还是 IDE 在拖（传感器 22.7fps）。建议：
- 移植 `.bak-strip20` 里的剖析器，拔掉 IDE 测真实 fps；
- 拐角判据域对齐到 row≥80 之后（见 A），上扩区域的 6 条剖面可以降采样
  （或只在判据需要时粗采样），把调用数压回去。

### G 诊断字段可读性

日志里 `上=0`、`侧=0` 没有注释，现场没法解读。每个字段在 PRINT 处加一行说明
（或直接用带名字的格式），排障时少猜一次。

## 三、优先级

| 序 | 事项 | 性质 |
|---|---|---|
| 1 | A：拐角判据域对齐 row≥80（或重标阈值） | 主因，一行过滤 |
| 2 | B：迟滞/投票 + 切线割线加权混合 | 去抖 |
| 3 | C：查 frame8 的 st=1 依据 | 排障可见性 |
| 4 | D：远近分半判据 | 提前量 |
| 5 | E/F/G：点数日志、剖析器、字段注释 | 工具性 |

§6 排查清单（摆车逐站读 ang）仍然建议最先做——"越来越偏"的因和拐角识别的调优
都需要这个基线。
