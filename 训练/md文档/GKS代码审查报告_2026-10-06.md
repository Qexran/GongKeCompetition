# 第一部分：STM32 固件（GongKeCompetition）

## A. 会静默失效 / 有物理后果

### A1. 标靶流控「距离辅助」永远不动车 —— 同一拍把自己清掉【已核实】

位置：`Application/app_rpi.c:4120-4128` 与 `:4166`

```c
4120    fMm         = fMmDist;      /* 距离辅助算出的挪车量 */
4121    ucMmLateral = 1u;
4128    ucStage     = TS_STAGE_X;   /* 回 X 重修 */
...
4166  if ((ucSeqEn == 0u) || (ucStage == TS_STAGE_X)) { fMm = 0.0f; ucMmLateral = 0u; }
```

距离辅助在**本拍**先把 `fMm` 写好，紧接着（4128 行）把 `ucStage` 翻回 `X`；于是 4166 行那道门控
（本意是"阶段 2 不许清，否则会抹掉距离辅助的量"）此刻条件成立 → **刚刚算出的挪车量被抹成 0**。
下发段 `if (fMm != 0.0f)`（`:4275`）恒假。

更糟：4167 的底盘接管块此时**反而会跑**，若 `ucChasActive != 0` 就把 `fMm` 重新赋成 CX 那一路的
**前后**进给量 —— 轴和方向都不是距离辅助想要的。

**后果**：`ucDistMoves++`、`fDistTravel += |mm|`、回 X 重修一圈全都照做，日志照打
`TGTS dist#N mm=..`，**唯独车一步不走**；`ts_dist_mm` 行程闸也因此永远不涨。
`ts_dist_en=1`（出厂 1）+ `ts_dist_px_to_mm≠0`（现场标定填了才非 0）时即可复现 ——
也就是"这个功能一标定就废"。这是 2026-10-06 新加的三层处方里的第③层。

**修法**：在循环体顶部快照 `ucStage` 再判，或把 `ucStage = TS_STAGE_X` 挪到下发之后，
或用一个「本拍已由距离辅助置位」的标志代替 `ucStage` 做清零判据。

### A2. 「测试」积木能测 `STEP_SCRIPT_CALL` / `SCRIPT_RETURN` → 帧栈泄漏、路线被静默截断【已核实】

位置：`Application/app_script.c:494-500`（防呆名单）、`:1133-1141`（唯一的弹帧点）

防呆只拒绝了 `TEST_LOOP_WAIT` / `SCRIPT_RESET` / `IF` / `ELSE` / `END_IF` / `STEP_COUNT`，
**漏了 `STEP_SCRIPT_CALL` 与 `STEP_SCRIPT_RETURN`**。而弹帧（`s_ucScriptDepth--`）**只存在于
`vScriptRun` 的循环里**，`vScriptTestLoop` 走的是 `vScriptExecStep`，永远不弹。

- 测 `STEP_SCRIPT_CALL`：压一帧、深度 +1，测试块结束后 `vScriptRun` 把**被跳入的那张表**当成
  当前帧继续跑 → **后半张路线被丢弃**（无报错）。
- 测 `STEP_SCRIPT_RETURN`：`vScriptReturn` 直接把**真实帧**的 `usIdx` 置到表尾（`:352`）→
  测试一跑完，正在跑的路线**就此结束**。

这与注释里「选 IF 标记这条不是保险，是必须的」同性质，应一并长鸣拒绝。

### A3. 蓝牙机械臂编辑模式：「脚本没在跑」这条入场路径是死的【已核实】

位置：`Application/app_bt.c:441`（入场门）vs `:189`（使用闸门）

- 入场门放行条件：`ucGetBtHsWait()==0` **且** 脚本没在跑 → `vSetBtEditMode(1u)`。
- 使用闸门 `bt_edit_active()` = `editMode && bt_hs_wait` —— **要求 `bt_hs_wait != 0`**。
- 而 `bt_hs_wait` 的两个写者全在脚本侧且离开即清零（`app_rpi.c:534/546/581`、`app_bt.c:245/270`；
  已全仓库 grep 确认无其它写者）→ **脚本空闲时它恒为 0**。

**后果**：能进编辑模式、能收到 `$B,OK`（控制台 toast 报「已进入」并放开滑杆与「获取当前位姿」），
但随后每一次 `JOG/GRIP/ARM/POS/PLAY` **全部回 `$B,ERR,NOTEDIT`**。
与 `tools/webconsole/CLAUDE.md`「② 脚本根本没在跑…放行是安全的」直接矛盾。
现场症状：菜单跑完一条任务预设后再进编辑模式，拖动无反应。

**修法**（二选一，都是一行）：`bt_edit_active()` 改成
`ucGetBtEditMode() && (ucGetBtHsWait() || ucGetScriptRunning()==0)`；
或让 `bt_cmd_mode` 的 ② 分支直接回 `NOHANDSHAKE`（行为与门禁一致）。

### A4. 上电后头 60 秒，「自动重启 Pi 客户端」被静默禁用【已核实】

位置：`Application/app_rpi.c:61`（`static uint32_t s_ulSysCmdTick = 0u;`）+ `:339`

`vAppRpiInit`（`:79-84`）只初始化了 `s_xLastRpiFrameTick`，**没管 `s_ulSysCmdTick`**。
于是 `(xTaskGetTickCount() - 0) < RPI_SYSCMD_SUPPRESS_MS(60000)` 在上电后头一分钟恒真 →
`vRpiRestartPiClient` 直接 return。这条互锁本意只是「刚发过 sd/rb 之后别凑单」。

**后果**：两条自愈路径（`ucRpiSendTaskCmdWait` 的重连重试、`ucRpiHandshake` 的
「对端活着却不发 SYNC_HS_1」）在这一分钟内**一帧 `"r"` 都发不出去**，最长要等满一分钟；
握手那条还会每 6s 打一条 `HS kick: peer alive but no SYNC_HS_1` 的**假日志**（`ulKickTick` 照更新），
看着"一直在踢"其实什么都没发。比赛上电即跑，这一分钟大概率落在路线开头。

**修法**：`vAppRpiInit` 里 `s_ulSysCmdTick = xTaskGetTickCount() - pdMS_TO_TICKS(RPI_SYSCMD_SUPPRESS_MS);`
或判据加 `s_ulSysCmdTick != 0u`。

### A5. 出队认领与代次号读取不在同一临界区 —— abort 可能被吞掉一整条动作【审查员发现】

位置：`Application/app_arm_action.c:712-726`

```c
pst = c_pstQueueClaim();     /* 临界区内 */
if (pst == NULL) { ... }
ulGen = s_ulSeqGen;          /* ← 临界区之外 */
while ((s_usStep < pst->usCount) && (s_ulSeqGen == ulGen)) { ... }
```

若一次 `vArmSeqAbort()` 恰好落在 `taskEXIT_CRITICAL()` 之后、`ulGen = s_ulSeqGen` 之前
（`taskEXIT_CRITICAL` 恢复 BASEPRI 是天然抢占点，`vBtTask`/脚本任务优先级不同即可命中），
泵就会认领 abort **之后**的新代次、把被中止的那条动作**整条跑完** —— 正是「后写者胜 + 新指令
显式终止旧序列」要防的"两边抢舵机"。

**修法**：把 `ulGen = s_ulSeqGen;` 挪进 `c_pstQueueClaim()` 的临界区。

## B. 本地 Web 控制台会静默改坏源码

### B1. `sanitize_tag` 不幂等，且会产出含 `//` 的标签【已核实：实测复现】

位置：`tools/webconsole/map_codec.py:281-313`

折 `//` 排在**配平括号之前**，删掉夹在两斜杠之间的 `(` 会把它们重新拼成 `//`：

```
'a/(/b'  ->  'a//b'  ->  'a/b'      ***  NOT IDEMPOTENT  ***
```

这与该文件自称「这几个函数都是**幂等的**」以及 `tools/webconsole/CLAUDE.md`
「`sanitize_tag` **必须幂等**」直接冲突。

产出的标签写进 `map.c` 后**两条下游后果**（机制已逐行核实）：
- `_parse_body:186` 的 `work = work.split("//")[0]` 从 `//` 处截断 → 括号计数不归零 →
  **下一条步骤被并进这一条**（界面两条变一条）；该条目一旦被编辑，
  `_serialize_step` 按合并后的单行重写 → **后一条路线步骤静默消失**。
- `_ensure_comma:380` 按行内首个 `//` 切分 → 尾逗号被插进**字符串字面量里**，积木名被无声改掉。

**修法**：`//` 折叠挪到括号配平**之后**再跑一遍（或循环「配平→折 //」到不动点）。

### B2. 手改 `app_arm_action.c` 只注释位姿行 → 保存会把禁用动作**重新启用**【已核实】

位置：`tools/webconsole/arm_action.py:324`（合并时 `disabled` 取**与**）+ `:503`（`_serialize_items`
对**未编辑**条目也跑 `_toggle_disable`）

手写文件里「位姿行被 `//` 注释、夹爪行留着」是正常形态（`webconsole/CLAUDE.md`：两行一起进出数组），
合并后 `True and False = False` → 保存把 `//` 剥掉 → **本该禁用的臂动作变成会真的播放**（动舵机），
且零 diff 破了。

**修法**：`disabled` 取**或**，或让 `_toggle_disable` 只作用于 `edited` 条目
（与 `map_codec.serialize_map` 一致）。

### B3. 任何一次真实保存都会把整份源文件从 CRLF 改写成 LF【审查员发现】

位置：`server.py:810`（`read_text()` 默认 universal newlines，`\r\n`→`\n`）+
`server.py:927`（`write_text(..., newline="")` 不转换）；`map.h` / `app_script.h` /
`app_config.h` / `app_arm_action.c` 同款。

本机现在 7 个受管文件全是 LF 所以不发作；但仓库**没有 `.gitattributes`**，
Windows 队友 `core.autocrlf=true` 检出即 CRLF —— 那时只要有一次真实编辑，
「只替换数组体、其余字节原样保留」这条核心契约就静默失效，diff 变成整文件。

### B4. `POST /api/tuning/meta` 不校验换算是否属于闭集【审查员发现】

位置：`tuning.py:523-546`（`write_meta` 直接落盘）、`server.py:1456-1461`。
`CONVERSIONS` 只在**改值**路径（`from_display`）校验。从任意 API 客户端（本控制台无鉴权）
写入 `{bogus->x}` 后，该参数在「调参」Tab 里**再也存不进去**（写盘抛「未知转换」，
用户只看到一句 ⚠ 而值没落盘）—— 正是根 `CLAUDE.md` 花大段警告的那个症状。
**修法**：`write_meta` 里对 `conv not in CONVERSIONS` 直接 400。

## A. 会静默失效 / 静默错数据

### A1. 巡线起流会被上一条的「收尾期」静默吞掉【已核实】

位置：`handler.py:842-848`（`_cmd_line_start`）

```python
if _line_thread is not None and _line_thread.is_alive():
    print("[WARN] 巡线已在运行，忽略重复的启动指令")
    return
```

固件每条巡线类步骤收尾都**无条件**发 `LINE_STOP`，紧接的下一步若又是巡线步就发 `LINE_START`；
而 `run_line_follow` 要等一拍（`1/LINE_SEND_HZ`）才在循环顶部看到 abort 退出 ——
这段窗口里 `_line_thread` 仍然 `is_alive()` → 新的 `"2"` 被当成「重复启动」丢掉，
**旧的流又正好退出** → 单片机这一整步一帧都收不到（`ucRpiLineRun` 起流段超时长鸣 + 车不动，
日志只有一行 WARN）。

对照：`_cmd_aim_start`（`handler.py:604-617`）**专门**写了「它正在收尾（abort 已置位）→ 等它释放相机」
的分支，巡线这条**没有对应分支**。**修法**：照抄 `_cmd_aim_start` 的收尾分支。

### A2. 靶标流「锁定阶段」的多帧投票是空操作【已核实】

位置：`tasks/_target_stream.py:129-149`

```python
n = max(1, int(config.TARGET_STREAM_INIT_FRAMES))
for _ in range(n):
    found, _small = _detect_frame(frame, cfg, config.TARGET_PROC_SCALE)  # frame 是入参，从不变
    for t in found: votes.setdefault(...).append(...)
```

`frame` 是函数参数、循环里**从不重新取帧**，而 `_detect_frame` 对同一张图是确定性的 →
n 次投票结果逐项相同 → `len(pts) >= _LOCK_MIN_VOTES(2)` 对**单帧命中**恒成立。
docstring 承诺的「单帧命中不算 —— 一帧误检就锁死会把整个闭环引到杂块上」**完全不存在**：
一次误检就能让 10Hz 的 P 环从此朝杂块推舵机（行程闸 50° 是唯一兜底）。
附带每次尝试白烧 n×全画面检测（~220ms/帧）。

**修法**：循环内重新 `feeder.wait_new` 取新帧，或在 caller 里先攒 N 帧。

### A3. 二维码失败留档排在结果帧**之前** → 失败路径必然顶穿「Pi 先放弃」【已核实】

位置：`tasks/_qr.py:741-759`（`_run_diff` 里先 `dump_failure`）+ `handler.py:181,189`
（`_cmd_qr_common` 在 `run_fn` **返回之后**才 `_send_qr_result("QRF")`）

自研解码失败（最常见路径：`_scan_qr` 重试到 6.0s 预算跑满）后，还要写 `frame.jpg` +
`warp.png`（1320×1320）+ `matrix.npy/png` + `hits.txt`，再由 `_prune` 对最多 20 个目录
`shutil.rmtree`（SD 卡上每次 50~300ms）——量级 **0.3~1.5s**，全部发生在回帧之前。
于是「收指令 → QRF」= `开相机 + 6.0s + 留档`，冷开时可达 8~11s > 单片机等的 7500ms
→ 迟到的 QRF 落进**下一次重扫**的等待窗口（正是 §6 明确警告的错位）。

**修法**：把 `dump_failure` 挪到回帧之后，或丢进后台线程。

### A4. 自研/开相机不计入预算 → 第二条超预算路径【审查员发现】

`tasks/_qr.py:461`（`_open_with_retry`）在 `:364` 的 `deadline` **之前**执行 —— 开相机不在预算内。
`_budget_from_ms(7500)` = 6.0s，余量注释假设开相机 1.3s（实测 ~1.5~2s）；
相机被占时 `_open_with_retry` 是 `5 × (~2s + 0.3s) ≈ 11.5s`，期间只在 attempt 边界查 abort。

### A5. 三位数校验只判「3 个数字」，不判 100~399 / 每位 1~3【已核实】

位置：`tasks/_qr.py:34-35`、`:411-417`

```python
_VALID_RE = re.compile(r"^\d{3}$")
```

视野里任何内容为 3 位数字的二维码（含 `000` / `999` / 场地其它贴纸）都会被判**成功**并回传
`QR000`，而单片机 `ucRpiWaitQrResult` 会接受它（它只认 `QR`+3 位数字），
下游（IF 条件 100~399、排爆首位 1~3、反恐第三位 1~3）**一律不合法** →
症状正是「Pi 报二维码识别成功、后面整链按旧值/不动」。
（固件侧 `STEP_QR_SET_TEST` 反而有 `c_iQrTestSanitize` 强制 1~3 —— 两端宽严不对称。）

**修法**：`_is_valid_code` 加「100 ≤ int(data) ≤ 399 且每位 ∈ {1,2,3}」，
或至少在日志里把「超出 100~399」单独标出来。

### A6. 色球多帧散布闸只查 `cx`，而 `cy` 同样被回传并当**横移**量用【已核实】

位置：`tasks/_color.py:483-486`

```python
if xs[-1] - xs[0] > COLOR_MAX_SPREAD_PX:   # 只有 xs
```

`cy` 没有任何一致性判据，但它是回传字段（§6d），且本车 `BALL_XY_SWAP=1` ⇒
单片机端「**横移 ← cy**、纵移 ← cx」。车沿横向挪动时 `cx` 基本不动（闸不响）、
`cy` 逐帧漂 → 取中位数得到一个**没人见过的位姿**的坐标，横移量静默偏掉且日志里"散布"看着正常。

**修法**：对 `ys` 用同一个闸。

### A7. 两球外推缺「间距自洽」与「落点在图内」两道判据，会报出画面外的第三颗球【已核实】

位置：`tasks/_color.py:336-360`（`_infer_by_two_balls`）

三种占位假设只用 `|mid − cx_center| ≤ cx_tol_px` 一条筛选，**没有** A2 那套
`s_tol` / `u_min` / `u_max` 自洽性校验，推出来的 `x_miss` 也**没有 `0 ≤ x ≤ 1920` 范围检查**。

反例（审查员给出，我核过算式）：板子识别失败 + 只认出左右两颗 + 车停偏 → `x1=51, x2=986`
时「相邻偏左」假设 `mid=986` 恰好在 926±60 内过关 → 返回 `x_miss = 2·986−51 = 1921`（**出画面**），
而正确假设「两端」因 `|519−926|=407` 被否。结果被不带任何标记地当三色结果回传，
单片机 `ucBallScanOnce` 认为识别成功、且**中球（对位基准）就是这颗假坐标**。
这违反文件头自己写的「任何一层判据不过就不推」。

**修法**：补 `0 ≤ x_miss ≤ 图像宽` 与间距自洽（`|gap − 预期间距| ≤ tol`）两道判据。
