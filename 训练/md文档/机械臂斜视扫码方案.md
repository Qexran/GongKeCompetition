# 机械臂主摄斜视识别二维码 —— 可行性与实施方案

> 结论先行：**可行**，而且基础设施大半已经就位。固件侧"主摄扫码"（任务码 `"D"`）、
> 主摄预热（`"C"`）、`STEP_QR_SCAN_MAIN_WAIT` 积木、机械臂动作预设录制体系全都现成；
> 真正要补的只有两件事：
> ① **Pi 侧解码链对透视畸变不够鲁棒**（核心瓶颈，见样张《畸形二维码.jpg》）；
> ② **在 map.c 路线层把"正视失败 → 臂摆斜视位姿 → 主摄重扫"串成第三级重试**。

---

## 1. 为什么远处正视会失败，为什么臂摄斜视反而能成

### 1.1 失败原因分析

| 因素 | 远处正视（现状，副摄 `"1"`） | 臂摄斜视（本方案） |
|---|---|---|
| 二维码在画面里的尺寸 | 距离远 → 单模块像素太少，是**主要失败原因** | 臂把相机送到板前，模块像素充足（样张里码面占画面约 1/4，1920×1080 下绰绰有余） |
| 透视畸变 | 板是斜放的，正视时梯形压缩 | 斜视畸变确实更大（样张约 35°~45° 混合畸变），**但这是算法能解的** |
| 平面旋转 | 小 | 大（样张约 30°~40°），同样可算法解 |
| 反光/眩光 | 一般 | 板面白亮反光强（样张左下高光），需预处理+多帧 |

关键认识：**二维码规范本身允许 ±30° 视角偏差，解码器失败的主因通常是"码太小"而不是"码斜了"**。
臂摄斜视把"太小"变成了"够大"，剩下的大角度畸变交给解码端解决——收益远大于代价。
样张《畸形二维码.jpg》就是臂摄实际拍到的画面：肉眼看清晰完整，只是"斜 + 转"，这类图
恰好是现代二维码检测器（下面第 3 节）的强项。

### 1.2 现有条件盘点（都已实现，直接用）

| 现成件 | 位置 | 说明 |
|---|---|---|
| 主摄扫码任务 `"D"` | `app_rpi.h` `RPI_TASK_QR_MAIN`；`app_rpi.c::ucRpiQrScanMain()` | 与副摄 `"1"` 同一条解码链、同一种结果帧（`QR<ddd>`/`QRF`），只换相机 |
| 主摄预热 `"C"` | `RPI_TASK_WARM_MAIN` | fire-and-forget；租约命中时**就地换曝光档不重开设备**，省 ~1.3s |
| `STEP_QR_SCAN_MAIN_WAIT` | `app_script.c:655` | 主摄扫码积木，结果写同一个 `iGetQrCode()`，下游零改动 |
| 机械臂动作预设体系 | `app_arm_action.c/.h` + webconsole「机械臂」Tab | 蓝牙点动录位姿 → 存成预设 → 地图里自动虚拟成 `STEP_ARM_PLAY_*` 大积木 |
| 失败重试模板 | `map.c:343-355` 预设 17/18 | "预热→挪近 190mm 重扫→再失败→跳过"的三级阶梯，照抄扩一级即可 |
| 主摄在臂上的瞄准能力 | `app_arm.c::vArmAimByPixels()` | 舵机6=画面X、舵机3=画面Y，可做像素级微调（备用手段） |
| 已有识别类位姿 | `ARM_ACT_18`（待命到二维码模式）、`ARM_ACT_10`（看靶子）、`ARM_ACT_15/16` | 录"斜视扫码位姿"有直接参照 |
| 蓝牙遥测 | `app_beam.c:1382`（`qr_code` 字段）+ webconsole「蓝牙」Tab | 台架上不跑全路线就能看扫码结果 |

## 2. 总体流程

```
车到扫码点（现有）
   │
   ├─ ① 远处正视扫（副摄 "1"，现有）──成功──→ 继续路线
   │        │失败（现有预设17）
   │        ▼
   ├─ ② 发"B"预热 → 前进190mm → 重扫（现有）──成功──→ 继续路线
   │        │失败（现有，原直接进预设18跳过）
   │        ▼
   ├─ ③ 【新增】臂斜视扫码（主摄 "D"）：
   │        发"C"预热主摄（排在摆臂动作之前，摆臂那几秒就是预热窗口）
   │        → STEP_ARM_PLAY 播「斜视扫码位姿」（阻塞，臂完全静止）
   │        → STEP_QR_SCAN_MAIN_WAIT 扫码 ──成功──→ 退回待命位姿 → 继续路线
   │        │失败
   │        ▼
   ├─ ④ 【新增】第二位姿兜底：换 ±15° 角度或退 50mm，再扫一次
   │        │失败
   │        ▼
   └─ ⑤ 跳过扫码继续跑路线（原预设18语义不变）
```

时间预算：③ 一步约 2s（摆臂，预热并行）+ ≤3s（扫码超时）；加 ④ 一次兜底共 ≈ **8~10s**。
若比赛节奏紧张，可砍掉 ④ 只保留 ③。

## 3. 工作包 A：Pi 侧解码升级（核心，树莓派仓库）

Pi 仓库当前 `_qr.py` 的解码链对大角度畸变不够鲁棒（样张就是证据）。按"主力 + 兜底"两级改造：

### 3.1 主力：OpenCV 微信二维码检测器（`cv2.wechat_qrcode`）

```python
# Pi 仓库：pip install opencv-contrib-python（通常已装 opencv，补 contrib 即可）
detector = cv2.wechat_qrcode_WeChatQRCode(
    "models/detect.prototxt", "models/detect.caffemodel",
    "models/sr.prototxt",     "models/sr.caffemodel")   # 模型文件随 opencv 源码分发，共 ~4MB

text, points = detector.detectAndDecode(frame)   # 内部自动做 CNN 检测 + 单应矫正
if text: result = text   # 直接就是解码内容，旋转/透视畸变都已处理
```

- 微信检测器自带 CNN 定位 + 透视矫正，对**大角度旋转、梯形畸变、尺度变化**的鲁棒性
  远超 zbar/pyzbar 和 `cv2.QRCodeDetector`——正是样张这种图的对症药。
- Pi 4 CPU 单帧推理 ≈ 100~300ms，一次扫码任务内完全可接受。
- 模型文件放进 Pi 仓库 `models/`，路径写进 `config.py`。

### 3.2 兜底链（任一环出结果即返回）

```python
def decode_qr_robust(frame):
    # 1) 微信检测器（主力，对畸变鲁棒）
    # 2) 全图 pyzbar（畸变不大时最快）
    # 3) 畸变兜底：轮廓分析找三个定位点(1:1:3:1:1) → getPerspectiveTransform
    #    → warpPerspective 矫正成 400x400 正视图 → 再 pyzbar
    # 4) 预处理后重试：CLAHE 增强对抗反光 → 回到 1)
```

### 3.3 多帧投票 + 曝光

- 一次 `"D"` 任务内**连扫 3~5 帧**（租约后台线程本来就持续读最新帧），任意一帧成功即返回；
  全失败才回 `QRF`。抗单帧反光/瞬间模糊，代价仅几百毫秒。
- 主摄 `profile="qr"` 曝光档已存在；斜视反光重，可在台架实测后决定是否需要再降一档曝光
  （曝光越短越不吃反光，但码面是印刷品、静态，可以放心压短）。
- 预处理参数：Pi `config.py` 里主摄一套 `QR_MAIN_SCAN_*`，`QR_MAIN_CENTER_CROP` 保持 **0.0**
  （不裁剪）——斜视位姿下码面不一定落在画面中心。新加的常量（如 `QR_MAIN_ATTEMPTS`、
  解码器开关）**必须登记进 `config.py::EDITABLE_CONFIG`** 才会出现在 Web 调参页。

### 3.4 协议零改动

结果帧仍是 9B ASCII `QR<ddd>`/`QRF`，`ucRpiWaitQrResult()` 一字不动，下游
`SCRIPT_COND_QR`、排爆抓取首位、反恐任务第三位读的还是同一个 `iGetQrCode()`。
**不要新增任务码/TAG。**

## 4. 工作包 B：机械臂"斜视扫码位姿"（录制与验证）

### 4.1 录位姿

1. webconsole「机械臂」Tab，蓝牙点动把臂摆到二维码板**侧前上方**，参照样张取景：
   - 主摄光轴与码面法线夹角 **≤35°**（位姿端尽量温和，把残余畸变留给算法兜）；
   - 二维码**完整入画**且占画面 ≥1/5；注意样张下缘夹爪已贴近画框，别遮挡；
   - 激光关闭、补光灯按需（压反光优先降曝光，其次才补光）。
2. 存成新动作预设「斜视扫码位姿」（生成块写在 `app_arm_action.c`，webconsole 自动维护），
   播放方式选**阻塞（NoWait=0）**——臂没停稳就拍会有运动模糊。

### 4.2 角度-解码率标定（决定最终位姿）

用 Pi Web 预览截屏，采集 **15° / 25° / 35° / 45°** 四档斜角 × 明暗两种光照，各 10 张，
用第 3 节的解码链离线跑成功率矩阵，**选成功率 ≥90% 的最小斜角**作为录制目标位姿。
样张目测在 35°~45° 档，若该档已达 90%+ 则位姿可以更随意（容差大意味着现场鲁棒）。

## 5. 工作包 C：MCU 路线层编排（`map.c`，仿预设 17/18，无新固件逻辑）

把第 2 节流程落到路线表：新增一个预设「臂斜视扫码」（挂在预设 17 重扫失败之后、
预设 18 跳过之前），骨架如下（宏名与现有表一致）：

```c
/* 预设: 臂斜视扫码（正视两连败后的第三级） */
SCRIPT_STEP_I1  (STEP_RPI_SEND_TASK,      "预热主摄", RPI_TASK_WARM_MAIN),
SCRIPT_STEP_I1  (STEP_ARM_PLAY,           "斜视扫码位姿", ARM_ACT_x),      /* 阻塞播 */
SCRIPT_STEP     (STEP_QR_SCAN_MAIN_WAIT,  "主摄斜扫"),                     /* 阻塞≤超时 */
SCRIPT_STEP_F1I2(STEP_IF_ELSE,            "扫到?", SCRIPT_COND_QR, 0, 0), /* 成功走0/失败走1 */
/* 分支0: 成功 → 播回待命位姿 → STEP_SCRIPT_RETURN */
/* 分支1: 失败 → 位姿微调(±15°或退50mm)再扫一次 → 仍失败进原预设18跳过 */
```

注意事项（全部是现有纪律，非新约定）：

- `SCRIPT_COND_QR` 是**快照型**条件，`STEP_IF_ELSE` 必须紧跟扫码步；
- 预热 `"C"` 排在摆臂动作**之前**——摆臂那几秒就是预热窗口，省 ~1.3s；
- `"D"` 已在 Pi `handler.py::handle()` 的互斥元组里（会先停巡线/靶标流），顺序编排即可，
  别再往元组加东西；
- `qr_manual` 人工预设对 `"D"` 同样生效：台架调试用 `STEP_QR_SET_TEST` 伪装结果，不碰真码；
- 主摄租约与人质识别共用：路线里扫码与人质本来就不并发，保持现顺序即可。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 臂体/夹爪遮挡画框（样张下缘已贴近） | 录位姿时以 Pi Web 预览确认全码入画；位姿里手臂再抬高一点 |
| 板面眩光（样张左下高光） | 压短曝光 + CLAHE + 多帧投票；硬件终极手段是码板贴亚光膜 |
| 摆臂运动模糊 | 位姿预设用阻塞播放，到位后约 200ms 再触发扫码（步骤间天然有间隔） |
| 与 Web 预览抢主摄（跨进程无协调） | 比赛时不开浏览器预览（与现状同一纪律），`_qr.py` 的 5×0.3s 重试兜底 |
| 比赛规则对臂动作的限制 | 斜视摆位只是臂的原位小幅转动，先核对规则允许 |

## 8. 明确不改动清单

- `ucRpiWaitQrResult()` / 结果帧格式 / 无新增任务码与 TAG（"D" 与 "1" 结果同构）；
- `app_rpi.c` 的 `qr_manual` 门与蜂鸣约定（共用 `ucQrScanCommon`，不复制第二份）；
- 下游所有 `iGetQrCode()` 消费方（排爆首位、反恐第三位、`SCRIPT_COND_QR`）；
- 预设 17（挪近重扫）原样保留，本方案只是在其失败分支后**插入**一级，而不是替换。

### 落地顺序建议

1. **先做 A**（Pi 解码升级）——它独立成立，顺手把"远处正视"的成功率也提上去；
2. **再做 B**（录位姿 + 标定矩阵），半天工作量；
3. **最后做 C**（map.c 串流程）+ D 验收。全程固件协议层零改动，随时可回退
   （删掉新预设即回到现状）。
