## 1. 实测事实（修复前先知道这些数字）

来源：Pi 日志 `/home/xixi/Desktop/GKS_Competition/logs/20260926_123128_log.txt`（2026-09-26 台架实测）。

- **冷打开一台相机 ≈ 1.5~2s**（`[INFO] 摄像头 /dev/camera_Qr 打开成功` 距指令到达 ~2s），不是代码注释里写的 ~1.3s。
- **扫码解码本身只要 0.56s**（`检测到二维码 [wechat]: 233（用时 0.56s）`）——开相机占识别步骤的大头，**预热方向本身是对的，值得修，不要砍掉这个功能**。
- **整份日志里没有出现过一条 `"B"`/`"C"` 预热指令**——当前跑的所有视觉步骤全是冷开。也就是说「预热没效果」的第一层原因是**预热根本没在发**（详见 §2）。

预热收益公式：`省的时间 = min(开相机耗时≈2s, 预热指令与识别指令之间的间隔)`。间隔不够 2s 的预热等于白预热（甚至因为 acquire 原地等预热落地而持平）。

## 2. 问题一：为什么预热看不出提速

### 2.1 路线里现在没有任何预热步骤

- 单片机侧积木和指令链路是**好的、现成的**：`STEP_RPI_SEND_TASK`（app_script.c:745）+ `RPI_TASK_WARM_QR/WARM_MAIN`（app_rpi.h:202-203，任务码表 app_rpi.c:99-100 对应 `"B"`/`"C"`），只发不等、无需等待结果帧。**固件不需要任何改动**。
- 但当前 map.c 里唯一的路线级预热积木（原预设 17 开头的 `STEP_RPI_SEND_TASK 预热扫码相机`）**在已提交版本里就是注释掉的**，本次工作区改动（预设 17/18/20/21 改写为就地嵌套 IF）更是把整个预设删掉了。
- map.c:63-65 那段「⚠️ 预热步骤: 让 Pi 在车移动的这几秒里把扫码相机开好……」成了**悬空注释**——它下面没有任何预热步骤。

### 2.2 全仓库唯一还在发预热的点是 OLED 菜单，但窗口不稳定

`app_script.c:1095`（`SCRIPT_REQ_TASK` 分支）在跑三条任务预设（色球放置/激光射靶/人质抓取）前无条件发 `RPI_TASK_WARM_MAIN`。它的预热窗口是「机械臂待命展开」那段阻塞播放——**但只在 `ucGetArmDeployed()==0`（本上电周期第一次）时才存在**。第二次以后跑任务，`"C"` 与视觉指令几乎同时到达 Pi，`acquire()` 原地等预热落地（上限 `LEASE_WARM_WAIT_S`=2.5s），总耗时 ≈ 冷开。这正是「预热与不预热几乎一样」的直接原因。

### 2.3 人质抓取预设的首步把窗口吃掉了

map.c 预设 16（OLED人质抓取）首步是 `STEP_ARM_PLAY_NO_WAIT`（非阻塞摆臂 `ARM_ACT_13`），紧接着就是人质识别——即使有展开窗口，非阻塞也让不出时间。另外人质识别要换 `hostage` 曝光档，租约命中后还要再丢 0.5s 收敛帧（`_discard_until`）。

### 2.4 修复办法（单片机侧，改路线不改固件）

1. **把预热积木排回路线**：在预设 1（默认路线）里、**≥3~4s 的移动段之前**插一块 `STEP_RPI_SEND_TASK / RPI_TASK_WARM_QR`。推荐位置：`STEP_DEAD 按主按键开始` 之后、`斜线到出发区中央`（70mm）+`前进准备扫码`（475mm）之前——这两段移动合计有数秒窗口，且紧贴第一次扫码。注意租约空闲看门狗 `LEASE_IDLE_TIMEOUT_S`=15s，**预热与使用点间隔别超过 ~12s**。
   - 用 Web 控制台「地图」Tab 加（推荐，避免手写格式踩雷）；手写则遵守 map.c 头部的预设规则（表头 5 行以内等）。
   - 顺手处理 map.c:63-65 的悬空注释：要么让预热步骤真的落在它下面，要么删注释。
2. **预设 16 首步改阻塞**：`STEP_ARM_PLAY_NO_WAIT ARM_ACT_13` → `STEP_ARM_PLAY_WAIT`，给 `"C"` 预热留出摆臂窗口。预设 15（激光射靶）首步已是 WAIT，不用动。
3. 主摄重扫链（预设 1 里的 `STEP_QR_SCAN_MAIN_WAIT` 系列）之前的 `STEP_ARM_PLAY_WAIT ARM_ACT_19/22` 摆臂段也可以各插一块 `RPI_TASK_WARM_MAIN`，但注意那两段摆臂本身只有 1~2s，收益有限，可选。

## 3. 问题二：相机随机打开失败的根因（按可能性排序）

「索引打开失败」的报错原文是 Pi 端 `camera.py:66` 的 `[ERROR] 无法打开摄像头索引 {index}`（`cv2.VideoCapture` 打不开设备节点）。

### 3.1 【主因】GKS_Web 预览页跨进程独占相机

- `GKS_Web/app.py::_send_stream`（~2043 行）：页面开着预览就一直 `open_camera` 占住设备，直到浏览器断开/页面点「退出」。
- main.py 进程里的 `handler._stop_main_stream()`（handler.py:304-313）只能停**自己进程内**的推流，对 GKS_Web 进程是空操作。`_cmd_warm_main` 的注释（handler.py:342-345）自己承认了这一点：「比赛时若有人开着 Web 预览，这里会打开失败、只打一条 [WARN]」。
- 后果链：预热 `"B"`/`"C"` 撞上推流 → `[WARN] 相机预热失败`（一闪而过）→ 随后的识别任务 `_open_with_retry` 重试 5 次 × 0.3s 也抢不回来（推流不会自己停）→ 报「打开失败」。**谁先开到设备谁赢，所以表现随机**。赛场只要有人开着预览页看车就必现。

**修复**（推荐做法，复用现成端点，不需要给 GKS_Web 加新东西）：

GKS_Web 已有 `GET /abort` 端点（`app.py:1855` `_handle_abort`）：带 `?cam=main|qr` 停指定相机的推流，不带参数停全部。端口 9000。

在 `camera_lease.py` 里加一个仅本机用的兜底：**任何一次 `open_camera` 失败后，先 HTTP 打一下 `http://127.0.0.1:9000/abort?cam=<main|qr>`，等 0.3s，再重试一次打开**。建议包成一个小助手（stdlib `urllib.request`，超时 0.5s，任何异常静默忽略——GKS_Web 没在跑时是 Connection refused，属正常），在两处使用：
- `_Lease._open_and_serve()` 里 `open_camera` 返回 None 之后；
- 模块级 `acquire_camera()` 的冷开兜底路径里（tasks 的 `_open_with_retry` 会多次调它，天然形成重试）。

注意：`/abort` 会连带 `set()` 页面内正在跑的识别（`_scan_abort`）——这是可接受的，页面识别与车上任务本来就在抢同一台相机，语义上就该车优先。

### 3.2 【次因】预热等待上限太薄 → 进程内双开竞态

`config.py:70` `LEASE_WARM_WAIT_S = 2.5`：`acquire()` 等「正在进行的预热」落地的上限。而实测打开就要 ~2s，余量仅 0.5s。Pi 一忙（YOLO 首次加载、日志 IO），预热线程超 2.5s 还没落地，`acquire` 返回 None → 调用方兜底 `open_camera` **与预热线程同时开同一台设备** → EBUSY。重试循环每轮会重新查租约，预热落地后能自愈，但 5 次重试用尽就是一次「随机失败」。

**修复**：`config.py` 里 `LEASE_WARM_WAIT_S` 2.5 → **4.0**（它是 `EDITABLE_CONFIG` 成员，改默认值即可，Web 可调性不受影响）。

### 3.3 【低概率但致命】`release_now()` 在窄窗口抛异常 → 设备被孤儿句柄永久占住

`camera_lease.py::_open_and_serve`（136-153 行）：在锁内认领 `self._cap`、创建读线程对象，**锁外**才 `th.start()`。这一瞬间若 `release_now()`（256-273 行）进来：
1. `release_now` 清空租约状态，对那个**还没 start 的线程**调 `th.join(timeout=1.0)` → Python 抛 `RuntimeError: cannot join thread before it is started`；
2. 异常让 `release_now` 在 `CameraManager.release(cap)` 之前就中断了；
3. `_open_and_serve` 随后 `th.start()` 成功，读线程握着 cap 继续跑——但租约状态已被清成「空闲」，**没有任何路径会再关它**；
4. 这台相机从此一直 EBUSY，直到重启 main.py。窗口极窄，但命中一次就表现为「莫名其妙再也打不开」。

**修复**（两道都做）：
- 把 `th.start()` 挪进**认领 `self._cap` 的同一个临界区**内（原注释要求「判 _pending 与认领 _cap 同一临界区」的不变量保持不变；线程 start 本身很快，持锁启动没有问题）；
- `release_now` 里给 join 包一层 `try/except RuntimeError` 作为保险。

### 3.4 【连带】`release_now` join 超时后「边读边释放」

`camera_lease.py:269-272`：`th.join(timeout=1.0)` 超时后仍直接 `CameraManager.release(cap)`——若读线程正阻塞在 V4L2 DQBUF 里，就是对使用中的句柄做 release，行为未定义。

**修复**：join 超时（`th.is_alive()` 仍为真）时**跳过 release 并打 WARN**（把 cap 的所有权留给读线程，读线程退出时自行 release），宁可漏放一次（15s 后看门狗……注意此时租约状态已清，看门狗管不到孤儿 cap——所以 §3.3 的修复才是主修，这里只是防御性兜底）。

### 3.5 【待查证】USB 硬件层因素

- `fix_device.sh` 没有做任何 USB 电源管理（无 autosuspend 处理）；两台 1080p MJPG 相机都挂在同一个 USB hub（1-1.1 / 1-1.2）。
- 排查法：复现「打开失败」时看 Pi 的 `dmesg | tail -50`——若时间点上有 `uvcvideo` 设备消失/重枚举记录，则是硬件/电源层（hub 供电不足或 autosuspend），软件修不了，考虑 Powered HUB 或内核参数 `usbcore.autosuspend=-1`。
- 若 dmesg 干净、只是 EBUSY，那就全是上面的软件问题。

### 3.6 顺带澄清一个猜测（不需要修）

「打开 A 相机去做需要 B 相机的任务」这个方向代码是**对的**：`acquire()` 拿到旧租约会先 `release_now()` 再冷开新相机（camera_lease.py:230-235），`warm()` 换目标同理（186-187 行）——只是退化成冷开（慢但不出错）。
真正要小心的是**反方向**：发 `"B"` 预热扫码相机会顺手关掉租约里的主摄——如果此刻靶标流（`"7"`，同样走租约）正在用主摄，**正在跑的流会被掐断**。当前路线没有这种组合，但建议在 camera_lease.py 文件头注释里钉死这条纪律：「预热会牺牲租约里的另一台相机；排路线时不要在靶标流运行期间发预热」。

## 4. camera_lease.py 的两处确定性 bug

### 4.1 `warm()` 命中同相机换档后没有更新 `self._profile`（169-182 行）

```python
if self._cap is not None and self._is_qr == is_qr:
    if self._profile != prof:
        self._reapply_exposure(prof)
        self._profile = prof      # ← 缺这行。后续 acquire() 判档位仍是旧的，
                                  #   会再设一次曝光、再丢 0.5s 帧
    self._last_use = time.time()
    return True
```
`acquire()`（226-227 行）是两行都写了的，`warm()` 漏了后一行。补上即可。

### 4.2 `_reapply_exposure` 没清 `self._latest`（195-211 行）

只设了 `_discard_until`，没清 `_latest`：换档后 0.5s 收敛期内，`LeaseHandle.read()` 照常把**换档前那一帧旧图**发给任务反复解码（读线程只是不再存新帧，旧帧还在被发放）。修法：设置 `_discard_until` 的同一临界区里加 `self._latest = None`。

## 5. 实施顺序与验收标准

按优先级：

1. **`LEASE_WARM_WAIT_S` 2.5 → 4.0**（config.py:70，一行，先消掉双开竞态）。
2. **跨进程仲裁**（§3.1：open 失败 → 打 `127.0.0.1:9000/abort?cam=…` → 重试）。
3. **修 §3.3 / §3.4 / §4.1 / §4.2**（都在 camera_lease.py 一个文件里）。
4. **单片机路线改造**（§2.4：预设 1 加回预热积木；预设 16 首步改阻塞；清悬空注释）。
5. （可选）预热失败日志打得更响：`_open_and_serve` 失败分支现在只有一条 `[WARN] 相机预热失败`，把它改成带相机名 + 「检查是否有人开着 GKS_Web 预览」提示的一行，方便现场区分「预热没生效」和「预热了但没窗口」。

**验收标准**（改完在台架跑一轮完整路线，看 Pi 日志）：
- 出现 `收到指令: b'B'`（或 `b'C'`）且 `相机预热完成` 这行**早于**对应视觉指令到达；
- 命中租约的视觉步骤**不再出现** `摄像头 … 打开成功`（租约命中不打开日志）与随之的 ~2s 空档，扫码步骤从指令到出结果应 < 1s；
- 开着 GKS_Web 预览页跑全程，不再出现 `[ERROR] 无法打开摄像头索引`；
- 连续跑 10 次任务预设（臂已展开、无展开窗口的情形）+ 反复开关预览页，无一次打开失败。

改完记得：改 Pi 仓库要重启 `gks.service`（或让单片机发 `"r"`）才生效；改 GKS_Web 要重启它的服务。两边仓库各有 CLAUDE.md，改完按各自惯例同步文档。

## 6. 别踩回去的坑（改动时保持这些不变量）

**树莓派侧：**
- `handler._cmd_warm_qr/_cmd_warm_main` **必须保持非阻塞**（串口接收线程内联调用，阻塞会压住心跳 → 单片机 8s 判断链）。
- `"B"`/`"C"` **刻意不在** `handler.handle()` 那个「先停巡线/靶标流」的互斥元组里（handler.py:802-810）——`"B"` 恰恰排在巡线之前，停巡线是错的。别顺手加进去。
- `lease_watchdog` 看门狗线程（main.py 启动）**不能删**——它是「预热了但没跟进识别」时唯一会释放相机的安全阀。
- tasks/*.py 只调 `acquire_camera()` / `release_camera()`，不要直接碰 `LEASE` 内部；`LeaseHandle.release()` 是**故意的**空操作（老任务的 finally 里留着 `CameraManager.release(cap)` 也不能真关设备）。
- `camera.py::CameraManager.open` 的 V4L2 初始化顺序（分辨率 → FOURCC → 分辨率 → 曝光 → 15 帧预热）不能乱，文件头注释写明了原因。
- `_MS_COMMANDS` 白名单（`1/D/E/F`）与「超时随指令下发」机制不动。

**单片机侧：**
- `ucQrScanCommon` 的「超时随指令发给 Pi、本端必后到期」契约不动（app_rpi.c）。
- `STEP_RPI_SEND_TASK` 是只发不等，不要给它加等待。
- 手改 map.c 遵守仓库 CLAUDE.md 的规则：表头 `/* ===== 预设: xxx ===== */` 必须在数组行上方 5 行以内；新预设一律追加到文件最后；改完让浏览器 Ctrl+F5 再从控制台保存。
