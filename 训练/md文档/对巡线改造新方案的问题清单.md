> 评审前提：该方案的事实性指控我们已逐条实测核验（见 §1），**大部分属实**，
> 包括对我们已写代码的两条有效批评（颜色身份门在路口失效、点集切换不连续）。
> 本文档只列**该方案仍然存在的问题**，按严重度排序。核验日期 2026-09-23。

## 一、【安全·最严重】连续 valid=1 拆掉了"真丢线即停"，且兜底在地图边缘必然失效

方案让 offset 饱和演化、valid 恒 1，唯一的急停兜底是"颜色谁都不像 → valid=0"。
问题：**车冲出地图外缘时看到的正是边界区色（灰地板），与 ref_zone 高度相似**——
不存在"谁都不像"的悬崖。于是车会以满偏横移一路跑到 `LINE_MAX_DURATION=1000s`。
方案在"代价"一节承认了这一点，但把它写成"不再有防跑飞"的等价交换；
实际上旧机制（持续丢线→停）拦住的恰恰是"冲出地图"这个最危险的场景，
新方案里它**必然**不触发，而不是偶尔不触发。

## 二、严格一次性参考锁有两个比 EMA 更糟的失败模式

1. **锁不上 → 该站永久瘫痪**：锁定门要求 margin≥35 且 8/8 内点且 |offset|≤40
   在收到 'G' 后头 N 帧内同时成立。11 个收敛站的起点不全是"摆正"状态
   （减速带后、路口附近起巡的段），凡是起点不理想，参考永远锁不上 →
   valid 恒 0 + 报警，**这一站巡线彻底不工作**。EMA 的最坏情形是"慢一点/漂一点"，
   严格锁的最坏情形是"零输出"，失败模式更硬。
2. **锁错/冻错 → 无法自愈**：锁定后 α≈0.03，参考基本冻结。用户的地图
   **黄区与灰区并存**（练习图黄、标准图灰），第一段锁下的参考色到后段失配时，
   判向（d_other − d_near ≥ 0.3×sep）系统性失准且永不恢复。
3. 它对 EMA 的污染指控被夸大：EMA 只在有效帧（margin≥20）更新，α=0.25，
   "margin 下滑途中下带大半是边界色"的污染窗口只有几帧，参考移动量是百分之几，
   不是"结构上无法自愈"。

## 三、"交界在窗内却定不到 → 朝远端 −100"是无论证的方向猜测

路口处交界就在窗内但穿越检测失败（margin 正常、点定不到）时，方案把 offset
推向 **−100（远离边界方向）**。若此刻实际边界在近端（下方，检测恰好在近端失败），
这是**朝边界冲**。该状态的方向选择在方案里没有任何论证，属于把启发式写成了定则。

## 四、NEUTRAL=−3.0 硬编码：跨仓库耦合之外，还有一个更实际的坑

`line_angle_target` 是**蓝牙可现场改的运行时参数**（app_beam.c 参数表、OLED 菜单都能改，
这正是它的设计用途——现场标定相机安装角）。OpenMV 里把 NEUTRAL 硬编码成 −3.0 后，
现场每调一次目标角，"弃权"就变成"按调增量的常值旋转"——比 angle=0 那个 3° 常偏
更难排查。方案自己在注释里写"改一边必须改另一边"，等于把一个跨进程的运行时参数
降级成了编译期常量。更稳的做法是协议里带一位"弃权"标志（方案自设了"不动帧格式"
的约束，但这个约束本身值得重新掂量——加字段的收益被它低估了）。

## 五、时序自相矛盾：主打的拐角判据，最怕它自己推迟处理的褶皱

方案风险节承认：褶皱假点会抬高**全点 RMS** → 拐角判据误命中 → **误弃权**
（弃权期间航向不修，车头保持进拐角前的朝向滑过去）。而它把唯一的褶皱对策
（追踪门，参数 35px 与我们已验证的实现相同）推到"等有褶皱实拍图再补"。
**主判据和对它的已知污染源应该同批落地**，否则新方案上线后最先出现的事故
恰恰是它自己预言的"误弃权"。

## 六、整个方案没有回答用户最初的抱怨："越来越偏、越来越不灵敏"

gyro_w=0×11 已证实 → **我此前把该症状归因于陀螺目标陈旧的诊断对实际路线不适用，
在此更正**。但方案对"越来越偏"只字未提，删除陀螺融合只是清理死代码，
不解释症状。在 gyro_w=0 的既成事实下，剩下的候选原因是：
- 相机 −3.0 安装标定本身漂移（减速带撞击 → 支架角度变化 → 越跑越偏，与症状的时间
  特征吻合）；
- 图像角的零点随横向位置/路段几何漂移（同一物理平行在不同站读数不同，
  单一 −3.0 目标无法逐站成立）；
- 角度符号/尺度在某站反转。
这些都需要排查项，方案里一个都没有。

## 七、小项

1. "不产生台阶"言过其实：切换点 PID=0.7 被覆盖为 0.5，是 0.2 的跳变（≈6rpm），
   比现状的 0.4 小，但不是零；
2. "加第 5 字段无收益"忽略了**调试性退化**：连续 valid=1 之后，现场日志永远打印
   `有效=1`，从日志上再也看不出车什么时候真丢了线（配合 §1，这是排障能力的净损失）；
3. "Pi 始终在 PID 一条路上"更多是修辞：|err|≥1 后 PID 输出本来就被 ±0.5 覆盖分支
   丢弃，两条路合并成的是"一个幅值"，不是"一条 PID 路"。

## 八、它做对的、应当吸收的（公平起见）

1. **拐角判据**（全点 RMS / 两半斜差）——采纳了我方反驳的口径，数值与我们独立复测一致；
2. **颜色身份门在路口失效**的批评——实测属实，二分假设在路口不成立，门必须修或弃；
3. **angle=0 ≠ 弃权**的固件语义考据——准确（死区 0.5° 实测核对无误）；
4. **PC 桩 + importlib 加载真源码做回归**——工程上很好的主意；
5. 风险小节的自省（OFFSET_SLEW 是拍的、7 张静帧标不出动态阈值）——诚实。

## 九、两条路线的取舍建议

- **方案 A（该方案）**：连续 valid=1 + 参考严格锁 + 删陀螺融合。
  收益：输出连续、架构"名实相符"。代价：§1 的跑飞风险、§2 的锁失败、§6 未答。
- **方案 B（在已有部署上修三处）**：保留 state 字段与 Pi 定向找线骨架，只修
  ①曲线判据换全点 RMS/两半斜差（双方已共识）、②颜色身份门在路口失效
  （弃用或加"上侧允许路面色"的路口豁免）、③点集切换加迟滞（如连续 3 帧 ≥6 才切）。
  收益：改动面小、保留急停与日志诚实性。代价：valid 0/1 的硬切换仍在
  （可用 CONFIRM_S 已有的确认窗缓解）。

无论选哪条：**拐角判据必须与褶皱对策（追踪门）同批落地**（§5），
且"越来越偏"需要一个排查项清单（§6），不能再悬着。
